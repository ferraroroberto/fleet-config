# Shared conversation capture

`hooks/transcript_readers.py` is the stored-transcript boundary for `conversation_capture.py`. Hook envelope adaptation stays in `_lib.normalize_payload`; transcript formats are separate native protocols. Capture is deterministic and does not call a model. `conversation_index.py` still digests settled captures through `hub_client` and the local hub; curated memory remains an explicitly approved downstream operation.

## Opt in

Existing `capture = true` projects keep Claude capture only. Codex additionally requires an explicit harness allowlist in that project's registry entry:

```toml
[example]
cwd_prefix = "E:/automation/example"
capture = true
capture_harnesses = ["claude", "codex"]
capture_routing = "flat"
conversations_dir = "conversations"
```

The shipped Codex `Stop` hook invokes the shared capture entry point. It is inert for unregistered projects, `capture = false`, or harnesses outside the allowlist. No project registry entry is opted into Codex by this change. Life OS adoption and launcher UI are separate issues. Claude's existing project hook wiring remains valid. Installed hook changes become live only when this branch is shipped to the primary checkout; native hook trust still follows the harness's normal approval flow.

Before opting in, keep the selected capture directories, generated `index.md`/`index.json` and `.search.db` in the adopting project's ignored private storage. For flat routing, ignore `conversations/`; for skill routing, ignore each skill's `conversations/` and the archive. This engine never stages, publishes, approves curated memory, installs hooks or alters another project's capture preference. A disposable proof can override only its process's `CLAUDE_HOOKS_PROJECTS_TOML` and `CLAUDE_HOOKS_STATE_DIR` to temporary locations.

## Skill routing and marker provenance

Under `capture_routing = "skills"` a skill's Step 0 writes its own name to the project's `active_marker`, and that same session's `Stop` hook reads, deletes and routes on it one turn later. The marker carries no identity, so a session that is interrupted or killed before its `Stop` fires leaves one on disk: whatever session stops next would otherwise adopt it and file an unrelated transcript under that skill (#784). The marker is therefore trusted only when its mtime is at or after this transcript's earliest recorded timestamp — a marker predating the session cannot have been written by it. A source stamping nothing at all falls back to a 12-hour age bound. A rejected marker is still deleted, never left to mislead a third session, and routing continues exactly as if it had been absent: `infer_skill_from_transcript`, then the shared `_archive` — for every configured harness, not Claude alone (#785).

## Harness parity: routing, backfill, rendering (#785)

A Codex session with no `.active-skill` marker used to fall straight to `_archive`, even when its own transcript names a known skill by path — `infer_skill_from_transcript` only ran for `harness == "claude"`. It now runs for every harness. Claude evidence (`<command-name>` tags, a Read tool's `file_path`) still comes from the raw entries only Claude's transcript shape carries; a third, harness-agnostic pass scans the reader-normalized `messages` for a plain skill-path mention in a user turn — the shape Codex naturally produces when a skill names itself ("Use the journal-daily skill from `.claude/skills/journal-daily/SKILL.md`."). Fixing this also fixed a real, previously-dead bug in `_skill_path_re`: a double string substitution left the regex permanently unable to match either slash style, so the Read-tool evidence pass had never actually worked for Claude either.

`render_markdown`'s preamble-stripping and command-tag-stripping used to apply only when `agent == "claude"`. Both now apply by role regardless of harness, so a Claude and a Codex capture of the same conversation differ only in the `agent` attribute and the speaker label (`**Claude**` / `**Codex**`) — not in whether skill-loading preamble survives into the body. Reader-boundary text extraction (`transcript_readers.text_content`) also normalizes `\r\n`/`\r` to `\n`, so a Windows-stored rollout renders with the same line endings as a Unix one.

**Backfill.** A session lost because its Stop hook never fired — most often because a harness's long-lived hosting process (Codex's `app-server`) had not yet loaded the capture hook when the session ran — used to require hand-rolling a synthetic `Stop` payload. `hooks/conversation_backfill.py` is the supported replacement: it scans a harness's own stored-transcript store for sessions whose recorded `cwd` resolves to a registered `capture = true` project, and runs each uncaptured one through the same `write_capture` the live hook uses.

```powershell
E:/automation/fleet-config/.venv/Scripts/python.exe hooks/conversation_backfill.py --project life-os
E:/automation/fleet-config/.venv/Scripts/python.exe hooks/conversation_backfill.py --project life-os --harness codex
E:/automation/fleet-config/.venv/Scripts/python.exe hooks/conversation_backfill.py --project life-os --dry-run
```

Unlike a live capture, a backfilled file's name is stamped from the transcript's own recorded start time, not `datetime.now()` — recovering a session from days ago must not file it as though it happened during the recovery run. Skill routing for a backfilled session always falls through to `infer_skill_from_transcript` (there is no live `.active-skill` marker for a session that's already over). Re-running the backfill over an already-captured session is a no-op: `write_capture`'s existing digest/turn-count dedup, shared with the live hook, already makes an unchanged session a no-write. Applying the session-start filename rule to *live* captures too — making every filename session-anchored rather than wall-clock-anchored — was considered and deliberately deferred; this only changes the backfill path.

**Operational trap.** Codex's `app-server` (the desktop app's long-lived host process backing every session) reads `hooks.json` once, at process start. Shipping a hook change to the primary checkout does not reach a session already running under an older server — only a restart of the app (or the hosting `codex app-server` process) picks up the new hook wiring. A session that ran under a stale server is exactly the failure mode `conversation_backfill.py` exists to recover from.

## Readers and identity

| Source | Supported interpretation | Identity and lineage |
| --- | --- | --- |
| Claude stored JSONL | `user`/`assistant` records, `message.content` text; native append order. Existing Claude command-tag/preamble handling and skill inference remain. | Exact `sessionId`, checked against hook `session_id`. Conflicting session IDs fail rather than inventing a resume. A native resume retaining its ID updates the same capture. Different IDs are separate, even with identical opening text; absent cross-session lineage is unknown. |
| Codex stored rollout JSONL | `session_meta` plus `event_msg.item_completed` containing `UserMessage`/`AgentMessage`, as observed on CLI 0.153.3. Duplicate completed item IDs are scoped by thread and turn. Separately supported older fixtures use `user_message`/`agent_message`. | Exact `session_meta.id`, checked against hook `session_id`; `forked_from_id` becomes `parent_sid`. Native resume keeps its ID; a fork keeps its own capture and points to its parent. The observed fork rollout contains only its new turns: the reader does not invent or fetch inherited history. |
| Codex `exec --json` stdout | Unsupported as a transcript. This stream lacks stored conversation context/identity metadata. | A `thread.started` event is not a stored rollout. `--ephemeral` prevents persistence and is unsuitable for this proof. |
| Pi / Grok / unknown formats | Unsupported until their own readers and native conformance evidence exist. | Never inferred from Claude-shaped hook envelopes or the first prompt. |

Codex `response_item` records mirror conversational events and also contain injected project/global instructions labelled as user input. They are deliberately excluded, as are tool output, reasoning and token accounting. Mixed old/new Codex event generations currently report unsupported, preserving the previous capture rather than silently discarding one generation. SQLite-only/paginated history without a readable rollout path is not supported. Missing source, unsupported format and parse failure are distinct logged outcomes; all leave prior captures intact. Malformed JSON (including a truncated tail), invalid UTF-8 and inconsistent identity prevent writes. A complete-lines source that shrinks below a stored capture's turn count also preserves the existing capture.

New headers extend the existing `<!-- capture sid="…" agent="…" updated="…" -->` grammar with `schema="2"`, a full harness/session key, turn count, content digest, reader format/version, and optional `parent_sid`. Missing fields remain missing; a missing native ID never gets a fabricated resume command. The source path can provide local idempotence for an identified harness with no native ID, but is not recorded as a resume identity. Search only produces commands for an explicit supported harness and safe native ID.

Updates match full harness + native ID across configured routing folders. They use a temporary file plus atomic replacement, and unchanged captures retain their bytes and mtime. Legacy full-ID headers can be updated in place; headerless files and unrelated sessions with matching opening text or matching last-eight ID characters remain untouched. Old prompt fingerprints and filename helpers remain available for existing consumers, but never authorize replacement or deletion. If an older Claude resume minted a new ID without explicit lineage, both captures remain: recovering lineage by prompt similarity would conflate unrelated sessions.

`index.md`, `index.json` and SQLite search remain derivatives. Existing captures retain the established header/body grammar and remain readable. Rebuild with `conversation_search.py --project <name> --rebuild`; it reads originals and only rewrites the search database. Capture identity takes precedence over stale digest metadata. Fork provenance remains in the original header for future consumers. Index turn counts recognize both Claude and Codex labels; filenames carry only a truncated (8-char) key token — the full identity hash lives solely in the header's `key` attribute — and that token stays out of displayed slugs (fleet-config#791).

## Future reader contract

A reader returns `Transcript(status, harness, session_id, parent_session_id, source_format, source_version, messages, entries, detail)`. `messages` is chronological `(user|assistant, text)` from that source's actual conversation, with replay/stream mirrors deduplicated only using native identifiers. `entries` is source-specific routing evidence, never an assertion that another harness shares its schema. `status` is `ok`, `unavailable`, `unsupported`, or `parse_failure`; errors must not become an empty successful capture. `ok` with no native ID is readable but not resumable. Unrecorded lineage stays unknown.

A Pi/Grok reader must add sanitized native fixtures and demonstrate: exact host/version/store schema; authoritative native identity versus hook hints; root/resume/fork lineage; multiple ordered turns; tool/context exclusion; idempotent replay; unrelated equal prompts; malformed/truncated input; private opt-in routing; and non-destructive index rebuilds. Add a native resume mapping only after its syntax and identity are verified on that harness. Do not parse Pi/Grok by reusing Claude's reader because the hook envelope happens to look similar.

### Automatic native Stop proof

Run the separately opted-in native probe from this checkout using the existing interpreter:

```powershell
& E:/automation/fleet-config/.venv/Scripts/python.exe tests/probe_codex_capture.py --model gpt-5.6-sol
```

The probe creates two disposable TEMP repositories and reviewed project `.codex/hooks.json` wrappers, then runs harmless new/resume/fork turns and an unregistered-project control. It requires a positive project `UserPromptSubmit` observation before each matching native `Stop`, readable saved conversation at Stop time, the expected completed model response, and CLI exit 0. The wrapper calls the real `conversation_capture.main()` with the original stdin envelope; only detached digest scheduling is suppressed. A second invocation is explicitly a replay check of bytes, mtime and trigger idempotence. Real CLI search/rebuild must preserve both originals and return their exact native resume commands. Capture storage must be gitignored, and the unregistered project must remain uncaptured even with identical opening text.

Keep normal saved subscription authentication and configuration discovery. `--ignore-user-config` suppressed project hooks in the earlier control and cannot establish absence of Stop dispatch; CLI stream events are also not saved rollouts. The probe checks `codex login status` for ChatGPT, forces the ChatGPT login method and OpenAI provider, removes API-key/base-URL environment overrides, and checks the requested model against the native hook's `model` field. These are observed client controls, not independent provider-side attestation. It disables the two locally configured MCP servers for the invocation and requires no model tool use. No credentials are copied or linked, and no project source is submitted as a probe prompt.

As with the existing native hook conformance probes, project trust is invocation-scoped and `--dangerously-bypass-hook-trust` permits the reviewed temporary hooks without persisting trust. `--approve-for-me` retains automatic sandbox approval review. ### Installed-global Stop proof (#783)

The proof above wires its own project-level `.codex/hooks.json`, which is sufficient for native dispatch but does not establish that the *installed* global `~/.codex/hooks.json` (this repo's own `hooks.json`, junctioned live) is what actually fires for an opted-in project with no project-level override. `tests/probe_indexer_boundary.py` and `tests/probe_codex_capture_global.py` close that gap.

```powershell
& E:/automation/fleet-config/.venv/Scripts/python.exe tests/probe_indexer_boundary.py
& E:/automation/fleet-config/.venv/Scripts/python.exe tests/probe_codex_capture_global.py --model gpt-5.6-sol
```

**`probe_indexer_boundary.py`** is model-free: it invokes the real `conversation_capture.py` directly against a disposable opted-in project and lets `_trigger_delayed_index` spawn its real, non-detached `conversation_index.py` child. `conversation_index.apply_delay()` sleeps for the full `_INDEX_DELAY_SECONDS` (60s) before ever reaching `hub_client.complete()` (`conversation_index.py:403`), so identifying that child by argv and terminating it anywhere inside that window — proven here with ~0.2s latency — guarantees zero live digest calls, with terminal exit accounting and no orphan. This validates the "job ownership controls lifetime, not I/O" boundary called for in #783 without any Codex CLI invocation or model call.

**`probe_codex_capture_global.py`** runs one real, harmless, tool-free turn through the actual installed global `hooks.json` — the disposable temp project carries **no** `.codex/hooks.json` at all, so `--enable hooks` can only resolve Stop/UserPromptSubmit through the real installed entries (`session_state_codex.py` + `conversation_capture.py`). `CLAUDE_HOOKS_PROJECTS_TOML`/`CLAUDE_HOOKS_STATE_DIR` are set only in the launched `codex` process's own environment, pointing at temp files; the run demonstrates that Codex's hook dispatcher does inherit that environment into the hook subprocess it spawns — the load-bearing premise every probe in this file relies on, but never directly exercised for Codex's *global* path until now. Because there is deliberately no project-level hook to carry an observer wrapper, the positive `UserPromptSubmit` observation instead comes from the installed `session_state_codex.py`'s own real side effect: `sessions-state.json` is polled while the turn is in flight and shows `status: "working"` for the exact session id before `Stop` flips it to `"needs-you"`, cross-checked against the same session id embedded in the native rollout's `transcript_path` and the resulting capture's `sid` header.

A background `BoundaryWatcher` thread owns process lifetime for the whole run: it enumerates the launched `codex` process's descendants (plus any indexer child matching this run's unique project name) every 300ms and kills `node.exe`/`node_repl.exe` and the indexer child on sight. **`mcp_servers.node_repl.enabled=false` does not prevent the host from being spawned** — reproducing the exact symptom #783 originally reported, on installed Codex CLI 0.153.4 (one patch past the 0.153.3 used for the project-level proof; `mcp_servers.cua_repl.enabled=false` is not a valid override shape for this build and fails config parsing before any call is made — that server is plugin-injected, not part of the static `[mcp_servers.*]` schema). The boundary here is therefore the live watcher's controlled, reviewed kill, not config-level suppression: after every run the script independently re-snapshots every acted-on pid and requires zero survivors (`surviving_owned_pids`) before reporting `PASS` — a `killed: false` action can mean the process had already exited on its own, which this final sweep distinguishes from a genuine failed kill.

Verified with Codex CLI 0.153.4 on 2026-09-06 UTC: session `01a07784-69c5-7291-bd01-9d24914bcce1` produced `status: PASS`, `captures_found: 1`, `capture_matches_session: true`, `capture_contains_marker: true`, `userpromptsubmit_observed: true`, `all_owned_processes_terminal: true`. Two earlier same-day runs (`01a07781-…`, `01a07783-…`) independently reproduced the same `node_repl.exe`/`node.exe` spawn-despite-disabled-config finding and the same clean post-run sweep; a system-wide process scan after all three runs found zero `node_repl.exe` processes and zero stray `conversation_index.py` children. Evidence roots (`evidence.json`, `argv.json`, `stream.jsonl`, `stderr.log`) are preserved under `%TEMP%\capture783_global_stop_*` and `%TEMP%\probe783_indexer_*`, not committed.

This proof establishes: installed-global `UserPromptSubmit`→`Stop` dispatch to the real hooks, correct capture identity/content on that path, and a demonstrated process-ownership control for both the delayed indexer and the previously-rejected internal host. It does **not** establish a supported config-level suppression for `node_repl`/`cua_repl` — none was found on 0.153.4 either — and does not repeat the fork/resume/unrelated-project dimensions already covered by the project-level proof above.
