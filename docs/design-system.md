This is the *educational* companion to `design.md` / `design.dark.md`. Those two files are **instructions** — terse, machine-readable, telling an agent exactly what to build. This file is the **why**: the problem the design system solves, the prior art we studied, the synthesis we landed on, and the ideas we looked at but did not (yet) adopt. If you come back to this in 30 days and need to remember *what we were doing and which references to re-open*, start here, then read `design.md`.

## TL;DR (30-second recap)

We adopted Google's **design.md** format (design-as-Markdown: machine-readable YAML tokens + human-readable prose rationale, one file) as the fleet's single source of visual + interaction truth for FastAPI + static-PWA web apps. We used **Vercel Geist** for the two-file light/dark convention, the **GitHub mobile app** for the palette/look, and **shadcn/ui** as the reference for component structure + accessibility. The spec is junctioned into `~/.claude/` like the global CLAUDE.md, every session is told to consult it for web-app UI work, and a `/design-sync` skill measures per-app drift from it. This doc records the references behind each of those choices.

## Why this exists

The problem was **drift**. Each web app (home-automation, app-launcher, photo-ocr, voice-transcriber, …) had grown its own ad-hoc palette, its own light/dark values, and — worst — its own *copy-pasted* navigation. home-automation's `tabs.js` literally said *"Mirrors app-launcher's nav.tabs pattern"*: the floating bottom-tab pill was re-implemented per repo, slightly differently each time. Every new app re-invented both the look and the interaction. There was no shared contract for either.

The fix is a **single fleet-wide design system** so every app *looks* and *interacts* the same. The non-obvious decision was the *format*: rather than a JSON token file or a Figma library, we adopted **design.md** — design expressed as Markdown. The value of that choice (per Google Labs, who created the format):

- **LLM-native.** Markdown is the format coding agents understand with the highest fidelity. The spec is *for* the agent that writes the CSS.
- **Captures intent, not just values.** JSON tokens say *what* a color is; design.md's prose says *what it is for* ("use the accent only for interactive emphasis", "status colors signal state, never decoration"). Google's framing: *"Instead of guessing intent, AI agents can know exactly what a color is for, and can validate their choices against WCAG accessibility rules."*
- **No tooling, framework-agnostic.** Plain text, versioned in Git, works immediately, independent of React/Vue/vanilla.
- **A semantic layer.** It encodes rules ("one accent does all emphasis", the navigation contract) that a flat token dump cannot.

That last point is why the **Navigation & interaction** section is the load-bearing part of our spec — it makes two apps *feel* identical, not just match colors.

## What we built

Pointers, not a re-description (the files are the truth):

- **`design.md`** (light) + **`design.dark.md`** (dark) at the repo root — same token names, different values, cross-linked in each `description` (the Vercel convention).
- **Junction** — `install.ps1` symlinks both into `~/.claude/design.md` / `design.dark.md`, so they are live in every session exactly like `global-CLAUDE.md`.
- **Global pointer** — `global-CLAUDE.md` tells every session to consult them for any web-app UI work (Streamlit POC spikes exempt).
- **`/design-sync` skill** (`skills/design-sync/`) — reads *both* spec files, maps their tokens onto a target app's CSS custom properties (light **and** dark), reports drift, and files one deduped `design-drift` issue per repo so `/cleanup-fleet design-drift` can fix a whole bucket at once.
- **shadcn rule** — components are modelled on their shadcn equivalents for structure + ARIA, then skinned with fleet tokens (added in #184).
- **Vendored components** — the actual nav HTML/CSS/JS lives in `project-scaffolding` and is copied verbatim per app (same model as `single_instance.py` / `tray_lifecycle.ps1`), so the spec describes the contract and the scaffold ships the implementation.
- **`/design-review` skill** (`skills/design-review/`) — measures a running app's rendered pages against `design.rubric.toml`; its full-app mode (a section of its SKILL.md) is the whole-app redesign review whose closing step writes each round's learnings back into this file and the spec (Round 8).

## The synthesis — what we borrowed from whom

We did not invent a format; we synthesized three prior arts plus a look:

| Ingredient | Source | What we took |
|---|---|---|
| **Format + schema** | Google Stitch `design.md` | YAML frontmatter, token sections in canonical order (colors → typography → rounded → spacing → components), `{path.to.token}` cross-references, and the 8 fixed prose `##` sections (Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's & Don'ts) — v2 extends this with a 9th **Motion** section for the reduce-motion contract; Round 4 adds three more (**Async data & feedback**, **Touch targets**, **Charts**) for the mobile interaction contracts. |
| **Light/dark convention** | Vercel Geist | Two sibling files, identical token names, different values, each cross-linking the other in its `description`; `*-p3` `oklch()` wide-gamut twins per accent. |
| **Palette + look** | GitHub mobile app | True-black-capable canvas, elevated cards, one blue accent, large radii, colored rounded-square icon tiles, the floating bottom-tab pill. |
| **Component structure + a11y** | shadcn/ui | The markup shape, ARIA roles/states, and keyboard behavior of each control — copied by hand (these apps are vanilla, not React) and skinned with our tokens. |

## The journey (fifteen rounds)

**Round 1 — build the system ([#178](https://github.com/ferraroroberto/fleet-config/issues/178) → [#181](https://github.com/ferraroroberto/fleet-config/pull/181)).** Authored `design.md` + `design.dark.md` on the Google-schema/Vercel-convention/GitHub-palette synthesis above; wired the `install.ps1` junction; added the `global-CLAUDE.md` pointer; built the `/design-sync` drift detector with `design-drift` as a first-class audit bucket. [#184](https://github.com/ferraroroberto/fleet-config/pull/184) followed, adding the "model components on shadcn" rule.

**Round 2 — audit + this doc ([#181](https://github.com/ferraroroberto/fleet-config/pull/181) follow-up).** A review of the shipped spec found three things in the shadcn section: (1) a **broken reference URL** — `ui.shadcn.com/docs/components/base` 404s; there is no `/components/base` page, Base UI is a *primitive backend* selected at project creation, and components live at `/docs/components/<name>` (fixed → `/docs/components`); (2) imprecise terminology — "shadcn base-UI variant" reads as a component variant when Base UI is a backend (tightened to "shadcn Switch", "model on shadcn"); (3) the substantive gap — shadcn components are **React + TSX + Tailwind**, but the fleet apps are **vanilla HTML/CSS/JS**, so you cannot "derive from" shadcn as code; you borrow its *markup + ARIA + interaction semantics* and re-author them by hand (now stated explicitly in the spec). The audit also confirmed `/design-sync` **does** fully consume `design.dark.md` (it reads, maps, drift-checks, and reports the dark theme symmetrically with light) — so a `/design-sync` run does check dark. This doc is the third output of that round.

**Round 3 — v2: component contracts + the polish-round decisions ([#278](https://github.com/ferraroroberto/fleet-config/issues/278)).** v1 was **token-level** (colors, type, radii, spacing) plus the navigation contract, but had no written contract *below* the token layer — nothing said how a card header, a disclosure row, an editor modal, an empty-state, or an icon tile is composed. The home-automation polish round (home-automation#358, closed) drove that app to canon on every token dimension and, in doing so, produced concrete, shipped, on-device-validated component patterns. v2 promotes them from tribal knowledge (they lived only in issue comments) into the spec: a **Component contracts** subsection (`card` header, `modal`, `empty-state`, `icon-tile` — each modelled on the existing Navigation contract's prose), the four decisions the round settled recorded normatively (**switch on = green `success`** not the blue accent, reversed in Round 6; **desktop content centered at `max-width: 772px`**; **one tokenized `:focus-visible` ring** app-wide; **`prefers-reduced-motion` honored** via a new Motion section), and an **`icons.size` token group** (`inline 16 / title 18 / feature 24 / nav-tab 24` — the round-3 original; `nav-tab` was later revised to **20px** on phone-validated geometry, home-automation#118, and 16 / 18 / 20 / 24 is the live step set) that closes the one census dimension never unified (icon sizing was still 16 distinct values). This is the foundational Phase-4 change: the component-vendoring work (project-scaffolding) implements these contracts, `/design-sync` v2 ([#277](https://github.com/ferraroroberto/fleet-config/issues/277)) checks conformance to them, and the fleet rollout migrates apps to them.

**Round 4 — mobile feedback & interaction contracts ([home-automation#409](https://github.com/ferraroroberto/home-automation/issues/409) → [home-automation PR #427](https://github.com/ferraroroberto/home-automation/pull/427), promoted in [#342](https://github.com/ferraroroberto/fleet-config/issues/342)).** The home-automation mobile-UX refinement was validated incrementally on the installed iPhone, then locked by 386 backend tests and 184 Chromium/WebKit e2e cases — and its lessons were broader than visual token alignment, so Round 4 promotes five behavioral contracts to canon. (1) An explicit **async lifecycle** — `loading / ready / empty / stale / error` — where a failed background refresh *preserves* last-known content, labels it `Last updated … · live data unavailable`, and disables freshness-sensitive actions: per [Apple HIG · Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts), cached data is labelled nonintrusively, never escalated to an alert. (2) **Feedback altitude** — passive/background status renders inline beside the affected surface; global toasts are reserved for user-initiated commands ([Apple HIG · Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback): give status *near the item it describes*). (3) **Effective ≥44×44px touch targets** app-wide — [Apple HIG · Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)'s 44pt hit region, with [WCAG 2.2 · Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) legitimizing invisible active-area expansion for isolated compact controls; the on-device lesson the guidelines don't spell out is that **adjacent clusters need real geometry**, because two invisibly-expanded rectangles that overlap route taps to the wrong control. (4) **Responsive, colour-independent charts** — a viewport-aware tick budget recomputed on resize ([Chart.js cartesian tick options](https://www.chartjs.org/docs/latest/api/): `maxTicksLimit` / `autoSkip` / `maxRotation: 0`), no canvas-driven page overflow (holding [WCAG 2.1 · Reflow](https://www.w3.org/WAI/WCAG21/Understanding/reflow)'s 320px single-scroll-direction baseline), and a non-colour second channel — dash + point style + fill — per colour-distinguished series ([WCAG 2.2 · Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color)). (5) The **dense collection** composition — saved automation items as flat summary rows opening staged native-`<dialog>` editors, Save as the only persistence boundary, Delete a labelled in-body danger action — a presentation-only refactor that changed no API payloads. Rejected along the way: a bar-chart history experiment (read as clutter on-device, reverted) and treating desktop Playwright/WebKit projections as authoritative for the installed-PWA shell (they are not; on-device confirmation stays mandatory). The round also settled the **verification split** now written into the spec, the lint, and `/design-sync`: static lint proves *authored* facts (tokens, markup shape, component CSS — including recognizing form-less JS-managed editor dialogs, plus the new `hit-target`, `chart-tick-budget`, `chart-noncolor-cue`, and `async-lifecycle` checks), while effective hit rectangles, overlap, chart-label collision, and page overflow are *rendered* facts that only a browser harness can prove — a clean static scan is not UX conformance, and the canonical rendered-geometry helper is tracked in [project-scaffolding#157](https://github.com/ferraroroberto/project-scaffolding/issues/157).

**Round 5 — the rendered audit ([#962](https://github.com/ferraroroberto/fleet-config/issues/962)).** Rounds 1–4 were written from the spec and from code. Round 5 started from pixels: a read-only Playwright walk of the live app-launcher (iPhone, Android and desktop, light and dark) measured computed contrast against the composited background. Several failures came from the spec itself, not from the app. **Contrast-safe roles ([#963](https://github.com/ferraroroberto/fleet-config/issues/963)).** The spec used one `accent` both as a fill and as text on its own 16% tint. The tint lifts the background, so the active nav label and the tint button fell to 4.13:1 (light) and 3.79:1 (dark), under [WCAG 2.2 · Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum)'s 4.5:1. The status hues had the same problem on their tints. White on the dark primary fill was 3.75:1. Input borders reused the card hairline at about 1.4:1, well short of [WCAG 2.2 · Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast)'s 3:1 for a control boundary. The fix splits each such hue into a fill role and a text role, which is how [GitHub Primer](https://primer.style/product/primitives/color/) already models it (`fgColor.accent` for text, `bgColor.accent-emphasis` for the solid fill). It adds `accent-text` and three `*-text` status twins for text on a tint, `accent-fill` for the solid primary, `control-border` for input boundaries and the switch off-track, and `neutral-soft` for chips. Dark chips had sat on true black inside a dark card, the "black hole" project-scaffolding#159 had already rejected for the active tab. The dark tile fills moved to Primer's emphasis step, since white glyphs on the brighter base hues were 2.5–3.4:1. The token values come straight from Primer's scales. Each ratio is recomputed in `tests/test_design_review.py`, compositing the tint over `card`, so a later token edit that breaks a pairing turns the gate red. Rejected: darkening `accent` itself. It would have fixed the tint pairs, but links and the focus ring would have lost the contrast they need on the dark canvas. **Unselected nav tabs are exempt from the 3:1 boundary ([#1012](https://github.com/ferraroroberto/fleet-config/issues/1012), decided 2026-09-25).** `control-border` raised input boundaries to 3:1, which left a question open when the rubric's COLOR-03 was aligned with the spec ([#996](https://github.com/ferraroroberto/fleet-config/issues/996), PR [#1002](https://github.com/ferraroroberto/fleet-config/pull/1002)): should the nav's unselected tabs get a 3:1 outline too? Roberto decided no. [WCAG 2.2 · Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast) asks for 3:1 on the visual information needed to *identify* a component. A tab that shows an icon and a text label is identified by that label, and the Understanding document excludes such controls, the way a borderless text button is excluded. So unselected tabs, in the phone pill and in the 1100px+ rail alike, draw no outline. The selected tab keeps the accent-soft tint with `accent-text` (4.5:1, the #963 pairing above), which is the one boundary the nav needs to show state. The rejected option was to add a 3:1 border to every inactive tab in `design.md` and the vendored nav. It would have changed every app's nav, put five outlined pills inside an already bounded, blurred bar, and weakened the single-tint cue that marks the selected tab. The spec now names the rule in the Navigation contract. COLOR-03 already measures only inputs, selects, textareas and switch tracks, and design_lint has no nav-boundary check, so neither needed a change. **Type scale and caps ([#964](https://github.com/ferraroroberto/fleet-config/issues/964)).** The five type roles jumped from a 12.48px `caption` straight to a 16px `body`, so every secondary line (paths, status, "last run") fell to the caption. That was 53–59% of the text runs on three app-launcher tabs. Two of the rendered sizes were fractional. [Apple HIG · Typography](https://developer.apple.com/design/human-interface-guidelines/typography) sets body at 17pt with 11pt as the footnote floor, and [Material 3's type scale](https://m3.material.io/styles/typography/type-scale-tokens) puts body at 14–16sp. The fix adds a 14px `body-sm` role for secondary lines, limits `caption` to chips, badges and timestamps, and rounds the scale to whole pixels: 12 / 14 / 16 / 20 / 24 / 32, with a new `heading-md` at 20. The spec had said "ALL-CAPS avoided" while the app shipped five uppercase rules. Rather than keep a rule nobody could enforce, the spec now legalizes one narrow use: an `overline` role for list group headers. Chips go sentence case, and numbers and units are never transformed, because "3M 33S" reads as mega, not minutes. **Width by the shape of the view ([#1113](https://github.com/ferraroroberto/fleet-config/issues/1113), decided 2026-09-30).** The spec had one sanctioned exception to the 772px measure, a multi-column board, and the width checks knew no other. Then the desktop-measure check (#1104) began failing task-os, whose Table, Tree, Board and Today views are full width on purpose. Roberto's answer was to state the reason, not add an exception per app: width is decided per view, by the shape of its content. **One-dimensional content keeps the measure:** prose, a form, settings, one list, a detail pane. Comfortable line length runs to roughly 60–80 characters ([WCAG 2.2 · Visual Presentation](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation), 1.4.8, asks for no more than 80). Past that the eye loses its place on the return sweep, and a control drifts away from the label it belongs to. A lone column across a 1440px window is also mostly empty space with the content pushed to its edges. **Two-dimensional content goes full width, because its columns carry meaning:** board lanes, a data table with many fields, a tree or grid whose columns are attributes, calendar days or a timeline. The user compares across the columns, so squeezing them into 772px truncates cells or forces a horizontal scroll, which hides the comparison the view exists for. Here the extra width is information density, not empty space. **One measure per view.** A full-width view's header and toolbar span with it, and a single view never mixes the two widths. Inside a full-width app its one-dimensional views still keep the measure, which is the part that makes this per view and not per app. **Where the decision lives.** An app declares its wide views in its `.fleet.toml` (`[design] wide_views`, the tab ids), because a checker that infers width from a hard-coded app list stops being a check. The static `desktop-measure` check cannot see views, so with wide views declared and no 772px cap in the CSS it warns and leaves the other views to `/design-review`'s LAYOUT-06. That rule now also fails an undeclared one-dimensional view stretched past the measure, and a declared wide view that does not fill the window. Rejected: an app-level flag ("this app is full width"), because it exempts the settings screen along with the table.

**Round 6 — one signature across the apps ([#1200](https://github.com/ferraroroberto/fleet-config/issues/1200), decided 2026-10-03).** Roberto checked the reviewed apps on his iPhone and found three places where they did not share one look. All three are now written into the spec and checked by `/design-review`. **Settings is never a tab.** The spec already pointed at a header gear (the `page-header` component, the Do list), but the Navigation text also allowed the Settings entry "when Settings is not a tab", and the rubric only failed a nav with more than five tabs. So photo-ocr (three tabs) and voice-transcriber kept a Settings tab within the letter of the rules, and local-llm-hub carried six items. The allowance is removed. Settings is the gear beside the theme toggle on every tab at every nav size, whatever the tab count, and a gear-only tab fails the same way. The reasons are those of [Apple HIG · Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars): a tab bar is for peer sections the user moves between, and a rarely used destination spends one of five slots on every screen; and a gear in the same place on every tab is a landmark the user learns once. **One toast.** The standard is app-launcher's neutral frosted toast (ported from home-automation #782): the nav-bar's glass treatment, centred above the nav, one line when it fits, balanced wrap, and only a real error tints. Apps had drifted (photo-ocr's success toast had a green border). A new `toast` component records the recipe, including the `width: max-content` detail that makes the max-width a real ceiling. The reason success stays neutral is the rule the spec already had for status colours: they signal state, and a toast that reports a completed command is not a state. **Switch on-colour reverses Round 3.** Round 3 recorded "switch on = green `success`, not the blue accent", on the argument that green is the universal on-state. On the real apps Roberto finds a green switch off-palette beside the buttons, tabs and focus ring, which are all the one accent. The fleet's rule is one accent for interactive emphasis, and a switch is interactive emphasis, so `switch.trackOn` is now `accent-fill`. That token, not `accent`, because the white thumb has to hold contrast on the track: `accent-fill` gives the thumb 5.19:1 (light) and 4.63:1 (dark), and the track holds 5.19:1 and 3.73:1 against `card`, over the 3:1 of [WCAG 2.2 · Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast). The thumb position and `aria-checked` still carry the state for assistive tech, so on does not depend on hue. A state toggle (alarm armed) may still use `danger` or `attention`; `success` is never a switch's on-colour. The `/design-sync` contract that enforced green (`switch-on-green`) flips with it and is renamed `switch-on-accent`. Rejected: keeping green as an allowed alternative, which would leave the fleet with two looks again.

**Round 7 — icon buttons draw nothing, references are one pill ([#1259](https://github.com/ferraroroberto/fleet-config/issues/1259), decided 2026-10-05).** The spec sent every icon button to the filled `button-surface` tier, and the vendored header toggles and modal close painted `--close-bg`, a filled square, at rest. In task-os ([task-os#357](https://github.com/ferraroroberto/task-os/issues/357)) that read as a row of painted squares beside plain glyphs doing the same job: the action-row kebab was already transparent at a real 44px. Roberto ruled that an icon is never shaded, even when its target is 44px, and chose to make it the fleet rule (the spec, the scaffold and the rubric change; the apps follow when they are next reviewed). **The icon button is its own component.** A glyph-only control has no fill, border or shadow at rest, one glyph size, and hover and press move only the glyph colour. Its 44px target stays invisible, by the Touch-targets routes Round 4 already set. This is the platform default, not a fleet quirk: [Apple HIG · Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) uses borderless, glyph-only buttons for toolbar and navigation-bar actions, and [Material 3 · Icon buttons](https://m3.material.io/components/icon-buttons/overview) makes the standard icon button a glyph with no container, keeping filled and tonal containers for a selected toggle or one main action. [WCAG 2.2 · Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) is met by the target, not the paint, so a visible square buys no accessibility. A state may still draw itself (pressed, current, expanded, selected, checked), because there the fill carries information. `button-surface` stays the labelled utility tier. **A reference is one pill.** A link to something openable (a folder, an AI conversation, an issue, a URL) is the chip geometry in `accent-text` on `accent-soft`, and no context resizes it into a control box. task-os had a reference chip forced to the control height beside an outlined pill that did the same job. A status pill keeps its status colour on the same shape, which is why the rendered check (COMP-06) compares height, radius, padding and font size but not colour: a closed issue drawn muted is still the one pill. **Why the review needed new rules.** No rubric rule measured a button's fill at rest or chip uniformity, so `/design-review` passed both drifts. COMP-05 fails an icon-only button painted at rest, and COMP-06 fails a screen whose reference pills differ in shape. `/design-sync` gained an `icon button` contract that reads `--close-bg`, so a static scan says the same thing. Rejected: keeping the vendored controls filled as a sanctioned exception, which would have left every app's header as the one painted pair on the screen.

**Round 8 — the full-app review becomes the standard ([#1332](https://github.com/ferraroroberto/fleet-config/issues/1332), worked example [app-launcher#1432](https://github.com/ferraroroberto/app-launcher/issues/1432), steps #1433–#1439, decided 2026-10-09).** Rounds 1–7 each fixed one dimension across every app: tokens, contracts, contrast, type and icon buttons. None of them asked whether a whole app was *composed* well. A tab can pass every token and contract check and still read as crowded, because seven differently drawn status treatments sit above its first useful row. app-launcher's redesign asked that question. Round 1 inventoried the most-used tab (30 items, each with where it lived and how often it was needed), named nine causes of crowding, drew four options at phone width and recommended one. Round 2 extended the chosen option to every tab as **one shared system**. It added an "everything is still here" table per tab, a one-home-per-fact table, a build plan of seven Step N/M issues (shared parts first) and ten decisions, each with a recommendation. Each step shipped as one PR and passed the owner's on-phone check before the next began. The method is now `/design-review`'s **full-app mode** (its SKILL.md), so the next app gets the same review. Its closing **write-back** step puts whatever a round learns into a new Round entry here (the reason) and into `design.md` / `design.dark.md` (the rule). That way the system improves with every app reviewed instead of forking per app. Rejected: a per-app style guide, which would record the same learnings once per app and let the apps drift apart again. The principles below proved out in that round. Each rule lives in `design.md` under the contract named, and only the reasoning is kept here. **The header names only exceptions** (`page-header`). This is [Nielsen's first heuristic](https://www.nngroup.com/articles/ten-usability-heuristics/), visibility of system status, held to the fleet rule that status colour signals state. A line that is coloured all the time teaches the user to stop reading it, and a fixed slogan reports nothing. **A glance card answers the tab's main question** (glance card). This is [progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/): the frequent fact goes on the first screen and the detail stays one tap away. Write the question down before drawing the card. The worked example dropped two planned first cards mid-build. One fact already had a home on another tab (app-launcher#1436). The owner never opened the other tab for its card (app-launcher#1439). **One row anatomy, one renderer** (`action-row`). The Board, the Jobs list and the session list each had their own row, so one session was drawn three ways. [Apple HIG · Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables) and [Material 3 · Lists](https://m3.material.io/components/lists/overview) both define a row as a leading element, text and a trailing element, because the eye learns one shape and then scans many rows. A variation is an optional field, never a fork: the worked example added one optional title glyph to a row shared by two tabs and left every other row byte-identical (app-launcher#1439). **The avatar badge means alive** (`avatar`). Health dots, alive dots, "running" pills and coloured meta text all said the same thing in four ways. One badge on the avatar, borrowed from Tailscale's device list and [Material 3 · Badges](https://m3.material.io/components/badges/overview), says it once. It is the only place `success` appears on a row, because "up" is a state. **Chips for exceptions only, in one tone map** (status chip). Three low-information badges on every row, all saying "normal", were the worked example's most visible cause of crowding. Seven chip styles collapsed into one. A chip that appears only for the exception carries information because the normal case is quiet. Uncommitted work moved from danger to attention because it is not an error. **One home per fact.** Usage was drawn two ways on two tabs, one session's controls were split three ways, and git counts sat in both the header and a button. Each duplicate was a second renderer that drifted, and a copy that went stale because its poll only ran on its home tab. **Detail in a sheet, never a native dialog** (`modal`). [Apple HIG · Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets) keeps a sheet for a scoped task the user returns from. The browser's `confirm()` and `prompt()` cannot be themed, ignore the type scale, the button tiers and dark mode, and block the page while open. **Settings as inset groups** (settings group). This is the [Apple HIG · Settings](https://developer.apple.com/design/human-interface-guidelines/settings) grouped-list pattern. About 40 rarely changed per-agent options left the most-used tab for it. Launch-time choices stayed on the launch toolbar, because launching should never need Settings. **A meter's colour follows pace** (`meter`). The quota line turned amber at 60% of the week even when usage was under the week's pace. That alarm reported nothing, and it taught the user to ignore the colour. The pace tick is borrowed from usage dashboards and screen-time meters. [Apple HIG · Progress indicators](https://developer.apple.com/design/human-interface-guidelines/progress-indicators) covers the bar itself. **Helper copy is a one-line footer** (Typography, secondary lines). A two-line note shown on every visit is noise after the first visit. **Usage beats the inventory.** The inventory's "how often" column is a hypothesis. The owner's answer at the decision or phone-check stage overrides it, through a dated decision-log comment rather than a silent edit. Two of the seven steps were rescoped this way, and both rescopes made the tab simpler.

**Round 9 — the second full-app review ([home-automation#872](https://github.com/ferraroroberto/home-automation/issues/872), steps #879–#886, decided 2026-10-09, built 2026-10-09/10; written back in [#1334](https://github.com/ferraroroberto/fleet-config/issues/1334)).** The full-app mode ran on a second, very different app: a home dashboard with five tabs, 29 closed cards, 26 dialogs saved three ways, about 20 row layouts and 16 chip styles for a handful of kinds of thing (a device, a schedule, a person, an event). The owner accepted all eleven recommended decisions, and the build ran in the planned order: shared parts first, then each tab, Settings last because it receives the moves. Five lessons generalise. **A segmented control was missing from the spec** (`segmented`). Arm mode, AC mode and fan, energy periods, the forecast day, Energy / Money and text size were drawn six different ways, and the alarm's state was a sentence above buttons that looked disabled (a COLOR-02 failure at 4.43:1). One control where the selected segment *is* the state fixed both. This is [Apple HIG · Segmented controls](https://developer.apple.com/design/human-interface-guidelines/segmented-controls) and [Material 3 · Segmented buttons](https://m3.material.io/components/segmented-buttons/overview). A segmented verb (a blind's Up · Stop · Down) is the one trailing item on a row, so the most frequent device action stays one tap. **Modes are not alarms** (status chip). An armed alarm was red every night, Disarm was a success-filled button, and a healthy UPS and every detector were green. Status colour had become decoration, the same failure as Round 8's always-amber quota line. The normal chosen state became the selected segment, with no colour of its own. Red is kept for triggered and amber for trouble, so a red pixel means something again. This narrows Round 6's switch note: a state toggle may still take `danger` or `attention` when its on-state is itself an exception (a destructive mode), but "alarm armed" is no longer the example, because armed is a normal mode. **A dashboard's header may state a fact** (`page-header`). Home's question is "is the house OK?", and its quiet line became the weather instead of a weather card that repeated the tab title. The exceptions-only rule still wins whenever something is wrong. **Connected, not alive, for devices** (`avatar`). The avatar badge carried over from sessions to devices once "alive" was read as "connected and expected to be". A plug that is unplugged on purpose is not broken, so it gets no badge, and the unreachable ones fold into one Offline row instead of a red mark per row. **Settings receives the moves** (settings group). Twelve closed cards hid every value. As inset groups with value-and-chevron rows ([Apple HIG · Settings](https://developer.apple.com/design/human-interface-guidelines/settings)), the first screen reads like a summary ("5 of 7 on", "9 kWp", "Arm and disarm"), and each sheet kept its controls' ids, so the move changed no data logic. Two help catalogues for one voice layer merged into one. One field-level exception surfaced: a 55% value column wraps labels like "Away minutes before arm" at 390px, so compact numeric fields keep their own width. **Ratchet candidates for the rubric** (measurable, each seen in this review): rendered IP, MAC or snake_case text outside a code element (judge J-07); an expanded section with no text and no control (J-09); more than one secondary line per list row (J-10); a dialog commit button quieter than another footer action (J-02). Each is tracked as its own follow-up ([#1336](https://github.com/ferraroroberto/fleet-config/issues/1336), [#1337](https://github.com/ferraroroberto/fleet-config/issues/1337), [#1338](https://github.com/ferraroroberto/fleet-config/issues/1338), [#1339](https://github.com/ferraroroberto/fleet-config/issues/1339)) rather than added to the rubric silently here. Rejected: keeping per-tab chip styles as "local flavour", and a Settings tab, both already settled by Rounds 6 and 8.

**Round 10 — the Chat mode contract ([app-launcher#1472](https://github.com/ferraroroberto/app-launcher/issues/1472), steps #1474–#1479, decided 2026-10-09, built 2026-10-09/10; written back in [#1335](https://github.com/ferraroroberto/fleet-config/issues/1335)).** The third full-app-mode review looked at one surface instead of a whole app: app-launcher's Chat mode, where a finished agent turn gets read, mostly on a phone. The rubric graded the app A (93.3) and none of the four failing rules sat in Chat, so the problem was composition, not tokens. That is the round's first lesson: **a passing token audit can hide a page that reads badly.** One turn rendered as two or three bordered cards, each repeating "Agent · time", copy and a chevron; with tool calls hidden, a turn that edited four files showed no sign of it; at 390px the step title's ellipsis cut exactly the counts that mattered; a `##` heading rendered at the 14px label size, smaller than its body; inline code was a 12px caption on true black inside a dark card; and paths were three-line absolute strings. The owner accepted all eight recommended decisions, and the build ran shared parts first. Four lessons generalise. **Code needs its own two sizes.** A 12px code span read as a timestamp, so `code-inline` is 0.875em of its text. A listing is 13px, the one sanctioned off-scale size: mono is wider than the system face, 14px fits too few columns at 390px and 12px is too small to read a diff on the phone. The black-hole rule from Round 5 extends to code: chips on `neutral-soft`, listings on `card` with a hairline. **A link to something openable keeps one family.** A path to a file the session edited became a linked chip by reusing the `reference-pill` colours on the code chip's geometry, not a new colour or an underline, and only for files the app can resolve without guessing, so a link never lands on the wrong file. **One turn, one header.** Fragments of a turn are not separate messages, so they share one header and flow on the canvas; the user's prompt is the only bubble, which is how chat apps already teach the eye to find "what I asked". Tool work becomes one quiet line per run with its counts outside the ellipsis, and a summary card closes the turn once it is over. **Undo is a request, not a button.** The summary is folded from the conversation, not from git, so a later turn, another session or a commit may have changed the file since; reverse-applying a patch from a phone writes files with no review. "Ask to undo" fills the composer and sends nothing, so the agent undoes it in the open and the user reads the request first. Rejected: a real reverse-patch revert with a conflict check (destructive, and a second source of truth), growing the summary card live while the agent works (the activity strip already carries progress), and linking every path to a read-only file viewer (a new endpoint that widens what the phone can read). **Ratchet candidates for the rubric** (measurable, each seen in this review): a rendered heading smaller than the body text around it; inline `code` under 13px or on a background darker than its card in dark; a single-line row whose trailing counts are cut by an ellipsis at 390px; the same "who · when" header repeated inside one turn. Each is tracked as its own follow-up ([#1341](https://github.com/ferraroroberto/fleet-config/issues/1341), [#1342](https://github.com/ferraroroberto/fleet-config/issues/1342), [#1343](https://github.com/ferraroroberto/fleet-config/issues/1343), [#1344](https://github.com/ferraroroberto/fleet-config/issues/1344)) rather than added to the rubric silently here. **Decided at write-back: one listing size.** The app drew fenced blocks at 13px and its Changed files diff at `caption` 12px. The spec takes 13px for both, because the reason for 13px (a diff must stay readable on a phone) applies to the diff most of all. The app's 12px diff is recorded as open drift for the app to close in its own change.

In grocery the glance card also took the tab's one primary (Fill carts, Record, Apply after a match). The row's meta line got a budget in a fixed order (the date, exception chips, one context name, at most two counts), and only the context name may ellipsize at 390px. grocery's done check is a second legal leading toggle: a check that a second tap undoes. **Priority is a plan, not an alarm** (status chip). task-os painted high priority as a red edge on every row. **Round 12 — a small household app, mostly dates ([parking-manager#112](https://github.com/ferraroroberto/parking-manager/issues/112), steps #113–#118, PRs 119–125; decided and built 2026-10-11; written back in [#1356](https://github.com/ferraroroberto/fleet-config/issues/1356)).** Another full-app review ran on a phone PWA that books parking days, with four tabs and Settings behind the gear. The judge's two baseline "no" answers (J-02, J-04) turned into "yes"; one new "no" (J-10) was a spec conflict, settled below. Most learnings are about date-keyed content, which earlier rounds did not cover. **State is a mark, colour only rings exceptions** (`day marks`, parking-manager#115). A day is its number over one small shape mark (booked, will book, extra day, looking, not booked on purpose), and only a problem day gets a coloured ring, so the eye finds the one ringed cell instead of decoding eight fills. This is Round 9's "modes are not alarms" applied to a grid. **A date tile leads a date-keyed row** (`action-row`, #113, #114): the weekday over the day number, today tinted with `accent-soft`, at the 44px floor and all text at least 14px. A per-device phone check is still owed on all three apps (light and dark, after a force-reload), and the radar's passkey relying-party name now defaults to the new app name, so a machine-local config that pins the old one keeps showing it. app-launcher#1500 and local-llm-hub#735 were still building and wait for a later round. Rejected: unifying the radar's two detail endpoints in the step that merged the tabs (the run sheet calls both from one renderer instead), and an explicit Save button on the radar's sheets (owner decision 5).

**Round 14 — an admin app with no activity table ([local-llm-hub#735](https://github.com/ferraroroberto/local-llm-hub/issues/735), steps #736–#742; decided 2026-10-11, built 2026-10-11/12; written back in [#1386](https://github.com/ferraroroberto/fleet-config/issues/1386)).** The full-app mode ran on the fleet's model hub admin app: five tabs that show hosts, models, services and a chat surface, used on a phone and on a desktop. The re-run on the finished build (two judges, rubric 1.18.0 baseline, 1.19.0 re-run) kept grade A at 93.83, with a ledger diff of 0 fixed, 0 regressed, 0 new and 33 unchanged. The change sits inside the one rule the review marks as the spec's, TYPE-01: the share of text runs under 14px on the five tabs fell from 41–75% to 18–40%, and failing screens went from 30 of 60 to 17 of 205 live and 4 of 216 synthetic. TYPE-02 stays the one accepted exception. J-07 moved from implementation terms as labels and status text to abbreviations only. The judges split on J-02 and J-08, so neither is confirmed. Seven lessons generalise; each rule lives in `design.md` under the contract named. **A pane reached only from a header button is a tab in disguise** (`page-header`, the Do/Don't list). The app hung a telemetry pane off a third header button on five tabs. The header already allowed two actions (`trailingActions: 2`), but nothing said what a third one means: a destination that is not on the tab bar, so the user cannot see it exists or tell where they are once inside it. [Apple HIG · Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars) keeps top-level destinations on the tab bar for exactly this reason. The rule is now explicit: the header keeps its two actions and never a third, and a pane with no nav tab becomes a tab, a sheet or a Settings row. **Raw identifiers are not status text** (Do/Don't). Exception class names, process ids and port numbers sat on the faces as status. They moved into sheets or Settings › About, where someone debugging looks for them. This is [Nielsen's second heuristic](https://www.nngroup.com/articles/ten-usability-heuristics/), match between the system and the real world: a status line speaks the user's words, and the system's own words are kept for the place that asks for them. The existing Don't line on raw infrastructure detail is widened rather than a second line added. J-07's wording is unchanged, because it already fails an identifier used as a label. The measurable part (a rendered `*Error` / `*Exception` name, or a bare port or pid beside a label) extends [#1336](https://github.com/ferraroroberto/fleet-config/issues/1336) instead of entering the rubric here. **When an app keeps no activity table, its tab-gated polls are usage evidence** (`/design-review` full-app step C.1). The app had no usage log, so the inventory's frequency column would have stayed a guess. Each tab polls its own endpoint only while it is shown, so poll counts per endpoint per day in the request log showed which tab was on screen and how often. That gave the round its whole usage picture, and it is now the step's fallback when `usage_summary.py` has no data. **Footnotes go behind an ⓘ info sheet; only a live exception stays visible** (Typography, secondary lines). Eleven permanent helper paragraphs made up most of the baseline's TYPE-01 failures. Round 8 already said helper copy is one line shown only while it explains something; that line is edited, not repeated. A standing explanation (how a value is computed, what a section means) now opens from an ⓘ icon button in a sheet, which is [progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/): the explanation is one tap away for the first visit and costs nothing on every later one. A live exception (a stale value, an unreachable host) stays on screen, because it reports state. **Capacity meters need headroom thresholds** (`meter`). Round 8's meter colours a usage bar by pace, which fits a quota that refills each period. Memory allocated on a host has no period, so a pace tick means nothing there and a colour by pace is undefined. The app drew its memory meters with fixed headroom levels, attention at 75% and danger at 90%, the same levels as its machine gauges. The spec now has an allocation variant: no pace tick, headroom colours, and a token (`meter.allocationAttentionAt`) beside the existing `criticalAt`. [Apple HIG · Gauges](https://developer.apple.com/design/human-interface-guidelines/gauges) describes the same split between a value within a range and progress through a task. **Remove a pane only after a function-by-function table is checked** (`/design-review` full-app step E). The owner used the pane the round removed. The step that removed it first moved every function to a new home, then checked a numbered 19-row table (function, new home, click path, ✓) one row at a time against the live pane with invented data. A retired route (a URL hash, a stored tab value) still works and lands on the new home. This is the concrete form of the "everything is still here" rule for a removal, where the risk is a function nobody listed. **Decided at write-back.** *Rubric:* unchanged at 1.19.0. The one measurable candidate extends #1336, and the review-tool gaps the run found (a disabled control failing COLOR-02, a walk wait shorter than slow live reads, the app's build id unread) were fixed separately under [#1385](https://github.com/ferraroroberto/fleet-config/issues/1385). *Dark:* the new rules are behavioural, so `design.dark.md` restates them as unchanged and mirrors the new `meter` token; no colour value changes. **A stopping or destructive verb is never the tinted one on a row** (`action-row`; J-03, both judges "no"). The action-row contract tints a row's one visible verb, so on a list of running models the most prominent control was Stop, while the same app drew Stop outlined in a sheet. The owner decided on 2026-10-13 that the outlined recipe wins even when Stop is the row's only visible verb, although Stop frees the memory that is the main reason to open the tab: prominence signals the action the user most wants to take, and a control that ends something should never be the easiest one to hit on a scanning pass, which is [Apple HIG · Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) keeping destructive actions visually apart from the preferred one. The existing "one visible dominant verb" line is edited rather than a second line added, in `design.md` and mirrored as unchanged in `design.dark.md`; the vendored `action-row` snippet carries the tint for every verb, so its contract change is a pointer issue in project-scaffolding, and the hub's own fix is its own issue. *Rubric:* the judges' proposed measurable rule stays a ratchet candidate and is not added to the rubric here. **Stat-label casing across tabs** (J-08, judges split) went to the J-08 ratchet in [#1365](https://github.com/ferraroroberto/fleet-config/issues/1365) at the owner's choice, so every learning of this round now has its home.

**Round 15 — a launcher used all day ([app-launcher#1500](https://github.com/ferraroroberto/app-launcher/issues/1500), steps #1501–#1506; decided 2026-10-11, built 2026-10-12/13; written back in [#1392](https://github.com/ferraroroberto/fleet-config/issues/1392)).** The full-app mode ran on the fleet's own launcher: five tabs (a coordination board, a phone launch pad, code sessions, scheduled jobs, local apps) used every day from a phone and a PC. The usage record shaped the plan before anything was drawn: activity on 31 of 31 days; two thirds of the sessions the owner started came from the phone launch pad, and 85% of those went to 6 of 17 rows; most work now starts from the coordinator's dispatches, whose questions the owner answers mostly in one sheet; jobs run themselves (222 of 305 runs scheduled, 11% failed). The baseline graded B 89.3 live (rubric 1.18.0) and A 93.3 on the synthetic instance; the judge answered 6 yes and 4 no. The owner accepted all ten recommended decisions, and two usage answers added the swipe and the resume-model work. No re-run on the finished build is recorded yet, so there is no after-grade here. The lessons that generalise are below; each rule lives in `design.md` under the contract named. **A tab badge counts every kind of waiting item the tab owns, fed by a poll that runs on every tab** (Navigation, app-launcher#1502, owner decision 1). At walk time six questions waited while the board's badge and header counted only the sessions in the user's turn, and a count fed by a poll that runs only on its home tab is stale exactly where the badge is read: off that tab. [Apple HIG · Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars) uses a badge to say new information waits on another tab, which only works if every kind of it is counted. The badge now reads the owning tab's payload while that tab is up and an every-tab poll elsewhere, and a part it cannot read adds nothing rather than a made-up zero. **Quiet history marks** (`history-mark`, app-launcher#1505, owner decision 7). The jobs list said "fine" thirty times with green dots, so the 11% that failed did not stand out. Muting the healthy mark leaves colour to the exception, the same reason the status chip has no success tone. The unknown mark (skipped, dry run, an unmapped status) is a dash, not a dot, because [WCAG 2.2 · Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color) does not let colour alone tell two states apart, and a muted dot beside a muted dot is no difference at all. **A question is a row** (`action-row`, #1502, owner decision 2). The questions rendered as two-line prose blocks with an amber stripe and filled the phone's first screen. A one-line row with a chevron to the answer sheet is the same anatomy as every other row, and three rows, an "N more" row and one Answer action keep the board visible underneath. **A launch pad's row carries recency** (`action-row`, #1503, owner decision 5). Every used row was starred, so the star sorted nothing, and the rows that took 85% of launches were scattered among the rest. Sorting by last use puts the habit at the top without the owner curating anything, and the words ("used yesterday") say why a row sits where it does; Pin to top keeps a deliberate exception. **Swipe actions** (`row-swipe`, #1503). The owner asked for left and right swipes and said they resume more often than they start fresh. The direction follows the iOS Mail convention, the frequent non-destructive action on the leading side, and the thresholds are the shipped values, now tokens so the next app does not re-tune them. A swipe is a path-based gesture, so [WCAG 2.2 · Pointer Gestures](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures) requires a single-pointer alternative: each swipe action is also the first item of the row's menu, and the panes are hidden from assistive tech so nothing is announced twice. The full-bleed phone list that gives the panes room stayed; its on-device check was still open at write-back, so the spec records it as shipped, pending that check, and says "may". **A plain row verb and a labelled segmented sort** (`action-row`, `segmented`, #1501). The baseline's painted icon-only verb failed COMP-05, and an icon-only timer glyph as the sort control was the judge's J-05. Both answers were already the spec's direction (the unpainted icon button; one segmented track per choice), so the rule lines are short: an icon-only verb is a muted glyph on nothing, still named, and a sort is a labelled segmented control in the filter sheet, which is [Nielsen's sixth heuristic](https://www.nngroup.com/articles/ten-usability-heuristics/), recognition rather than recall. The scaffold side is [project-scaffolding#347](https://github.com/ferraroroberto/project-scaffolding/issues/347). **Resume keeps the conversation's model** (`action-row`, #1503). The owner switches models between conversations often and wanted a resume to keep the one it ran on. A probe at the start of the step showed one agent's bare resume keeps the model and another's falls back to the configured default, so the second gets the conversation's recorded model, falling back to the default with a note in the reply when that cannot be read; the picker's hint says it is for new conversations. **A segmented control is one track** (`segmented`, #1506). The text-size setting was three separate pills; it is now the one segmented track the spec already named for text size, so no spec line changes. **A page header's line is never a fixed slogan** (`page-header`, #1506, owner decision 10). The settings pane carried the same sentence on every visit. With nothing wrong it now shows the running build, so a stale installed app is visible from its own header, and it names only what the pane shows as a problem. **Plain values, chips for exceptions only, path never a label** (settings group, #1506). Healthy checks wore green "Ready" pills, which is a success chip by another name, and a healthy check showed its config path as a label (the judge's J-07). A healthy check is now a plain value, only an exception wears a chip, and the path appears only in a failing check's fix-it line. A related trap: the vendored modal styles every `span` in a sheet row as the row's label, which flattened muted detail lines to full ink; the app overrode it, and the vendored rule is [project-scaffolding#363](https://github.com/ferraroroberto/project-scaffolding/issues/363). **Decided at write-back.** *Rubric:* unchanged at 1.20.0; every measurable candidate is a ratchet issue. *Dark:* `design.dark.md` mirrors the two new token lines (`history-mark`, `row-swipe`) and restates the new rules as unchanged; no colour value changes. **Ratchet candidates for the rubric** (each seen in this round): a page-header line whose text never changes ([#1395](https://github.com/ferraroroberto/fleet-config/issues/1395)), an unconventional icon-only control with no visible label (noted on [#1366](https://github.com/ferraroroberto/fleet-config/issues/1366)), and a config path used as a label (noted on [#1336](https://github.com/ferraroroberto/fleet-config/issues/1336)). **Open points.** *The dark selected segment reads pressed in, not raised.* The `segmented` contract raises the selected segment on `card`, but in dark `card` is darker than the `neutral-soft` track, so the selection reads as inset; the reference `.segmented` does the same. Either dark gets its own `selectedFill` (for example a lighter step than `card`) or the spec says the inset reading is intended. **Closed 2026-10-13 ([#1396](https://github.com/ferraroroberto/fleet-config/issues/1396), owner decision: fix it fleet-wide).** Dark gets its own `selectedFill`: 30% `fg-muted` over `card` (`#353b43`), a step lighter than the `neutral-soft` track (`#262c34`), `fg` on it 9.6:1; light is unchanged. The first idea, a new `card-2` elevated surface, was rejected on measurement: over a card, dark `card-2` (`#21262d`) is still darker than the track, so it would have read pressed in too, and a mix of two existing tokens needs no new token. The fix is in the vendored snippet ([project-scaffolding#377](https://github.com/ferraroroberto/project-scaffolding/issues/377)) and `design.dark.md`'s `segmented` line and Components prose. The full-bleed phone list's on-device check, and a re-run of the review on the finished build, are still owed.

The row menu, written down after it was built ([#1393](https://github.com/ferraroroberto/fleet-config/issues/1393), the contract for the vendored `row-menu` from project-scaffolding#362). Two apps had each fixed the kebab's menu in their own copy, with different stacking, a different surface and a different gap under the button, so the owner asked for one menu everywhere and the `row-menu` contract records what the two agreed on. **Why the band.** A menu opened from a row near the bottom can land under the floating nav pill or run off the screen, so the rule is a band the menu must stay inside (the viewport minus the pill), a flip across the button when it does not fit, and a clamp with an internal scroll only as the last resort, because a clamp hides rows and a flip does not. A menu in a `<dialog>` ignores the pill, which is hidden behind the dialog, and mounts inside it, since the top layer would otherwise cover a body child. **Why `z-index` 200.** It has to clear the nav (120) and a sticky header, and stay under the toast (400) so a message never hides behind the menu that triggered it. **Why the surface is a step above the card.** A menu drawn on `card` would share the fill of the row it opened from and read as part of it, in dark above all; the menu takes `border-muted` there and `canvas-subtle` in light, the same two values the spec already uses for a control's fill, so no new colour enters the palette (the vendored CSS reads them as `--card-2`, the owner's choice on 2026-10-13). **Why it re-places while the anchor reconnects.** A list that polls rebuilds its rows, and a menu that was open reattached to a button that was not yet in the page would draw in the top-left corner; it is held hidden, re-placed each frame for about a second, and closed if the button never returns ([project-scaffolding#373](https://github.com/ferraroroberto/project-scaffolding/issues/373)). The 44px rows are the touch-target floor, and the 16px glyph and 1rem weight-500 label are the `icons.size.inline` and `body` steps, so the menu adds no size to the scale. **Decided.** *Rubric:* unchanged. *Dark:* `design.dark.md` mirrors the `row-menu` token line with the one differing surface value and restates the rest as unchanged.

**A confirm dialog's Delete is outlined too** ([#1403](https://github.com/ferraroroberto/fleet-config/issues/1403), decided 2026-10-13, on [#1364](https://github.com/ferraroroberto/fleet-config/issues/1364)). The `COMP-08` check first exempted a confirm dialog (only a dismiss control beside the destructive one), on the reasoning that the destructive verb is then the dialog's one committing action and the danger tint marks it. Roberto ruled the other way: a destructive verb takes the outlined recipe everywhere, with no tinted or filled exception for the final confirm. The confirm is already a second, deliberate step, so the colour adds no safeguard; what the tint did was make the one control that destroys data the most inviting thing to tap, which runs against [Apple HIG · Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) keeping destructive actions visually apart from the preferred one. One rule with no carve-out is also one the check can measure without guessing what counts as a confirm. The spec's tint-on-`danger` allowance is gone, the check's `confirm` clause with it, and the rubric moved to 1.23.0.

## The two borrowed vocabularies — why shadcn, why Lucide

`design.md`'s **Base UI** and **Icons** sections state the rule; the reasoning behind both lives here (they are one decision, not two: the icon set was chosen *because* it is the component reference's native set).

**Why components are modelled on shadcn/ui.** [shadcn/ui](https://ui.shadcn.com/docs/components) is the reference for component **structure, markup, accessibility, and interaction** because its primitives encode the WAI-ARIA patterns correctly — on whichever headless backend a shadcn project picks, [Radix UI](https://www.radix-ui.com/primitives) or [Base UI](https://base-ui.com/). But these apps are **vanilla HTML/CSS/JS, not React**, so shadcn is never installed: you copy its *markup shape and interaction semantics* (element structure, ARIA roles/states, keyboard behavior) by hand and skin them with the fleet tokens. That is the Round-2 correction — you cannot "derive from" shadcn as code, only borrow its semantics — and it is why the rule is phrased as *model on*, never *use*. The raw headless libraries are often the more direct read when hand-rolling a control (see the Component libraries table below); the same caveat applies to them.

**Why Lucide is the one icon set.** [Lucide](https://lucide.dev) is shadcn/ui's default icon set, and the spec already endorses shadcn as the structural reference for every interactive component — so the glyphs and the component shapes come from the same vocabulary rather than a new, unrelated dependency. It ships ~1,600 icons under the permissive **ISC** license on a **24×24** grid with a **2px** outline stroke — the calm, GitHub-mobile line-icon style this identity is modelled on — as plain **SVG**, so it drops into vanilla HTML/CSS/JS PWAs with no React and no build step. Unlike an icon font it carries no web-font payload, consistent with the system-font, instant-first-paint typography choice. **Rejected:** [Radix Icons](https://www.radix-ui.com/icons) (the set behind the Radix UI backend above) — ~300 glyphs at 15×15 is too small a library to dress a multi-app fleet.

## Ideas not yet incorporated (open horizon)

Things the references take seriously that our spec / workflow does **not** (yet) — recorded so a future pass can decide whether to adopt them, not as TODOs:

- **WCAG contrast as a first-class concern.** Google's whole pitch is that an agent can *"validate their choices against WCAG accessibility rules,"* and the official CLI's `lint` checks WCAG contrast. Our spec lists colors but never declares a target contrast or asserts that fg/canvas pairings meet AA. A short contrast note (or a lint pass) would close this.
- **The official `@google/design.md` CLI** (`lint`, `diff`, `export`, `spec`). We hand-author the spec and built our own `/design-sync` drift detector for *apps*. The official `lint` (structure + broken **token** references — note: it validates `{path.to.token}` refs, *not* external doc URLs, so it would **not** have caught our 404) and `diff` (regressions between versions) are adjacent tooling we could run on the spec itself.
- **`export` to Tailwind / W3C Design Tokens.** An interop path to other token formats. Low relevance while our apps use vanilla CSS custom properties, but recorded as an option if a React app ever joins the fleet.
- **Motion / animation tokens.** ~~Neither Stitch's 8 canonical sections nor our spec cover transitions, durations, or easing.~~ **Partly addressed in v2 ([#278](https://github.com/ferraroroberto/fleet-config/issues/278)):** a **Motion** prose section now covers the `prefers-reduced-motion` contract and the functional-not-decorative rule. Still open: named `motion` *tokens* (durations, easing curves) — v2 added the section and the reduce-motion behavior, not a token group, since the fleet's transitions are still simple enough not to warrant one.
- **"Study real screens before building"** (Mobbin / Refero MCP). The idea that an agent searches real product screens before it builds. We rely on the static spec and do inspiration manually/ad-hoc; folding a screen-study step into the design workflow is an option. The tooling for this now exists off-the-shelf — the *Tools — extract/generate a design.md* references above turn any reference URL into a design.md you can diff against ours, so the open part is the *workflow* (when/where to invoke one), not the capability.
- **Versioning discipline.** We stamp `version: alpha` but don't bump or `diff` across changes. If the identity starts evolving, the CLI `diff` exists for exactly that.
