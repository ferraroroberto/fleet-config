# Cross-agent parity — one source, every agent

One install, one source of truth: editing a hook, the global `CLAUDE.md`, the statusline, or a skill **once** should be live in every coding agent that can read it. The full matrix — what each agent supports, what is wired, and where a class is a deliberate non-goal (#189):

| Config class | Claude Code | Codex | Pi | Copilot | Grok | Antigravity |
|---|---|---|---|---|---|---|
| **Global instructions** (context file) | `~/.claude/CLAUDE.md` | `~/.codex/AGENTS.md` | `~/.pi/agent/AGENTS.md` | `~/.copilot/copilot-instructions.md` | *(reads `~/.claude/CLAUDE.md` — no link needed)* | — *(IDE; no user-home context file)* |
| **Design system** | `~/.claude/design.md` + `design.dark.md` | *(read via `~/.claude`)* | *(read via `~/.claude`)* | *(read via `~/.claude`)* | *(read via `~/.claude`)* | — |
| **Hooks** (code + wiring) | `~/.claude/hooks/` + `settings.json` | `~/.codex/hooks/` + `~/.codex/hooks.json`; context filter wired but fail-open because rewritten command failures are misreported as hook failures (#755) | ✅ context filter via extension middleware (`pi/extensions/context_filter.ts`, #545); other hooks unwired (`tool_call`/`tool_result` surface available) | ✅ context filter via `copilot-hooks/fleet-context-filter.json` → `~/.copilot/hooks/` (`preToolUse` + `modifiedArgs`, #547; TUI delivery upstream-unknown); other hooks unwired | *(reads `~/.claude/settings.json` — payload normalized in `_lib`; PreToolUse can allow/deny only — it can **block** but never **rewrite** tool input/output)* | ✅ context filter via the `agy/plugins/fleet-context-filter` plugin (`PreToolUse` + `overwrite`, #546); other hooks unwired |
| **Skills / prompts** | `~/.claude/skills/` + `commands/` | `~/.agents/skills/` + `~/.codex/prompts/` | `~/.agents/skills/` (same junction) | `~/.copilot/skills/` (own junction) | *(scans `~/.claude/skills` + `~/.agents/skills` — no link needed)* | ❌ no native skills dir — plugin-only |
| **Project/package skills** | scoped `.claude/skills/<name>` | scoped `.agents/skills/<name>` links | same `.agents` links (trusted project) | not probed by scoped installer | native Claude compatibility; no mirror | not probed |
| **Statusline** | `~/.claude/statusline-command.ps1` | native TUI footer (`config.toml` `tui.status_line`) | `~/.pi/agent/extensions/statusline.ts` custom footer | ❌ none | ❌ none | ❌ (IDE) |
| **Settings / permissions** | `settings.json` (manual merge — holds secrets) | `~/.codex/config.toml` | `~/.pi/agent/settings.json` *(tool-managed)* | `~/.copilot/config.json` *(tool-managed)* | `~/.grok/config.toml` *(tool-managed)* | VS Code settings |

The **wired** classes (a single repo source linked into each home) are the context file (all four CLI agents), hooks/prompts/design for Claude+Codex, Pi's footer extension, and **skills for all four CLI agents** — Claude (`~/.claude/skills`), Codex + Pi (the shared `~/.agents/skills` junction), and Copilot (its own `~/.copilot/skills` junction). The links: `global-CLAUDE.md` → `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.pi/agent/AGENTS.md`, `~/.copilot/copilot-instructions.md`; `codex-hooks.json` → `~/.codex/hooks.json`; `hooks/`, `commands/`, `skills/`, and `pi/extensions/` junctioned per the table.

**`global-CLAUDE.md` is agent-neutral**: it reads correctly as any of those files, and the few genuinely Claude-specific sections (the 3-wide Opus sub-agent cap; the Git-Bash-strips-backslashes-in-`settings.json` gotcha) are marked *(Claude Code only — skip on other agents)*. Unlike Claude's `settings.json` (which mixes in machine-local secrets and so stays a manual merge), Codex's `hooks.json` is hooks-only, so it is symlinked live from `codex-hooks.json`. Claude Code routes hooks through `run-hook.ps1` because its settings commands pass through Git Bash on this machine. Codex invokes the Python hook modules directly with short per-hook timeouts, avoiding an unnecessary PowerShell stdin shim and preventing a hook bug from burning Codex's default 600-second timeout.

**Codex patch syntax feedback** (#744) is verified through real `apply_patch` on CLI 0.153.3: all surviving Python targets are compiled once and both errors in a multi-file edit reach the model through structured PostToolUse context. Patch verification failures emit no post event in that client, so no syntax feedback is claimed for those attempts. The [shared edit contract](adding-a-coding-harness.md#shared-edit-events-and-codex-syntax-feedback) preserves native Claude edits and translated Grok writes; the file-policy consumers below use that same contract and inspect every target in a Codex patch (#745).

### Scoped skills and instruction-chain evidence

Project skills use individual same-scope discovery links, with maintained `.claude` or `.agents` sources preserved. Claude and Grok use `.claude` discovery; Codex/Pi use `.agents`. Native compatibility does not justify a second Grok or Pi mirror. See [installer behavior, collisions and worktree cleanup](install.md#scoped-project-discovery). Filesystem diagnosis reports native loading as unknown, and missing clients or unsupported capabilities remain distinct from failed verification.

The repeatable `skills/_lib/discovery_probe.py --run` fixture on 2026-09-05 checks a global skill plus distinct project/package sentinels. Claude Code 2.1.261 initialization metadata, Codex CLI 0.153.3 `skills/list` with reload, and Pi 0.84.4's trusted `DefaultResourceLoader` return global+root / global+root+package / global+root for root/package/sibling sessions, once per sentinel. Claude's catalog establishes names/counts; it does not expose a native source path, so that path evidence remains unknown. Codex/Pi paths are compared with the actual maintained synthetic sources. Skill execution and Pi's interactive trust UI are not established by these inventory checks.

Grok 0.2.118 `inspect --json` has returned both the full ancestor inventory and global+root / global+package / global across fresh fixtures. Native `.claude` compatibility works without a Grok mirror or duplicate sentinels, but reliable ancestor inheritance remains **unconfirmed**. The probe repeats Grok's native inventory: matching full inventories verify that run; matching current-scope-only inventories report the missing capability as unsupported; changing inventories report unknown. Do not infer reliability from filesystem ancestry or the scaffold's earlier summary. Missing clients and unavailable loader interfaces have their own states; neither means a successful native verification.

Instruction evidence is separate. A Claude Code 2.1.261 request assembled for a local loopback recorder contained the actual global file's EOF and every normalized nonempty line except its two HTML system-map delimiter comments; the global source was 35,361 bytes. Synthetic project instructions over 40 KB and nested instructions were present in full through EOF. This used a dummy key, no tools/MCP/session persistence, and no external model request; raw request content was deleted. Claude reads the real Windows user-global instruction path even when synthetic home/config variables are supplied, so this particular local check explicitly permits that one known global file and retains only hashes, counts and booleans.

Codex CLI 0.153.3 native `debug prompt-input` preserved EOF markers in a synthetic global file over 40 KB plus root/nested `AGENTS.md` files, including with `project_doc_max_bytes=32768`: the global file is outside that project-document byte cap. This does not prove a pointer was followed. A separate fresh GPT-6 Astra run with `codex exec --ephemeral --json --approve-for-me` did follow canonical root/nested `AGENTS.md` pointers, read only the two synthetic `CLAUDE.md` targets with one successful `Get-Content` call, and returned exactly `CLAUDE_ROOT_EOF_748,CLAUDE_NESTED_EOF_748`. The native CLI selected its installed PowerShell 7.6.5 executable despite the requested PowerShell 5.1 tool setting; the successful read is observed, not inferred from the requested shell. Approval-never mode could not establish that fact on this host because its shell policy blocked the read; it is not counted as passing evidence. The repeatable full helper subsequently passed with a 40,590-byte global fixture and a 40,589-byte root target. No installed size/fallback configuration was changed.

### Command and edit policy coverage

The table records observed delivery semantics rather than treating a registration as proof. **Blocks** means the target harness prevents the call; **advises** means the nudge reaches model context while the call proceeds; **not verified** means the compatibility path is wired but its user-visible delivery has not been established; **unsupported** means no adapter/wiring implements that policy on the harness; **not applicable** means the harness has no corresponding tool surface. Codex checks run under `--approve-for-me` in a trusted disposable repository, so approval mode cannot be mistaken for the hook's effect. `--ignore-user-config` suppresses project hooks and is only a negative control, never a coverage result.

| Policy | Claude Code | Codex | Grok (Claude compat) | Pi | Copilot | Antigravity |
|---|---|---|---|---|---|---|
| GitHub inline-body quoting (`gh_body_file_guard`) | advises | advises | not verified | unsupported | unsupported | unsupported |
| Dated filenames under `docs/` (`docs_dated_filename_guard`) | blocks | blocks | blocks | unsupported | unsupported | unsupported |
| Branch before launcher-dispatched edits (`branch_before_edit_guard`) | blocks | blocks | blocks | unsupported | unsupported | unsupported |
| Downstream inline `claude -p` (`hub_bypass_warn`) | advises | advises | not verified | unsupported | unsupported | unsupported |
| Browser launch stealth (`browser_stealth_lint`) | advises | advises | not verified | unsupported | unsupported | unsupported |
| Chief-managed question suppression (`block_askuserquestion_chief`) | blocks | not applicable | not applicable | unsupported | unsupported | unsupported |

Codex command payloads use the client-observed `tool_input.command`. Codex edit policies match the edit family but receive `tool_name: "apply_patch"`; `_lib.edit_event()` parses that command as data and returns all add/update/delete/rename targets. Pre-edit blockers inspect intended targets, while PostToolUse advisories inspect final files only after the shared outcome is confirmed successful. `tests/test_codex_policy_coverage.py` pins positive and negative behavior for each newly wired policy, including a second-target violation, native Claude behavior, and Grok's compatibility denial. The acceptance matrix separately derives expected Codex registrations from its explicit policy table, so deleting one expected hook from `codex-hooks.json` fails the gate.

**Grok is wired by *not* wiring it** (#491). Grok Build ships Claude-compatibility scanning that is **on by default** (`[compat.claude]` in `~/.grok/config.toml`), so it already reads `~/.claude/CLAUDE.md`, `~/.claude/skills/`, and `~/.claude/settings.json`'s hooks — confirmed with `grok inspect --json`, which reports the global instructions at 8,720 tokens and resolves 14 user-tier + 13 project-tier fleet skills. Adding a `~/.grok/rules/` link or a second skills junction would have created a drifting duplicate of the fleet's most important file, so neither exists. What *did* need building was translation, not plumbing: Grok's hook payload is camelCase with lower_snake event values (`hookEventName: "pre_tool_use"`, `toolName: "run_terminal_command"`) where Claude's is snake_case with PascalCase, so every fleet hook was firing inside Grok sessions and silently doing nothing while still listing as healthy in Grok's own `/hooks` modal — an A/B of the guards found most of them blocking a dangerous command for Claude and allowing the identical one for Grok. `hooks/_lib.normalize_payload()` translates once at the single `read_stdin_json()` entry point every hook shares; a Claude-shaped payload is returned as the *same object*, so Claude behaviour is unchanged (asserted in `tests/test_payload_normalization.py`). Two behaviours only a live session revealed: Grok reports our exit code `2` as `1` and fails **open** on anything that isn't 2 — so `_lib.block()` also emits Grok's documented `{"decision": "deny"}` on stdout, gated on the detected agent — and Grok fires a second, observe-only `Stop` *after* `SessionEnd`, which taken literally resurrects the Board row that was just deleted. The generalized procedure is [`docs/adding-a-coding-harness.md`](adding-a-coding-harness.md); per-agent state coverage is [`docs/session-state-capability-matrix.md`](session-state-capability-matrix.md).

**Pi and Copilot context paths were verified empirically, not assumed** (#189): a sentinel context file was placed in each candidate location and the agent run non-interactively (`pi -p` / `copilot -p`) from a neutral cwd to see which path it actually read. Pi reads `~/.pi/agent/AGENTS.md` (its `PI_CODING_AGENT_DIR` config dir — it ignores `~/.pi/AGENTS.md` and a home-dir `~/AGENTS.md`); Copilot reads `~/.copilot/copilot-instructions.md` (not `~/.copilot/AGENTS.md`). Both load plain markdown, so `global-CLAUDE.md` links verbatim with no format translation.

**Documented non-goals** (intentionally *not* wired, so this doesn't get re-attempted):

- **Hooks for Pi / Copilot / Antigravity** — ~~none of them expose a lifecycle-hook mechanism~~ **stale as of 2026-08 (#548): all three now do.** Pi's extension API intercepts and mutates tool calls/results (`~\...\pi-coding-agent\docs\extensions.md` — `tool_call` ~705-744, `tool_result` ~768-801); Copilot CLI ≥1.0.70 fires native user-scope hooks from `~/.copilot/hooks/*.json` with `preToolUse` + `modifiedArgs` (live proof: `fleet-config-lite`'s session-state hook; caveat: interactive TUI sessions may fire no hooks — upstream copilot-cli#991/#2201/#1730); the `agy` CLI reads `hooks.json` with `PreToolUse` + `overwrite`. The context filter is now wired on Pi (#545, extension middleware), agy (#546, plugin install — its Go plugin scanner does not descend junctions, so this is the one registry+copy channel, drift-guarded by the acceptance gate), and Copilot CLI (#547, a drift-guarded per-feature file under `~/.copilot/hooks/`; verified non-interactive — interactive TUI hook delivery is an upstream unknown, copilot-cli#991/#2201/#1730). Beyond the context filter, the general hook set remains wired on Claude Code + Codex only, and Grok runs Claude's hooks via compat but can only allow/deny (no input/output rewrite).
- **Settings / permissions for Pi and Copilot** — their settings files (`~/.pi/agent/settings.json`, `~/.copilot/config.json`) are **rewritten by the tool itself**, so symlinking a repo source over them would break the tool or be clobbered on next launch. Left to each tool to manage.
- **Statusline beyond Claude/Codex/Pi** — Copilot and Antigravity have no statusline surface.
- **Skills for Antigravity (`agy`)** — `agy` *does* now ship a CLI, but it has **no native user-skills directory** it auto-scans: `agy --help` exposes no skill/prompt flag, and skills load *only* by installing a plugin (`agy plugin install …` → `~/.gemini/antigravity-cli/plugins/<name>/skills/`). The candidate global paths other tools use (`~/.agents/skills`, `~/.gemini/config/skills`) are not read by `agy` and don't exist on this box, so there is no clean single-source junction to make — wiring it would mean maintaining a forked plugin bundle, the exact drift #160 set out to avoid. Recorded as a non-goal (#160); revisit if `agy` adds a scanned user-skills dir. The other classes (context/hooks/statusline) remain non-goals too — Antigravity is an IDE-first tool with no user-home context/hook/statusline file to link.

**Why Codex skills live in `~/.agents/skills`, not `~/.codex/skills`.** This trips people up because Codex *does* have a `~/.codex/skills/` directory — but that's Codex-owned: it holds Codex's own bundled skills under `~/.codex/skills/.system/` (imagegen, skill-creator, skill-installer, …), marked with a `.codex-system-skills.marker`. The [official skills doc](https://developers.openai.com/codex/skills) lists `$HOME/.agents/skills` as *the* USER skill location — `~/.codex/skills` is **not** a documented user path. So the `~/.agents/skills` junction is correct, and we deliberately do **not** also junction into `~/.codex/skills`: it can't be a whole-directory junction anyway (the installer won't clobber the real `.system/` dir), and exposing each skill via two scanned roots would double-list every skill in Codex's selector (Codex doesn't merge same-named skills — both appear). If you see Codex *guess* a `~/.codex/skills/.system/<name>/SKILL.md` path and 404 before reading the skill from `E:\…\fleet-config\skills`, that's the model fumbling the path once and self-correcting, not a broken link — the skill still loads.

**One format, every agent (#160).** The worry that porting the issue-workflow skills to other agents would need per-agent *translation* turned out to be moot: Claude Code, Codex, Pi, and Copilot have all converged on the **same `SKILL.md` format** (a `<name>/SKILL.md` folder with `name` + `description` frontmatter), and each scans a user-skills directory automatically — Codex/Pi at `~/.agents/skills` ([Codex doc](https://developers.openai.com/codex/skills); [Pi doc](https://pi.dev/docs/latest/skills), which also reads `~/.agents/skills`), Copilot at `~/.copilot/skills` ([Copilot doc](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference), auto-discovered, no enable step or restart). So the whole port is a **junction**, not a translation layer: one `skills/` source, junctioned into each home, edited once. The `_lib/` helper dir has no `SKILL.md`, so every agent's discovery ignores it as a skill (it's still importable by the absolute `C:/Users/rober/.claude/skills/_lib/…` paths the skills call, which resolve on any agent).

**Validated:** all four CLI agents discover these skills live. Codex (gpt-5.5) loads and runs them — e.g. invoking the `screen` skill executed `skills/screen/SKILL.md` straight from the repo. Pi (`pi -p`) and Copilot (`copilot -p`) both confirm `issue-start` in their discovered-skills set via their respective junctions (#160). One Codex-vs-Claude nuance — relevant to **app-launcher#251**, which injects `/issue-start <N>`: Codex's client only treats a message as a slash command when the *whole* message is a registered client command, so a bare `/issue-start 160` line is rejected by the client — invoke a skill mid-message (`check this /screen 3`) or in natural language (`start issue 160`) and it fires. The launcher should inject the natural-language/mid-message form for non-Claude agents.

**Codex sandbox verification.** Sandboxed `codex exec` depends on Codex's Windows sandbox helper binaries under `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\`, which are managed by Codex rather than this repo. If sandboxed sub-agent delegation starts failing with `orchestrator_helper_launch_failed` or `codex-windows-sandbox-setup.exe ... error=program not found`, verify the live runtime path instead of guessing from files on disk:

```powershell
.\install.ps1 -VerifyCodexSandbox
```

That opt-in check runs a real `codex exec --sandbox workspace-write` probe and fails loudly if the helper cannot launch. The same probe can be run directly when debugging:

```powershell
codex exec --sandbox workspace-write "Print exactly: codex-sandbox-ok"
```

If `workspace-write` is broken but Codex still needs to be spawned for urgent fleet work, `--sandbox danger-full-access` is the temporary helper-free fallback. Treat that as a workaround to unblock the run, then repair or update the Codex install and re-run the workspace-write verification before relying on sandboxed sub-agents again.

**Grok compat verification (fleet-config#491).** Grok is wired by *not* wiring it, so there is no link for the installer to check — but that makes xAI's compat defaults load-bearing config this repo does not own. If a cell flips (a version bump, or a managed/`requirements.toml` layer), Grok silently loses the fleet's guards, instructions, and skills with nothing here changing. Verify the reach itself:

```powershell
.\install.ps1 -VerifyGrokCompat
```

The opt-in check runs `grok inspect --json` and fails loudly unless all four `compat.claude` cells (`rules`, `agents`, `skills`, `hooks`) are enabled, the global instructions actually resolve from `~/.claude`, and at least one fleet skill resolves through a scanned root. It verifies resolution, not mere scannability — an enabled cell that resolves nothing is still a failure.

**Rate-limits cache (fleet-config#259 / app-launcher#326).** `statusline-command.ps1` also caches the payload's `rate_limits.five_hour`/`seven_day` (`used_percentage` + `resets_at`) plus a `captured_at` stamp to `~/.claude/hooks/state/rate-limits.json` on every render — a pure additive side effect, written atomically (tmp file + `Move-Item -Force`, retried) so app-launcher's Board and Coding tabs can show current Claude usage % without being the statusline process themselves. `rate_limits` is account-wide, so any active session's render refreshes it for every consumer; either window may be `null` if Claude Code hasn't reported it yet (e.g. before the first API response in a session). Written with a BOM-less UTF-8 encoding (`New-Object System.Text.UTF8Encoding($false)`) — the default `[System.Text.Encoding]::UTF8` emits a BOM that breaks a plain `json.loads` on the reader side.

**Codex statusline parity.** Claude Code's statusline is a custom command (`statusline-command.ps1`) that receives a JSON payload including `context_window.used_percentage`, so it can render `used % | model | project (branch)` with color thresholds. Codex does not use that command surface; it has a native TUI footer configured by `/statusline` or by `~/.codex/config.toml`:

```toml
[tui]
status_line = ["context-used", "model", "current-dir", "git-branch", "five-hour-limit", "weekly-limit"]
terminal_title = ["project", "git-branch", "model"]
```

This is the closest supported Codex shape today: context first, then model, current directory, branch, and the native primary and weekly quota windows. It deliberately uses Codex's built-in items because Codex does not expose a custom statusline command payload or a bare percentage item equivalent to Claude's compact `0%` segment. Codex omits a branch or quota window when its data is unavailable and elides trailing fields at narrow terminal widths; it does not turn missing data into `0%`. Installed CLI 0.153.3 exposed the exact `five-hour-limit` and `weekly-limit` IDs in `/statusline`; at 160 columns an available weekly window rendered and agreed with `/status`, while the same field was elided at 80 columns. Run `.\install.ps1 -ConfigureCodexStatusline` for the idempotent, comment-preserving opt-in merge, then open a fresh Codex terminal. Use `/statusline` to inspect or reorder the items and `/status` to compare available windows. The setting applies only to the terminal TUI: it does not alter the Codex desktop conversation UI or promise custom styling beyond Codex's native theme behavior.

**Pi statusline parity.** Pi exposes footer replacement through its extension API, so this repo ships `pi/extensions/statusline.ts`, installed as `~/.pi/agent/extensions/statusline.ts`. It renders the Claude-style compact footer: `ctx% | model | dir (branch)`, with the same context thresholds (`<30` success/green, `30–34` warning/yellow, `>=35` error/red) and model-family normalization (`opus` / `sonnet` / `haiku`). Known gap: Pi reports context usage as unknown immediately after compaction and before the next usage-bearing response; in that state the extension omits the context segment rather than faking a percentage, matching Claude's "null means omit" behavior. To validate locally, run `install.ps1`, restart/open a fresh Pi TUI session, and confirm the footer shows the compact three-segment line once context usage is available.

**OTel project attribution for Claude Code (fleet-config#310).** `install.ps1` also wires `shell/claude-otel-project.ps1` into both the pwsh and Windows PowerShell 5.1 `$PROFILE`s: a `claude` function that auto-tags `OTEL_RESOURCE_ATTRIBUTES` with the current git repo's name before calling the real `claude.exe`. This is host-level infrastructure with exactly one current consumer — `local-llm-hub`'s OTel receiver, which surfaces a per-project column in its admin panel ([local-llm-hub#234](https://github.com/ferraroroberto/local-llm-hub/issues/234)) — **not** a generic fleet requirement; see [`docs/otel-project-attribution.md`](otel-project-attribution.md) for the full why/how, verification steps, and troubleshooting. Requires a fresh shell after install (`$PROFILE` only loads at shell startup).

**Codex Browser plugin.** Codex's bundled Browser plugin loads its *instructions* even when its *runtime backend* isn't live — `agent.browsers.list()` can return `[]` despite the plugin being enabled in `config.toml`. That backend is Codex-client/runtime state, not a dependency this repo installs. [`docs/codex-browser.md`](codex-browser.md) is the durable note: how to diagnose `iab` availability from a session, why installed plugin files don't mean a registered backend, the restart-and-check recovery path, and — when `iab` stays `[]` — the deterministic **Playwright + real-Chrome fallback** ([`skills/_lib/browser_verify.py`](../skills/_lib/browser_verify.py)) that keeps the `/issue-finish` visual gate operational instead of abandoning it.
