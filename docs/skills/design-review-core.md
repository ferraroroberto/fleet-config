# Design review core (rendered facts, scored from data)

`skills/_lib/design_review/` is the deterministic half of `/design-review` (fleet-config#970; the measure/evaluate core in #971, the renderer, mock-up library and the skill in #972, the bounded judgment stage in #973, the ledger, diff, issue upsert and fleet mode in #974). It exists because `design_lint` reads *authored* CSS and the 2026-09-21 app-launcher audit (#962) found what only a rendered page can show: 93 of 121 controls under 44px on the iPhone projection of a 24-PASS/1-WARN app. Everything the audit had to re-decide by hand is now data and code — which metrics to collect (`measure.py`), the thresholds and severities (`design.rubric.toml`, a flat `[[rules]]` array beside `[meta]`, `[weights]`, `[grades]`, `[penalties]` and `[params]`, versioned on its own), the scoring (`evaluate.py`: each category starts at 100 and loses 25/12/6/2 once per failing P0/P1/P2/P3 rule, letters from `[grades]`, the overall verdict a `[weights]`-weighted mean). Thresholds resolve from `design.md` tokens where one exists (`threshold_token`, `[params.*].token` through `design_lint/spec.py`), else from the rubric's literal — `components.hit-target.min` is the 44px floor the page script measures with, `components.button-primary.height` the 48px `TOUCH-03` compares against, `icons.size` the canonical steps `COMP-02` checks. Every rule carries a stable `id`, `category`, `metric`, `fail_when`, `severity`, `standard`, `fix_template`, `owner` (`spec` | `scaffold` | `app`) and `mockup`, so the next steps render, judge and diff by id without restructuring.

**Two legs, two interpreters.** `measure <repo>` runs in this repo's stdlib venv: `plan.py` resolves the target's loopback base URL from `hooks/projects.toml` (`webapp_port` + `browser_scheme`) and an optional `[design.review]` block from its `.fleet.toml` (`theme_storage_key`, `tab_selector` — resolved inside the first `[role=tablist]`, so `[role=tab]`, never `[role=tablist] [role=tab]` — `no_go`, `extra_steps`: a step may `open` one `details` and then run a `clicks` sequence, each click refused when its element sits inside a `no_go` selector, #995; a step marked `synthetic = true` runs only under `measure --synthetic`, which boots the target's `[design.review.synthetic]` `command` — a throwaway instance with synthetic data that prints `URL=` and exits when its stdin closes — walks it under that block's own `no_go`, then stops it, tree-killing it only after a 30 s grace; the run is `mode: synthetic`, and the ledger diffs it only against earlier synthetic runs); `capture.py` creates the run directory **outside every tracked tree** (`~/.claude/hooks/state/design-review/<target>/<UTC stamp>/`, via the shared `hooks_state.state_dir()` — on this host a junction into the primary clone's gitignored `hooks/state/`, so nothing there can be committed; no retention sweep yet, a full app-launcher run leaves ~144 PNGs), probes the port with a raw TCP connect, and spawns `walk.py` as a child of the **target repo's** `.venv` interpreter — the same `browser_verify.discover_venv_python` / `playwright_probe_cmd` pair the visual gate uses, because Playwright lives in the fleet apps' venvs and this one stays stdlib-only. The walk is read-only by construction: it clicks the primary tabs (`[role=tablist] [role=tab]`) and the header Settings gear (#1217, below), sets `details.open` on every screen kind — tabs, dialogs and extra steps (#995), a disclosure that stays closed staying excluded through `checkVisibility()` (#998), and only the first popover of each family opening (a `<details>` whose body is positioned over the page, grouped by its `name` else its first class: a list's row menus never coexist in the app, #1155) — calls `dialog.showModal()`/`close()`, screenshots each screen (viewport + full-page with details open), and runs the in-page script — computed sizes and families, WCAG contrast against the composited background, effective hit rectangles, icon boxes, radii, overflow, accessible names, controls per row — on a fixed device matrix (`iphone` WebKit at 390px / `android` Chromium / `desktop` Chromium × light/dark). A Chromium full-page screenshot drops the Pixel 7 descriptor's touch emulation (`(pointer: fine)`, `maxTouchPoints` 0, until the page closes), so the Android walk re-enables it over CDP after each one (#1017); otherwise every later Android screen measures the desktop layout. A full-page capture never fails its screen (#1085): a page over the engines' 32767 device-px limit (an iPhone page over ~10,900 CSS px, e.g. a long list with its `details` open) is captured clipped to its first 32767 device px, any other capture error skips it, and either way the screen keeps `status: ok` and its metrics, with a `note` on the record. Controls per row (LAYOUT-03) skip the rows of a WAI-ARIA grid (`[role=grid]`/`[role=treegrid]`): a month's week of day cells is not an action row. They also leave out the controls of an open disclosure inside the row (#1029): a popup or fixed box, an open `<details>`' body (its `summary` still counts), or the region an `aria-expanded=true` trigger names in `aria-controls`. The trigger stays the row's accessory, and a region whose trigger doesn't declare `aria-expanded=true` stays the row's own, so an unmarked inline drawer still counts. Effective rectangles reuse project-scaffolding's canonical `tests/e2e/_geometry.py` JS (the `::before`/`::after` negative-inset expansion), imported from the scaffold checkout at run time rather than copied; no scaffold → `GEOMETRY_MISSING`, never a re-implementation. Overlap counts within one layer only (#1019): a pair whose meeting point a fixed or sticky layer takes, with the other control's own box under that layer (the nav pill over scrolled content, a full-screen overlay over cards), is recorded as `covered`, not as a TOUCH-02 overlap, since the cover takes the tap. A pair is covered too when one control's layer paints over every sampled point of the intersection (#1094): a switch whose `::before` expansion reaches into a nav tab never gets a tap there, so its verdict no longer flips with the scroll offset. A control painted over a layer's control still counts, since it wins taps inside it. An absolutely positioned popup (`[role=menu]`, `[role=listbox]`, `[role=dialog]`, `dialog`) is such a layer too (#1029): a row's open menu drawn over the row's own main control takes the tap, while two touching items inside the one menu still overlap. The `clearance` section scrolls each list's scroller to its end (instantly, restored afterwards, after the screenshots) and records a list whose last row still sits under a fixed bottom bar (LAYOUT-07); a transient overlay (`[role=menu]`/`listbox`/`dialog`/`alertdialog`, an open `[popover]`, `.row-menu`, `.toast`) is never that bar (#1464). Each icon box also names its element (#1020): the glyph (a sprite `<use href="#i-NAME">`, else `data-icon` or a class), the control or identified ancestor hosting it and that control's accessible name, capped per size, so a COMP-02 finding points at the icons to resize. `evaluate <metrics.json>` is pure stdlib and prints the rule results and grades as JSON.

**The app's own e2e suite as a second walk** (`measure <repo> --e2e`, #1498; #1383 Step 3/6). The walk never opens an overlay nothing declares (#1353), but each app's e2e suite already opens most of them on its own disposable server. After the walk (live or `--synthetic`), `capture.py` prepares `<run_dir>/e2e/` — `script.js` (the walk's own page script, emitted by `walk.py --emit-script` under the target interpreter so the scaffold geometry loads), `params.json` (the walk's params, component map included) and, with a declared `theme_storage_key`, `capture.json` — then runs the suite in the foreground from the target root under the target's venv with `DESIGN_SURFACE_CAPTURE` set, `NO_WINDOW` and a timeout (`[design.review.e2e]` `command`, default `-m pytest tests/e2e`, and `timeout_s`, default 900; past it the process tree is killed). project-scaffolding's vendored `tests/e2e/_surface.py` hook writes one JSON + PNG per `surface(page, name)` call and theme; each becomes a screen `<device>-<theme>-e2e-<surface>` (`kind: step`, `source: e2e`, the device from the test's own context: no phone UA → `desktop`, a phone on WebKit → `iphone`, otherwise `android`), graded by the full rubric, and the overlay-coverage line is the union over walk and e2e screens. The outcome is its own `e2e` record — `E2E_SKIPPED` (the walk measured nothing), `E2E_BAD_CONFIG`, `E2E_HOOK_MISSING`, `E2E_SCRIPT_FAILED`, `E2E_TIMEOUT`, `E2E_FAILED` (non-zero exit before any capture, with the output tail) and `E2E_NO_SURFACES` — that never touches the walk's result; a suite that fails after capturing keeps its screens with a `note`. Two more states ride beside that outcome and are never folded into it (#1507): `warning` `E2E_THEME_MISMATCH` (the screens in `theme_mismatch` rendered another theme than the hook asked for — an app that stamps `data-theme` at load needs `[design.review] theme_storage_key`, or every dark capture is light; `measure` prints it as `E2E=E2E_THEME_MISMATCH`, not `ok`) and `tree` (`E2E_TREE=clean|restored|restore_failed|unchecked`: after the suite, `capture.restore_tree` puts the target's working tree back as it found it — a rewritten tracked file restored from HEAD, a new untracked one removed — and never touches a path the user had already edited; one it cannot restore is `restore_failed` and `measure` exits 1, and a target that is no git checkout is `unchecked`, not clean). `--e2e` without `--url` implies `--synthetic`: the walk runs on the target's own disposable instance and never probes the live port, so a target with no `[design.review.synthetic]` block is `SYNTHETIC_UNDECLARED` (and `E2E_SKIPPED`) until it declares one or is given a `--url`. The ledger diffs an `--e2e` run only against earlier `--e2e` runs. Without `--e2e` the output is unchanged: no suite runs and no `e2e` key or line is written. **To be measured, an app** vendors `_surface.py` into `tests/e2e/` (tracked as `surface_capture`), imports its `pytest_collection_modifyitems` into the e2e conftest, calls `surface(page, "<area>.<surface>")` directly in each test body once its surface is open, declares `[design.review.e2e]` only if its suite is not `-m pytest tests/e2e`, and runs `measure <repo> --e2e`.

**Unknown is a state.** A target that is not listening (`NOT_LISTENING` — the port refused) is told apart from one that does not answer (`TIMEOUT`; on this Windows host a refused loopback connect only surfaces after ~2s of SYN retries, so the probe deadline stays above that), from a venv without Playwright (`PLAYWRIGHT_MISSING`), from a tab that failed to open (`TAB_FAILED`), a dialog that would not show (`DIALOG_FAILED`), an engine that would not launch (`BROWSER_FAILED`) and a script section that threw (`section targets: GEOMETRY_MISSING`). Each makes exactly the rules that read it `unmeasured` with that reason. One state is deliberately not in that list: an extra step whose target never attaches within 5 s (`STEP_TARGET_ABSENT`, status `absent` — a row menu on an empty list) is a surface that does not exist in this app state, so it is left out of every rule and named in `absent_screens`, the rule's reason and the report's caveats, instead of turning a dozen unrelated rules `unmeasured`; a rule left with no other screen is still `unmeasured`, never a vacuous pass (#995) — the status lattice is `fail > unmeasured > pass`, so a rule is `pass` only when every applicable screen was measured and none failed; a category holding one is flagged `unmeasured: true`, as is the overall verdict, and it is never scored as failing. A screen a rule has nothing to say about (no primary action to size, no text to histogram) is N/A and counted separately, so a vacuous pass says so.

**Stable shapes** (documented in the package docstring): `metrics.json` = `schema_version`, `rubric_version`, `target`, `commit` (target HEAD via `git_run`), `generated_at` (UTC ISO), `base_url`, `run_dir`, `devices`, `params` (`script` floors + `resolved` spec values), `interpreter`, `unmeasured` (`null` or `{reason, detail}`), `walk`, `screens[]` — each screen `{id, device, theme, view, kind, status, reason, error, screenshot, screenshot_full, metrics}` with ids like `iphone-light-board` / `desktop-dark-dialog-settings`; the evaluate document = the same envelope plus `params` (the resolved floors), `rules[]` (`{id, category, severity, owner, status: pass|fail|unmeasured, reason, evidence: [{screen, value, items, facts}], measured: {screen: value}, threshold: {value, source}, params, title, standard, fix_template, mockup}`), `categories{cat: {score, grade, unmeasured, failed, unmeasured_rules}}` and `overall{score, grade, unmeasured}` — `params` and `evidence[].facts` (`{count, total}` behind a share) were added in #972 so every `fix_template` placeholder is fillable from the document alone. Same app at the same commit gives identical rule results; the acceptance for the whole pipeline was reproducing the 2026-09-21 numbers against the live app-launcher (93/122 small controls on the iPhone Apps tab, 4.13:1 light / 3.79:1 dark for accent on `accent-soft`, the 11 / 12.48 / 14.72 / 16 / 24px size histogram, no horizontal overflow). Screenshots stay in the run directory and are never attached to an issue, PR or comment. Rubric, scoring, the lattice, the probe and the browser leg (against `tests/fixtures/design_review/fixture.html` through a sibling venv's Playwright, reported as a skip when none has it) are unit-tested (`tests/design_review/`, reached from the one acceptance gate); the browser leg is its own suite, `tests/test_design_review_browser.py` (~78 real walks, ~34 min), which the gate runs only when the diff touches the design-review surface (`tests/acceptance/gate_routing.py`; reported as a skip otherwise, `GATE_FULL=1` forces it, #1481).

**The report** (`report.py`, #972) turns that document into one self-contained page — inline CSS on `:root` tokens with `prefers-color-scheme` and `[data-theme]` overrides, no script, no external request, readable at 400px — in a fixed section order: verdict and grade, scorecard, since the previous run (#974's `diff`), method and caveats, what is already strong, findings by category, judgment (#973), now-vs-proposed mock-ups, where the fixes land. Nothing on it is authored: every finding sentence is the rule's `fix_template` filled from the **worst failing screen's** evidence (`{count}`, `{total}`, `{screen}`, `{value}`, `{sample}`, `{share}`, `{hit_min}`, `{threshold}`, `{component}`, `{ratio}`, `{fg}`, `{bg}`, `{inner_w}`, `{viewports}`), followed by the `standard` it cites; findings sort by severity then rule id within a category; grades and scores are printed from the JSON, never recomputed; `unmeasured` rules and categories are shown as such. A placeholder with no value is left as its literal `{token}` with a "not in the JSON" note — never a crash, never an invented number (`{{ }}` are literal braces, for TYPE-02's CSS snippet). The **mock-up library** (`mockups.py`) is keyed to the rubric's `mockup` field — `type-scale` (TYPE-01), `hit-target` (TOUCH-01), `nav-five` (NAV-01), `row-density` (LAYOUT-02), `action-row` (LAYOUT-03), `destructive-in-menu` (LAYOUT-04), `form-primary` (TOUCH-03, COLOR-03), `contrast-swatches` (COLOR-01), `wide-desktop` (LAYOUT-06); rubric v1.1.0 — each a parametrized HTML/CSS partial with a Now variant drawn from the measurements and a Proposed variant drawn from the threshold, placeholder names only ("Item name", "Tab 3", "Action"), never a capture; `contrast-swatches`' proposed swatches are *computed* (the same foreground on the background moved along the black/white axis until it measures AA, and the note says the spec owner picks the real token). `rubric.validate_rubric` refuses a `mockup` id the library lacks and the tests assert the other direction (every template referenced by a rule); a template whose needed value the run did not measure renders no mock-up and a one-line note naming the value. The two slots the later steps fill are read from the same document: `judgment{status, answers[{id, question, answer, evidence}], uncatalogued[{title, severity, detail, owner}]}` and `diff{previous_run, fixed[], regressed[], new[], unchanged[], unmeasured[], rubric_changed}` — omitted cleanly when absent. `cli.py` adds `probe <repo>` (the skill's pre-flight: `PROBE=listening|NOT_LISTENING|TIMEOUT|BAD_URL` plus `CLAUDE_MD=` for the restart pointer; it never starts anything), `evaluate --out` (writes the document, prints summary lines), and `render <evaluate.json|metrics.json> [--out]` (writes `report.html` into the run directory; a raw `metrics.json` is evaluated first and its `evaluate.json` written beside the page). Filling, ordering, both library directions, every template from the violating fixture, the no-mock-up note, the slots, no-screenshot/no-request, render determinism and the three CLI legs are unit-tested (`tests/test_design_report.py`, reached from the one acceptance gate).

**COLOR-03 counts an inset-shadow boundary** (#1185, rubric 1.7.9; facilitation-suite#164, fixed there in #182). The measure read a field's boundary from `border` alone, then fell back to its own fill, so the 44px-field recipe (home-automation documents it for hit targets: the visible control sits inside a transparent border band and its 1px boundary is `box-shadow: inset 0 0 0 1px <colour>`) measured as `boundary none, ratio 1` and the rubric and the recipe disagreed about what a boundary is. Now an inset shadow with no offset, no blur and at least 1px of spread is a drawn edge when the border is not; the strongest such shadow is the boundary and must still reach 3:1 against its surface like a border. Each `boundary_low` entry carries `via` (`border`, `inset-shadow`, `fill` or `none`) so a finding says what was read. An offset or blurred shadow (a drop shadow, a one-sided line) is not a boundary, and the check keeps the same exemptions.

**A leg whose app ignores the stamped theme is not measured as the requested one** (#1216, rubric 1.12.0; facilitation-suite's "light" screens rendered dark). The walk stamps `data-theme` and sets the colour scheme, but an app that follows a server-driven appearance re-applies its own choice, so both halves of a run measured one theme and COLOR-04 failed a dark switch track against the light spec's accent. Each screen now records `theme_applied` and `theme_observed` (the attribute plus the luminance of the composited canvas); a screen that rendered the other theme is `unmeasured` for the rules the rubric marks `theme_dependent` (COLOR-02 to COLOR-05) with a reason naming both themes, while touch, layout, navigation and type still score it. The walk records and never re-stamps in a loop: the app owns its theme, and the fix is the app's to make or to declare (`[design.review] theme_storage_key`). The report's method section lists the screens. An unreadable page is unknown (`null`), never flagged.

**Icon buttons draw nothing at rest; reference pills are one shape** (#1259, rubric 1.14.0; task-os#357). COMP-05 counts every visible icon-only button (a `button` or `[role=button]` holding an `svg`/`img` and no shown text; screen-reader-only text does not count as shown) and fails one that shows a fill, a border or a shadow against its surface. A state draws itself, so a pressed, current, expanded, selected or checked control is left out. The vendored header toggles and modal close read `--close-bg`, so an app that still sets it to a fill fails on every tab until it adopts the transparent default. COMP-06 groups the links drawn as chips (a `chip`/`pill` class, or a drawn link as round as a pill) by height, radius, padding and font size, and fails a screen with more than one shape. Colour is left out on purpose: a status pill keeps its status colour on the same shape. Most icon buttons live in detail drawers the walk does not open, so an app that wants them measured declares the drawer in `extra_steps`. The static twin is `/design-sync`'s `icon-button-unpainted` contract, which reads `--close-bg` directly.

**A label fits its control; a control fits its container** (#1325, rubric 1.18.0; home-automation#859). The `iphone` leg is the 390px class (Playwright's `iPhone 13` descriptor, WebKit) instead of the 430px `iPhone 15 Pro Max`: a row of buttons first wraps in that 40px, and every screen id keeps its `iphone-` name. COMP-07 reads every visible `button`, `[role=button]` and non-inline `a[href]` outside a segmented group (COMP-03's) and fails one whose label runs over two lines, or whose text or glyph extends past its border box sideways by more than 1.5px. A text run over 40 characters is prose and may wrap, and text under `text-overflow: ellipsis` on a clipped box is a chosen truncation. LAYOUT-08 fails a visible control that reaches past the side of its nearest container: the first ancestor that clips (`overflow-x: hidden`/`clip`), is a dialog, or draws a fill or side border. It does not need the page to scroll, which is why LAYOUT-01 stayed green. A scroller that is none of those scrolls its controls on purpose and is left out, as is a control in a fixed layer inside the container. Both rules are pinned by `label_fit_broken.html` (the home-automation#859 row: it fails both) and `label_fit_fixed.html` (the same dialog laid out properly, plus a prose button, an ellipsis label and a self-scrolling chip strip: it passes both), walked at the iphone leg. Not built, since design.md does not yet say a cluster needs a plate: the advisory flag for three or more adjacent shape-less icon buttons.

**A chart is not an icon** (#1211, rubric 1.11.1; local-llm-hub's hub sparklines). The icon scan reads every `<svg>` box and COMP-02 holds it to the `icons.size` steps, so four 162x64 sparklines read as icons off the steps. An SVG with `preserveAspectRatio="none"` is stretched to fill its box, which an icon never is, so the scan leaves it out. A chart drawn without that attribute (a donut at its natural aspect ratio) is still scanned: declare it in `[design.review].exclude_selectors`.

**Embedded content is declared, then left out of every measure** (#1185, rubric 1.7.8; facilitation-suite#164). An app can draw content that follows another theme than the app's (facilitation-suite's Plan tab scales a slide preview from the session theme, whose uppercase title was scored as TYPE-05 and whose scaled glyph as COMP-02 — two permanent false positives). A review cannot tell a preview from app chrome, so the target says so in its `.fleet.toml`: `[design.review] exclude_selectors = [".preview-frame"]`. The measure script's one visibility test refuses any element inside an excluded selector, so text, controls, targets, icons, rows and the a11y probe all skip it with no per-rule special case. The declaration is recorded in `metrics.json` (`params.script.excludeSelectors`, and a per-screen `excluded: {selectors, elements}`), so a run says what it left out. No heuristic guesses at embedded content; an `iframe` is a separate document the DOM walk never enters anyway.

**A11Y-02 reads the vendored text-size control by its own markers** (#1185, rubric 1.7.7; parking-manager#58, facilitation-suite#164). The control lives in Settings, which exists in the DOM only while open, so the old per-screen probe failed every other screen by construction, and it looked for `data-text-size` while the vendored markup uses `data-textsize`. The `a11y` section now matches `#textSizeControl`, a `[data-textsize]` button (never `<html>`, which carries the boot script's stamp), or any element named "text size" / "font size" by `aria-label` **or `aria-labelledby`**. The control is then one fact about the app: seen on any walked screen it satisfies every screen. If it was seen nowhere but `html[data-textsize]` is stamped (the app has the vendored boot script and its Settings pane was never opened), the rule is `unmeasured` with a reason naming why (its Settings pane was never opened), never a pass and never a false fail. **Rubric 1.13.0 (#1217, Roberto's decision of 2026-10-04):** the walk now opens that pane itself, on every app with no declaration: after the tabs and dialogs it clicks the header gear (the vendored `home-head` button named "Settings", found by role and accessible name, never a per-app selector), screenshots and measures the pane as the `gear-settings` step screen, and refuses the click when the gear sits inside a `no_go` selector. This is the one click the walk makes beyond the primary tabs without a declaration; it only switches a view and writes nothing. An app with no such button records `SETTINGS_GEAR_ABSENT` (an `absent` screen, named in the report's method section) and A11Y-02 stays `unmeasured` with the reason naming it; a gear that opened a pane without the control fails A11Y-02 even when the boot stamp is present. `extra_steps` still serves an app whose Settings is not behind a gear. **Rubric 1.11.0 (#1211, Roberto's decision of 2026-10-03):** the rule is now "No text-size control" (metric `a11y.no_text_size_control`) and fails an app without the control whether or not its viewport locks zoom; before, an app that allowed pinch-zoom passed with no control at all, so home-automation, task-os and local-llm-hub read clean. `zoom_locked` stays in the evidence line. A fix is the vendored `text-size` control in Settings; an app whose Settings pane the walk never opens and that has no boot stamp still fails, so declare the Settings step in `extra_steps`.

**Every screen carries a control and text inventory** (#1497, Step 1/6 of #1383). The page script's read-only `inventory` section lists each visible control: its `kind` (button, icon-button, link, select, combobox, range-tab, segmented, switch, checkbox, input, textarea, menuitem, tab), its `component` (`vendored:<name>` or `bespoke`), its accessible role, a masked and truncated label (digit runs become `#`), and the font family, size and weight it renders in. Identical renderings fold into one entry with a count. A select or combobox also carries `options` (its option count: a `<select>`'s, a datalist's, or the `aria-controls` listbox's when that is in the DOM, else absent), and a segmented or range-tab control carries `group` (its parent's key, numbered `~N` in document order when several share one, #1505). Each text role (heading-1..4, row-title, secondary, caption, button-label, overline, body, code) is listed with the font variants it renders in. A role is assigned by structure (tag, ARIA role, part class), never by size, because size is the thing being compared. `capture.vendored_components()` reads project-scaffolding's `.fleet.toml` `[components]` table and each web component's own stylesheets once per run. It turns them into root classes (classes that lead a selector) and part classes (classes only ever nested). The map rides into the script's params like `exclude_selectors`. A class several components lead with goes to the component whose name prefixes it, else to none. A control's own classes are read in order, then its wrapping `<label>`'s, and a part class counts only inside its root. With no scaffold or no catalog, `inventory.unmeasured` says why and every control reads `unknown`, never `bespoke`. Entries are sorted and carry nothing positional or timed, so two runs over one page are byte-identical. The section is no rule's input yet; #1383's cross-app comparator reads it.

**The judgment stage** (`judgment.py`, #973) bounds the one thing the metrics cannot decide — lists built like spreadsheets, destructive actions as the loudest controls, every tab with a different anatomy — as a **file contract, not prose**. The checklist is rubric data: `[[judgment]]` entries with a stable `J-NN` id, the `question` (each states what makes it a `no`, because three independent judges must reach the same vector), `maps_to` (the rule ids a `no` may be attributed to; empty means a `no` must be raised as uncatalogued) and `screens` (`all | tabs | dialogs`); `validate_rubric` refuses a duplicate id, an unknown `maps_to` rule or an unknown scope, and rubric v1.2.0 seeds the ten questions from #973 (row primary action, most prominent control, destructive prominence, one reading order, icon-only learnability, shared tab anatomy, user-language labels, casing, empty states, key fact at a glance). `judge_prompt(doc, run_dir, rubric)` writes one deterministic prompt (`judge-prompt.md`, same run + rubric → same bytes, no timestamp) carrying only the checklist, the screen table with the **local** `shots/<id>.png` / `-full.png` paths, the `metrics.json` path, a minimum-coverage instruction (every `iphone-light` screenshot incl. the full-page tabs, every `desktop-light` tab full page — the metrics support a reading, they never override what is visible) and the required output schema; it never names `evaluate.json`, `report.html`, another run or an expected answer, or agreement would mean nothing. `validate_answers(payload, rubric, doc)` validates per answer (#1185 reversed the original all-or-nothing contract on Roberto's decision of 2026-10-03; the rules, per answer: every seed id exactly once, `yes | no | na`, `evidence` a real screen id inside the question's scope (null only on `na`), `maps_to` a subset of the question's own list, every `no` either mapped or backed by an `uncatalogued` entry (`question`, `title`, `severity` P0–P3, `detail`, `owner`, `proposed{metric, threshold}`) naming that question, uncatalogued only on a `no`) — a violation drops only the answer or uncatalogued entry it sits on (an answer left without its backing `no` entry goes too) and lists it in `dropped: [{id, reason}]` with `status: "partial"`; a free-form top-level key, a reply that is not one JSON object, or a reply with no surviving answer yields `{status: "unmeasured", reason, errors: [...]}` with no answer kept. `merge_judges` treats a question one judge dropped as `not confirmed` and carries every judge's drops; the `partial` status files and ledgers its kept uncatalogued findings like `ok`. `merge_judges` (for `--judges 2`) keeps the answers every judge agrees on, lists disagreements as `not confirmed` (status `not_confirmed`) and keeps an uncatalogued finding only when every judge raised it (the same title after case/punctuation folding, or the same question — an agreed unmapped `no` never loses its finding to wording). `judge-merge <run_dir> <answers.json>...` writes the `judgment` document into `evaluate.json` and touches no other key — grades are printed from `categories` / `overall` and the tests assert byte-equality with and without a judgment — so an uncatalogued finding can never move a grade; the report renders the answers with their evidence and mapped rule ids, and the uncatalogued list with each proposed rule, outside the grade. The Python side spawns nothing: the skill spawns one fresh agent per judge through the capability contract, collects its reply within the turn, saves it verbatim as `judge-<n>.json`, and never re-prompts, edits or answers itself. **The ratchet:** an uncatalogued finding the user accepts becomes a `[[rules]]` entry when it can be measured (`measure.py` grows the metric and the question leaves the checklist) or a `[[judgment]]` question otherwise — by PR, with a `[meta].version` bump, no automation. Acceptance for this step was three independent fresh judges on the same app-launcher run directory (72 screens) agreeing on the yes/no/na vector for all ten seed questions. The durable lesson: a question agrees across judges only when it says which screenshots count and where the boundary of the thing being judged is. Checklist validation, prompt determinism and bounds, the schema refusals on a malformed fixture, the merge, the grade invariance and the three CLI legs are unit-tested (`tests/test_design_judgment.py`, reached from the one acceptance gate).

**The ledger and the diff** (`ledger.py`, #974) close the loop the manual audit closed by hand. Every run leaves a few-KB entry in a **local state file** — `~/.claude/hooks/state/design-review/<target>/ledger.json`, the last 20 kept — not an `audit-meta` issue comment: filing is opt-in, the report must open with a diff even when nothing was ever filed, the file never carries captured text, and a state file ports to fleet-config-lite. The entry is `{run_id, generated_at, commit, live_build, rubric_version, judgment_rubric_version, overall{score, grade}, categories{name: grade}, rules{id: status}, uncatalogued[{question, title_norm, severity, owner}]}` — `commit` is what the target checkout says and `live_build` what the running process reports on its `api_version_path` (one best-effort GET through `service_probe.running_sha`, `null` when unreadable), two facts that differ exactly when the tray is serving an older build and are never folded into one. `ledger <run_dir>` records the entry and writes `diff` into `evaluate.json` (it runs after `judge-merge`, so the entry carries the judgment's rubric stamp, and before `render`, so the page opens with it): by rule id, `fixed` = fail→pass, `regressed` = pass→fail, `new` = fails now and the id was absent before, `unchanged` = same status (a rule first seen passing lands here — nothing to act on), and a rule `unmeasured` on either side goes to `unmeasured[]` and is never fixed or regressed, so an unmeasured category is never a regression; `previous_run` is `null` on a target's first recorded run and `rubric_changed{from, to}` names a version change between the two runs, which the report and the summary carry as "a moved rule may be the rubric, not the app". The report's diff slot grew additively: an `unmeasured` bucket and the rubric note in the lead.

**Filing** (`filing.py`, #974) is opt-in per run (`file`) and machine-composed: one managed `design-review` issue per repo through `audit_issue.py` (`KINDS` gained `design-review`, stable title `design-review: rendered findings`, label `design-review`, the `design-drift` marker identity and collapse-strays mechanics; `audit_issue.py upsert --dry-run` prints the plan and the marker-stamped body without writing, and `get_managed` / `upsert_issue` are the Python entry points). A finding line is `- [ ] **<rule id>** (<severity>, app) — <title> — <n> screens, worst <screen id> · <standard>`; a re-run updates the line in place and keeps its checkbox; a listed rule that passes again keeps its line, unticked (the fleet's audit issues never machine-tick), tagged `_(fixed — passes since <date> @ <sha7>)_` with the first date kept; an unmeasured one is `_(carried — unmeasured this run)_`; uncatalogued findings (judgment status `ok` or `partial`) are their own list keyed by question + normalised title, titles and severities only; a dated bullet lands in `## Review run log`, and the run log alone is not a change (`CHANGED=no` on an unchanged app). **Spec- and scaffold-owned rules are never filed on the app**: `route()` sends them to the fleet digest, deduped by id and listing the failing apps, and from there to fleet-config's (spec) and project-scaffolding's (scaffold) own `design-review` issue in fleet mode. A `[[design.accepted]]` entry with `rule = "<rubric id>"` and a `reason` (optional `record`) in the target's `.fleet.toml` suppresses that rule for that repo — listed under `## Accepted`, never under Findings; an accepted id that fails nowhere prints `PROBLEM=`; `design_lint/accepted.py` skips `rule`-keyed entries and `filing` skips `check`-keyed ones, so the one table serves both skills (schema: `architecture/README.md`). The merged body is always written as `<run_dir>/issue-body.md`; only `--file` upserts it. No issue body, ledger entry or digest ever carries a screenshot path, captured page text, an evidence item or a judge's `note` / `detail` — rule ids, titles, severities, owners, counts, screen ids and the `standard` citation only, asserted by the tests.

**Fleet mode** (`fleet.py`, #974; `/design-review fleet`) walks every `hooks/projects.toml` table with a `webapp_port` in file order, **one app at a time** — probe, measure, evaluate, ledger + diff, render — so there is never more than one browser open; an app whose port is `NOT_LISTENING` or `TIMEOUT` yields an `unmeasured` run and an `unmeasured` ledger entry and is never started, restarted or killed. The judgment stage is skipped (a per-app, on-demand step) and the digest says so. An **app-owned rule failing in two or more measured apps is promoted** to the scaffold list once (`promoted: true`, the apps listed, `app → scaffold` on its line) and left off every app issue — the fix belongs in the shared base; an app that accepted the rule is not counted. The digest lands under `~/.claude/hooks/state/design-review/_fleet/<stamp>/` as `fleet-digest.json` (`apps[]` rows with probe, grade, filed / promoted / accepted ids and the diff counts, the deduped `spec` and `scaffold` lists, `promoted`, `filing{mode, issues}`) and `fleet-digest.html` (the report's CSS, one page); every would-be body is written beside it on the default dry run, and `--file` upserts the app issues plus the two digest issues through the same merge. Entry shape and forbidden content, record / trim / previous, every diff branch, the report slot, accepted rules on both loaders, routing, the body merge, the fake-`gh` dry run, promotion and the `ledger` / `file` / `fleet` CLI legs (two dead-port fixture apps → both unmeasured, nothing started) are unit-tested (`tests/test_design_ledger.py`, reached from the one acceptance gate).

**Inventory comparison** (`inventory.py`, fleet-config#1500, Step 5/6 of #1383) runs at the end of a fleet sweep. It compares rather than measures: it reads each app's newest `inventory` section (Step 1/6, #1497; the newest run under `<target>/` that carries one, so a walk, synthetic or e2e run alike) and lists every place the fleet renders one thing more than one way. `INV-01` is a text role with more than one `{family, px, weight}`, or off design.md's `typography.*` value. `INV-02` is a normalised action (destructive, commit, dismiss, sort, …) rendered by more than one component or variant (component, kind, px and weight). `INV-03` is a bespoke control whose kind has a vendored component in project-scaffolding's catalog. `INV-04` is one kind of choice, at an equivalent option count, rendered as different controls, against design.md's rule (2–5 options a `segmented`, 6+ a `select`). Each group's reference is design.md's value where it has one, else the (vendored) rendering most apps use, else none, and then every app diverges. One divergent app makes a single-app finding, filed on that app's managed issue beside its rules. Two or more make a cross-app finding, which goes in the digest's `inventory` section, its HTML Inventory section and fleet-config's `design-review` issue, through the same `filing.py` merge. Each line names the renderings, the counts, one example screen id per divergent app and the fix path, vendored component + `/propagate-vendored`. Lines never carry a label, a control key or a screenshot path. Normalising is DOM first: kind and component from the inventory, then a short masked label against a fixed vocabulary. A label over four words is a whole-row tap and is never matched. An `unknown` component (no catalog at capture) is never compared. A select or combobox counts its options only from an `options` field (#1505; an older inventory without it is `unclassified`), and a segmented or range-tab group is one group per component and `group` key per screen, so two groups on one screen stay two. Whatever the DOM cannot decide is listed under `unclassified` in the local digest JSON for Step 6's readers. It is deterministic: the same inventories give byte-identical output in any input order. With no inventory anywhere the digest has no `inventory` key, and every body and score is byte-identical to before. Three invented fixture apps, the routing, the dry-run bodies, the leak checks and that equivalence are unit-tested (`tests/test_design_inventory.py`).

`skills/_lib/perf_review/` is the deterministic half of `/perf-review` (fleet-config#1121), split across two interpreters like `design_review`, whose `resolve_target` / `probe_listening` / `resolve_interpreter` / `target_commit` / `repo_slug` it reuses. `load.py` is a self-contained Playwright child under the target's `.venv`; `http_probe.py` (stdlib) times endpoints with nearest-rank p50/p95, the first request kept apart as cold; `report.py` owns the budget verdict (`pass` / `fail` / `unmeasured`, never folded), the managed-issue body and the local ledger at `~/.claude/hooks/state/perf-review/<repo>/ledger.json` (last 20 runs, ids and numbers only); `cli.py` is `measure` / `file`. Two measured traps the load leg is built around: Playwright turns the HTTP cache off under any `route()`, so non-GETs are observed, never intercepted (a test fails on any `route(` in `load.py`); and Chromium never caches a response served under a certificate error, so the Chromium leg maps the name the app's cert is issued for (read from the cert, never configured or written to an issue) to loopback, and marks the warm leg `unmeasured` when that cannot verify. Two measurement artefacts it also guards: Chromium launches with `--proxy-server=direct://` because Windows proxy auto-detect stalled a cold first request ~2.7 s (fleet-config#1139; `--no-proxy-server` and `--proxy-bypass-list` do not take effect), and the cold leg is taken three times in fresh contexts (`ready_samples_ms`) with `report.cold_ready` scoring the median and flagging an outlier, so one slow first load after a restart is not a regression (fleet-config#1140); "ready" is the page time of the first animation frame the `ready_selector` is visible (`wait_for_function`, `polling="raf"`), never `wait_for_selector`, whose 500 ms re-check made two apps read the same ~1455 ms (fleet-config#1236); a declared `ready_selector` that never shows fails its own `ready.selector` check instead of leaving the ready times silently `unmeasured`; and `stamping.py` reads the target's `src/static_versioning.py` and fails a per-file stamp that does not cover the import graph (`cache.stamping`, playbook P11). `tests/test_perf_review.py` is the probe self-test against a local fixture server.
