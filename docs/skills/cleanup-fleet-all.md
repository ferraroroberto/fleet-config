# `/cleanup-fleet-all`

- **`/cleanup-fleet-all [<bucket>...]`** — the genuinely **unattended** sibling of `/cleanup-fleet`: walks all nine queued audit buckets (or a restricted subset for a dry run) in one pass, with **no human review gate at all**. (`security` is never queued — it's self-healed inline by `/codebase-audit`; `cert-drift` is `/design-sync`'s review-only kind, also never queued; a hard-tier `prompt-drift` issue is deferred to an attended `/cleanup-fleet` run, and a `prompt-drift` validator also runs the preservation harness.) Every issue goes through four independent agents — **build** (implement + verification gate, then stop), **validate** (a fresh agent, no memory of the build, that independently re-runs the gate and leniently judges whether the diff actually addresses the issue), **execute** (ship: push, PR, CI, merge, tray restart), and **teardown** (the terminal step of *every* lane: comment the outcome + any WIP SHA onto the issue, remove the worktree, delete the branch, verify the repo is back on a clean default branch) — so no single agent both builds and ships its own work unchecked, and no lane can end leaving state behind. A failed validation retries the build once with the validator's feedback, capped at 2 rounds total; a second failure **escalates**, meaning *commented on the issue and torn down* — never force-merged, never a branch parked for someone to find later. The retry/ship/escalate decision is deterministic code — a fixed lookup on each agent's schema-validated verdict, not a fourth LLM call re-interpreting an already-decided result — so a long unattended run can't drift or forget state.
  - **Three rules keep an unattended run honest**. *Seriality*: one bucket at a time and one repo at a time inside it, the next lane starting only after the current one's teardown reports clean, so at most one worktree exists fleet-wide at any instant. *Teardown* judges its own lane's mess and nothing else — its own branch, its own worktree, the tree it left behind — while conditions it is not mandated to fix (a stale `index.lock`, a primary behind origin, a zombie-pinned empty shell, another lane's branch) are reported and never halt. *Halt-on-residue*: a lane that can't be returned to clean halts the run rather than stacking a second worktree on the first. `tests/cleanup_fleet_all_flow.mjs` asserts all three against the real workflow script with stubbed agents, so a re-introduced fan-out fails the gate. Every agent works a forced worktree (`worktree_claim.py acquire … --force-worktree`), never a primary checkout, and a live-e2e guard refusal is a hard stop (`E2E_LIVE=1` is forbidden).
  - **A skipped repo is deferred, never dropped**. A repo that is dirty, off its default branch, or already holds a worktree is still skipped — never stashed, never force-switched, that criterion is unchanged — but the run no longer forgets it. The per-repo check is the re-runnable, stateless `skills/_lib/repo_preflight.py` (shaped after `issue_state_gate.py`, whose counts work precisely because something re-runnable computes them); its `skipped` list is the run's deferred set, re-checked once after the last bucket so a repo committed and pushed mid-run is picked up in the same pass, with the retry necessarily re-establishing every fact rather than replaying an hours-old verdict. Whatever is still unavailable lands in one `cleanup-deferred` tracking issue whose **open state means there is unprocessed work** — an empty deferred set closes it, a non-empty one reopens-or-creates it — and the final report carries `skipped: N repos, M issues unprocessed` on every run, zero included, beside the existing `candidates:` line. A run that skipped *every* candidate repo prints `SCHEDULED-RUN-FAILED` rather than reporting a clean sweep. The same check also globs each repo's `<repo>-wt-*` siblings exactly as teardown check 2 does. An unregistered leftover that is not provably inert (non-empty, a junction, or `dir_holders.py` `LIVE`/`UNKNOWN`) skips the repo up front as `leftover-dir`, naming the path and holder pids, instead of halting the run at that repo's first teardown hours later. A zombie-pinned empty shell still dispatches.
  - **A foreign worktree defers its repo, it does not halt the run**. Pre-flight skips a repo that already holds a worktree, but one can appear mid-run when another lane starts work there. Teardown classifies every extra registered worktree with the stateless `skills/_lib/worktree_residue.py`, against the run's own worktree paths and branches, which the decision script supplies. A foreign worktree that is clean and has its HEAD proven merged (an ancestor of `origin/<default>`, or a squash whose `merge-tree` result equals the default tree) is reported in `foreignWorktrees`. The rest of that repo's issues then go to the workflow's `deferred` list, the same retry pass and ledger as a pre-flight skip. The run's own leftover, and any dirty, unmerged or unclassifiable foreign worktree, still halts as before. The helper never removes a worktree.
  - **Leftover branches are reported with proof; teardown never deletes them**. A foreign branch is not residue and does not halt a run, and teardown's check 3 judges it without hand-run `gh pr list` / `git diff` lookups: it runs the read-only `skills/_lib/branch_residue.py branches <repo>`, which classifies every local and remote ref: `landed` needs a closed issue, a tip proven merged (an ancestor of `origin/<default>`, or a squash whose `merge-tree` result equals the default tree, the same proof as `worktree_residue.py`) and no open PR; `unknown` is its own class and a branch with no issue number is never `landed`. The same report lists sibling `<repo>-wt-*` folders that `git worktree list` does not register (`ORPHAN=` lines, informational; check 2's five conditions stay the halting authority). `/issue-finish` prints the same report as one summary line after landing the primary. Deleting other lanes' branches is a separate, explicit act that teardown does not take and no scheduled skill passes: `branch_residue.py branches <repo> --delete [--branch NAME]... [--remote]`, run by the owner or by the chief after a Board yes (delete with: `branch_residue.py branches <repo> --delete --branch <name>`). It acts only on refs that are `landed` right now, re-derived from a fresh tip and proof immediately before each delete, never the default branch or a checked-out one, skipping any head with an open PR. A remote delete needs the separate `--remote` flag, proves the `ls-remote` tip on its own and is lease-pinned to that sha (`--force-with-lease=refs/heads/<n>:<sha>`), so a later push turns it into `STAYS`. Every deletion prints its sha, proof and a `RESTORE=` command. `worktree_residue.py` stays strictly read-only, and `/issue-finish` and `/cleanup-fleet-all` still only call the report.
  - **Shape and runtime.** The build/validate/execute split is the fleet's reusable **independent-review gate** convention, documented in [`docs/independent-review-gate.md`](../independent-review-gate.md) so other build-then-ship skills can adopt it deliberately — `/issue-yolo` is the first adopter. Built on the **`Workflow` tool** (`.claude/workflows/cleanup-fleet-all.js`, its first use in this repo): the script owns zero Bash/filesystem access — every repo-mutating action happens inside a spawned agent — and the invoking `SKILL.md` never sees any agent's intermediate work, only the final structured result. Designed to run via `claude -p "/cleanup-fleet-all"` headless, so it never backgrounds a tool call and waits for a notification (a headless `claude -p` session has no wake-up, so the run would exit reporting success without the skill having finished); it polls `TaskOutput` to completion within the same turn instead. First run should be attended (see the skill's Notes) before wiring the scheduled job.
