# Deploy-coverage gate (merged is not shipped)

`skills/_lib/deploy_coverage.py` enforces the fleet convention that a change is not done merely because it merged — a merged change can report as shipped while a runtime component kept serving old code. A repo declares each not-fully-covered runtime component (out-of-tree, or an in-tree process deliberately excluded from the standard restart) in its own `CLAUDE.md` — a `## <component name>` heading whose bullets include `what/why`, `update command`, `liveness signal`, and `NOT restarted/deployed by`; app-launcher's `:8446` session-host (`GET /api/version`'s `session_host.stale`) is the reference case. A repo with no such block — nearly every repo today, including `fleet-config` itself — gets `DECLARED=no` and pays nothing: no git call, no extra step. `check <repo>` additionally diffs `<main>...HEAD` against the path-looking backtick tokens in each declared component's prose (the scaffold's template has no structured `paths:` field, unlike the sibling UX-surface block above, so a future reword can silently change what's detected) and reports `TOUCHED=yes|no|unknown` per component; `unknown` (no parseable path token, **or** a diff that could not be taken at all) is treated as touched, never as a silent "no". `/issue-finish` (step 6b) runs this after the restart step and, for any touched-or-unknown component, reads that component's liveness field from the same build-identity poll rather than issuing a second request — never blocking, never invoking the declared update command itself (a confirmation-gated manual action stays a human/operator call), only qualifying the finish summary across three honest outcomes: confirmed live, **merged but not yet live**, or unknown. Parser + matcher are pure-logic unit-tested (`tests/e2e/test_deploy_coverage.py`, reached from the one acceptance gate).
