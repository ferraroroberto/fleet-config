# Skill tiers and scheduled runs

Skills live in **three tiers**, versioned in this repo — two fleet-wide, one directory-scoped:

- **Global** (`skills/`, junctioned → `~/.claude/skills` + `~/.agents/skills`) — load in every session in every repo: the issue-workflow set (`/issue-add`, `/issue-start`, `/issue-finish`, `/issue-yolo`, `/issue-triage`, `/issue-batch`, `/issue-finish-batch`), `/e2e`, `/quick`, `/handoff-commit`, `/screen`, `/codebase-audit`, `/design-sync`, `/design-review`, `/perf-review`, `/e2e-audit`, `/docs-shots`, `/propagate-vendored`, and the shared `_lib/` helpers. `/e2e`, `/design-sync`, `/design-review`, `/perf-review`, `/e2e-audit`, `/docs-shots`, and `/propagate-vendored` are global (not fleet-only) because they operate on *sister* repos and must load there.
- **Fleet-only** (`.claude/skills/`, project-scoped) — the whole-fleet orchestrators that never make sense from a single sister repo: `/audit-fleet`, `/design-sweep`, `/perf-sweep`, `/cleanup-fleet`, `/cleanup-fleet-all`, `/chief`, `/context-audit`, `/context-purge`, `/insights-weekly`, `/learning-log`, `/system-map`, `/config-map`, `/fleet-health`, `/sota-watch`, `/prompt-audit`, `/fleet-10x`. Their maintained sources stay here; the installer creates individual `.agents/skills/<name>` discovery links for Codex and Pi. Claude and Grok use native `.claude` discovery. Keeping these sources at project scope excludes them from unrelated repositories. `/codebase-audit` stays global because `/audit-fleet` invokes it inside sister repos.
- **Directory-scoped** (a subsystem's own `.claude/skills/`, loading only when cwd is under that subdirectory — the same project-scoped mechanism as the fleet-only tier above, one level narrower) — currently just `stream-deck/.claude/skills/streamdeck-deploy/`, which drives the Elgato Stream Deck plugin's build/link/package/profile-diff workflow; see `stream-deck/README.md`'s "Deploying a change" section for the detail.

The directory tier receives its `.agents/skills/<name>` link inside that same directory. Start Codex/Pi there to establish scope. Real `.agents` sources in adopters get an inverse `.claude` link; neither source nor private content is copied. `skills/_lib/scoped_discovery.py` owns diagnosis, per-checkout link manifests and safe removal. See [installation and worktree lifecycle](../install.md#scoped-project-discovery) and the canonical [portable-project contract](https://github.com/ferraroroberto/project-scaffolding/blob/main/docs/agents/project-skills.md).

Every checked-in scheduled `run-weekly.bat` still calls `skills/_lib/claude_progress.py`. That compatible facade and the explicit `scheduled_runner.py --harness codex` entrypoint share one lifecycle and normalized progress boundary; provider commands and events live in `runner_adapters.py`. Existing elapsed milestones, delivery assertions, no-tool detection, stall handling, background-kill detection and pre-tool-only Claude transient retry remain covered. Missing terminal results, malformed or unknown streams, and unfinished tools/children now remain unconfirmed even on exit zero. No production schedule changes provider. The supported arguments, exit codes, native smoke evidence and Pi/Grok extension contract are in [Scheduled runners](../scheduled-runners.md).

**Stall watchdog.** The adapter also kills a scheduled run whose stream has gone completely silent and exits `124`, so a wedged unattended run surfaces as a *failed* job within the hour instead of holding its slot until a human notices. The default limit is 45 minutes of silence — far above any legitimate quiet stretch, since every wrapped Bash/PowerShell call is itself bounded by the context filter's `FLEET_CONTEXT_FILTER_TIMEOUT` (600s default). Tune it per launcher with `--stall-timeout <seconds>` (consumed by the adapter, never forwarded to `claude`), fleet-wide with `CLAUDE_PROGRESS_STALL_TIMEOUT`, or disable it with `0`. The kill is a process-tree kill: Claude's own sub-processes hold the stdout pipe, so killing only the direct child would leave the adapter wedged alongside the run it just ended. The watchdog kills *before* it announces the kill, and the announcement is best-effort — announcing first parks the watchdog thread in a `print()` on a backpressured stdout, so the kill never runs.

**False-success guards.** A scheduled run that reports `exit 0` having delivered nothing is worse than one that crashes, so the adapter turns each known shape into its own exit code. Claude Code's `--print` mode kills any sub-agent still in flight once its background-task ceiling elapses and exits `0` regardless — the adapter watches stderr for that kill signature and exits `125` instead, and now also *prevents* the kill by handing the child `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`, the CLI's own documented "wait indefinitely" setting. The ceiling is set after the inherited environment (a stale ambient value can't silently reinstate it) and before any explicit `env=` override, and the 45-minute stall watchdog remains the real upper bound on a wedged run. The third shape — a run that ends perfectly normally having done no work at all — is invisible to both, because only the skill knows what "no work" means for it: a scheduled skill asserts its own delivery at the end of its run and prints the literal marker `SCHEDULED-RUN-FAILED` when that assertion fails, which the adapter maps to exit `123` (`/audit-fleet`'s step-6 delivery assertion is the reference implementation: ≥1 repo evaluated, a digest composed and printed, and the digest comment either posted or skipped with a stated reason). The fourth shape needs no cooperation from the skill at all: a run that invoked **zero tools** cannot have done its job whatever prose it printed, so the adapter exits `120`. Both an assistant `tool_use` block and a `task_started` system event count, so an orchestrator that only dispatches sub-agents still reads as working.

**Skills are asked for by name, not slash-invoked.** Claude Code 2.1.237 changed how a bare `/<skill>` prompt is framed in headless `-p` mode: the skill body arrives as a passive `isMeta`/`turnCompanion` message while the user turn carries only the command name, so a skill whose text opens with descriptive prose reads as reference material and the model answers "Ready — what would you like to do?" and stops. `/cleanup-fleet-all` did exactly that on 2026-08-20 — 5.3 seconds, `exit 0`, green card, nothing run. `build_command()` therefore rewrites a leading `/<skill>` into an explicit instruction naming the skill and forwarding its arguments, and every `run-weekly.bat` keeps its familiar `"/<skill> %~1"` shape unchanged. Appending the instruction after the slash command is not an option — trailing text lands in `<command-args>`, where the skill parses it as its own arguments.
