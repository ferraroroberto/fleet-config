# `/propagate-vendored`

- **`/propagate-vendored`** — turns a `project-scaffolding` component fix into a one-command, Dependabot-style distribution wave instead of N hand-filed issues + N hand-built PRs (~40 mechanical byte-copy PRs across 6–7 repos for two components). Fans out a byte-for-byte re-vendor of named components (`nav,usage_log`, one name, or `--all-behind`) to every adopter listed in their `.fleet.toml [vendored]` manifest entries: copy, hash-verify each component, bump the recorded shas, run that repo's own verification gate once, and open one auto-merging PR per repo carrying every component it is behind on, linking back to the scaffold commit and listing each component's old and new sha — no per-repo issue, since a byte-for-byte re-vendor carries no decision of its own. `skills/_lib/vendored_wave/plan.py` groups the drift scan by repo and generates each repo's branch, commit text and PR body; a one-component run gets the same per-component branch, commit subject and one-line PR body as always. `--dry-run` (or bare `check`) reports, per repo, the components it is behind on and how many PRs the wave would open, touching nothing. A **contract-change check** diffs the component's CSS selectors and README between each behind adopter's pinned sha and the tip, and a removed selector stops the wave until a human says the markup still works (a byte-for-byte, hash-verified re-vendor cannot see a `modal` component split in the scaffold that left two apps unstyled). Invoke explicitly (by hand or a periodic batch), never reflex-fired per scaffold commit — see `skills/propagate-vendored/README.md` for the manifest-schema decision writeup.
