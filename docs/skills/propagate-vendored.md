# `/propagate-vendored`

- **`/propagate-vendored`** — turns a `project-scaffolding` component fix into a one-command, Dependabot-style distribution wave instead of N hand-filed issues + N hand-built PRs (~40 mechanical byte-copy PRs across 6–7 repos for two components, `project-scaffolding#144`–`#150`). Fans out a byte-for-byte re-vendor of one named component (`nav`, `tray_lifecycle`, …) to every adopter listed in its `.fleet.toml [vendored]` manifest entry: copy, hash-verify, bump the recorded sha, run that repo's own verification gate, and open an auto-merging PR linking back to the scaffold commit — no per-repo issue, since a byte-for-byte re-vendor carries no decision of its own. `--dry-run` (or bare `check`) reports who's behind, touching nothing. A **contract-change check** (fleet-config#1227) diffs the component's CSS selectors and README between each behind adopter's pinned sha and the tip, and a removed selector stops the wave until a human says the markup still works (a byte-for-byte, hash-verified re-vendor cannot see the `modal` split of `project-scaffolding#300` that left two apps unstyled). Invoke explicitly (by hand or a periodic batch), never reflex-fired per scaffold commit — see `skills/propagate-vendored/README.md` for the manifest-schema decision writeup.
