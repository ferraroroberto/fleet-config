# Stranded index locks (a read that freezes a repo)

`git status` takes `.git/index.lock` purely to write back a refreshed stat cache — an optimisation, not part of producing the output — so a read-only caller killed mid-refresh strands a 0-byte lock and touches nothing else. The part worth remembering is that a stale lock is invisible to a read: `git status --porcelain`, `git fetch`, `git rev-list` and an up-to-date `git pull --ff-only` **all exit 0 with the correct output** while the repo cannot `git add`/`commit`/`pull`/`stash`, so the raise-on-non-zero check never fires and a sweep files the repo as healthy. The failing signal is never generated, so any detector built on "did a git command fail" will miss it. The incident accounts and the rules live in [recurring-gotchas.md](../recurring-gotchas.md#a-fleet-wide-git-status-sweep-strands-0-byte-index-locks-unless-it-sets-git_optional_locks0).

Two halves, both one-place fixes. **Stop creating them:** `skills/_lib/git_run.git_env()` sets `GIT_OPTIONAL_LOCKS=0` inside `run_git`, so all 62 callers inherit it, with a hooks-tier copy in `hooks/_lib.py` (`branch_before_edit_guard` shells out to `git` on every Edit/Write in every live session, by far the highest-frequency git spawn this repo owns; `tests/acceptance/tree_boundary.py` asserts the two copies agree). Byte-exact readers (`git show <ref>:<path>` for hashing) get `git_run.run_git_bytes`, the same spawn without the UTF-8 decode, so “I need raw bytes” is no longer a reason to hand-roll one; `tests/run_acceptance.py`'s `git_wrapper` check now fails on any literal `subprocess.<spawn>(["git", …])` under `hooks/`, `skills/`, or `.claude/skills/` outside the two wrapper modules, so the inheritance is enforced rather than remembered. Only *optional* locks are suppressed — a requested write still takes the real index lock and still refuses when one is held, proven against real git in `tests/repo/test_git_run.py` rather than asserted in prose. **Find the ones that already exist:** `skills/_lib/index_lock.py` reports five verdicts — `absent`, `fresh` (younger than 15 min: a git op is legitimately in flight, an established fact rather than an unknown), `stale` (past the threshold with no `git` process on the machine at all), `stale_unconfirmed` (past the threshold but that could not be established), and `unreadable` (the git dir did not resolve; never folded into `absent`, because an unasked question is not a clean bill of health). Whether a lock is *reported* never hinges on the fragile process probe — that only downgrades confidence. `fleet_audit_scan` checks it before believing any read and gives it its own `stale_lock` bucket, which `/audit-fleet` surfaces by name every week; it is the one bucket that never self-heals, so it repeats verbatim until a human acts. **Nothing here ever deletes a lock** — it is another process's file, and refusing to remove one on chief authority is what surfaced the whole class in the first place.
