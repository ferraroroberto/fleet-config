# Concurrent same-repo work (claim-or-worktree)

Two agent sessions working the **same** repo used to collide: they shared one working directory, so a `git checkout` in session B rewrote the tree under session A mid-build. The collision window isn't branch-cut time — it's the minutes-long *study* phase before either agent writes anything. So the fix claims the repo at the **very first action**, before reading the issue: **first come, first owns `main`.**

`skills/_lib/worktree_claim.py` is the one concurrency primitive. `/issue-start`'s step 0 calls `acquire <repo>`, which atomically publishes a claim — written fully-populated in a private temp dir, then `rename`d into place, because a bare `mkdir`-then-write let two racers both win `MODE=primary` — under the repo's shared git dir (`git rev-parse --git-common-dir`, visible from every worktree). The first session wins `MODE=primary` and works in place on `main`; every session after gets `MODE=worktree` and builds in an isolated sibling worktree `<repo>-wt-<N>` on its own branch, sharing the object store — separate HEAD + separate files, no race. Because `/issue-yolo`, `/issue-add now`, `/issue-batch` in-place, and `/cleanup-fleet` all route through `/issue-start`, they inherit the behaviour for free — **but only by pointing at it, never by paraphrasing it.** `/issue-yolo`'s Phase 2 once restated `/issue-start` as "pre-flight, checkout main, pull, cut the branch", silently dropping step 0; a Board-dispatched lane followed the summary, never ran `acquire`, and cut its branch in `app-launcher`'s live primary checkout, bypassing the forced-worktree rule below. Handing-off skills now name step 0's `acquire` as the mandatory first action and defer every other git step to `/issue-start` itself; `tests/run_acceptance.py`'s worktree-mandate check fails if `/issue-yolo` Phase 2 stops naming `acquire` or starts restating the git steps again. This is still prose, and a PreToolUse backstop refusing `git checkout -b` in a launcher-dispatched primary was deliberately not added: `/quick` legitimately cuts its `quick/` branch in a launcher primary, and a command's effective directory (a `cd` or `git -C` inside it) is not the payload's session `cwd` — the same cwd-resolution false positive that got the first branch guard reverted.

**The branch may already exist.** `setup_worktree()` picks its `git worktree add` form from what's already there: an existing *local* branch is checked out as-is, a branch that exists only on `origin` is created from `origin/<branch>` so the lane resumes the work already pushed to it, and only a genuinely new branch is created off the default branch. The previous unconditional `-b <branch> <main>` crashed with a raw traceback on the first case and — silently — started the lane at `main` on the second, so every agent needing a worktree on an existing branch fell back to `acquire --force-worktree` plus a hand-made worktree. The one failure no start point can fix, a branch already checked out in another worktree, now names the holding tree.

**The worktree is a faithful runtime twin**, differing only where sharing is the bug. `setup_worktree()` stages the primary's gitignored runtime config (`config/*.json`, excluding `*.sample.json` templates) into the new worktree, since `git worktree add` only populates tracked files — without it, a repo's e2e suite silently mass-skips inside the worktree while its own pre-ship gate still reports green. That copy is byte-verbatim **except for a top-level `port`**, which is repointed into the `8500–8999` band — deterministic from the issue number, then probed past anything listening or already handed to a sibling config in the same worktree, so a repo with two ported configs gets two distinct ports. Carrying the primary's port across made every lane's e2e suite see the user's live tray and refuse to run, and left a worktree that actually boots the app trying to bind the primary's port. Secrets and every other field copy untouched. The primary's gitignored **`.env`** is mirrored the same way, right after `config/*.json` — byte-verbatim, no-op if the primary has none, existing destination left alone. Without it, a repo whose startup path reads a secret from `.env` (`local-llm-hub`'s `LOCAL_LLM_HUB_SSH_KEY`, driving its fleet-reconcile SSH probe) stalls on the missing value until an unrelated timeout trips, and the e2e stage of the pre-ship gate goes red for a reason that has nothing to do with the diff. Some repos keep their runtime config at the repo **root** instead of under `config/` (`accounting-quarterly`'s `config.json` and `classification_rules.json`, `home-automation`'s `devices.json`) — `copy_root_config` mirrors those too, right after `.env`, reusing the same port-repoint and machine-bound-blanking rules. Rather than hardcode which root filenames matter, it asks `git check-ignore` which of the repo's own root-level `*.json` files are gitignored, so a repo that adds a new one is covered with no code change here; a tracked file matching the `*.json` glob (a `package.json`, a checked-in `*.sample.json`) is never copied. Its stderr receipt is `ROOT_CONFIG_COPIED=`, alongside `CONFIG_COPIED=` and `ENV_COPIED=`. The need showed up when an audit-rework worktree in a sister repo crashed on startup with no config at all.

**A worktree's config is disposable — its machine-bound values must be too.** "Faithful twin" stops at any value that resolves to real state outside the worktree: a synced mirror/backup folder, an index path, another repo's database. `/issue-start`'s own "ready to validate" handoff boots the copied config for real, and a session in a sister repo did exactly that — its worktree instance read and wrote the owner's real OneDrive mirror twice before anyone noticed. `copy_runtime_config` now blanks those values in the same per-file pass as the port rewrite, right after it. A repo declares exactly which dotted keys are machine-bound via `.fleet.toml`'s `[worktree]` table (`blank_config_keys = ["mirror.dir", "mirror.backup_dir"]`, read by `worktree_blank_config_keys` the same way `extra_junctions` is read); a repo that declares nothing gets a conservative built-in default instead — any string value that looks like an `{onedrive}`-style template placeholder or an absolute Windows path is blanked (list entries filtered the same way), never left carrying the primary's real path. An empty string is what the app already treats as "feature off" (task-os's mirror does); a repo whose gate genuinely needs to keep a value opts out per key, or opts out of the default heuristic entirely with an explicit empty `blank_config_keys = []`. Same fail-open contract as the port rewrite: a config that isn't a JSON object, or doesn't parse, copies untouched rather than breaking setup. Separately, a repo can list keys whose values must never be reproduced in a worktree at all — `secret_config_keys = ["auth.token"]` in the same table — and `remove_secret_config` deletes them from the copy outright, whatever their type. It is additive: it never switches off the default heuristic the way declaring `blank_config_keys` does, and an undeclared repo removes nothing.

**Standing a side instance up is a guarded step, not a judgement call.** Validating a change by booting a *second* disposable instance out of the lane's own worktree — leaving the user's live app on its own port untouched — is strictly better than detaching the primary onto a branch and restarting the tray, and it is the default. Three things about it were per-lane judgement, each learned from something that happened on 2026-09-19. `worktree_claim.py side-instance-preflight [<checkout>]` (0 = safe to boot, 1 = refused, 2 = **unknown**, which is never permission) answers all three at the one step such a lane cannot skip.

- **It refuses a primary checkout.** `worktree_forced` already does that — but inside `acquire`, and a free-text-dispatched lane that never invokes `/issue-start` never calls `acquire`; it just runs `git checkout -b` wherever it woke up. `branch_before_edit_guard` does not catch it either, since it blocks edits on the *default branch* and the lane is on a feature branch. Every guard stayed intact, none was consulted, and the live `:8445` app served an hour of uncommitted JS and CSS to a phone. Two escapes, both deliberate: `WORKTREE_CLAIM_ALLOW_PRIMARY=1` (the same spelling `worktree_forced` honours) and a repo's own `[worktree] primary_instance_ok = true`, which puts `life-os`-shaped operational lanes — whose gitignored identity/context/state exist only in the primary clone — in the repo that owns the exception rather than in whichever session remembered to export the variable.
- **It knows which blanked config keys are safe to restore.** Blanking (above) is correct but blunt: for `app-launcher` it empties eight keys at once and the instance will not boot usefully until some come back, and restoring a *write* path silently points the test instance at live state. `[worktree] read_safe_config_keys = ["projects_dir", "apps_scan_root"]` names the read-only ones. Additive like `secret_config_keys`, never a mode switch, and **fail-closed**: blanking stays the default, exemption is opt-in by exact key or declared sub-table, an explicit `blank_config_keys` entry wins, and an undeclared key — including one added to the config after the list was written — is blanked. The preflight then re-checks a provisioned config and refuses by name when a machine-bound value sits under a key the repo never declared read-safe.
- **It claims the port instead of deriving it.** `worktree_port` seeds its offset from the issue number and probes past anything *listening*, but at provisioning time nothing has booted, so two lanes set up back to back could be written the same port and collide later as a bind error that never mentions the other lane. Ports are now reserved in one machine-global registry under `hooks_state.state_dir()` (`worktree-ports.json`), consulted by `worktree_port`, written by `_repoint_config_port`, released by `remove-worktree`. Liveness is the worktree **directory**, not a TTL — gone means the reservation is pruned, so a crashed lane cannot strand a port and a slow one cannot lose its own. The preflight *reserves* rather than merely observing, so a worktree provisioned before this existed self-heals instead of reporting `unknown` forever; a port another live worktree holds is refused with the holder named.

**What the preflight does not do, and says so.** It does not boot: starting the app is repo-specific (a tray batch file, uvicorn, Streamlit) and a `stand-up` command that could not actually start most repos would be the helper that looks total and isn't. A green run prints what the lane still owns — start the app yourself, point the browser at the reported port rather than the primary's, don't commit the provisioned config — and it cannot help a lane that never calls it. Missing gitignored runtime directories (`app-launcher`'s `webapp/certificates/`, without which the tailnet URL and WebAuthn fail in a way that reads like a bug in the change under test) need no new mechanism: `[worktree] extra_junctions` already covers them, and the preflight refuses when a declared target exists in the primary but not here.

**Release is a verified step.** `/issue-finish` releases the claim (primary) or tears the worktree down (worktree), confirming `status` → `CLAIM=free` so a foreign or abbreviated finisher can't silently skip it; `/issue-yolo` inherits the same release, since its Phase 4 delegates to `/issue-finish` (its old inline-merge path released the claim itself). A claim left behind anyway self-heals on the next `acquire`: it's reclaimed once it ages past the 8h TTL **or** as soon as its recorded branch no longer exists on the remote (a merged-and-deleted branch is definitionally done — `is_stale` checks `git ls-remote`).

**The claim decides only *tree selection*** — it says nothing about who holds it at the moment something actually runs `git checkout <main>` on the primary, and a concurrent flow that reached the primary tree without its own live claim did exactly that against a session with 7 uncommitted files. `assert-owner <repo> <issue>` closes that gap: `/issue-finish` step 5 and `/issue-start` step 4 both call it immediately before their `git checkout <main>`, refusing (with the "primary held since..." message) unless the tree is clean and the claim is free or already owned by the calling issue. It guards only those two call sites — a hand-run `git checkout`, a sub-agent, or a future skill still bypasses it, since this is a flow-level precondition, not an enforced boundary (a `PreToolUse` hook was tried for the adjacent problem and reverted within the hour for blocking legitimate operations fleet-wide).

**A running process is not a claim holder.** The launcher webapp, home-automation's tray, and this repo's own `hooks/`+`skills/` junctioned into every live `~/.claude` hold no claim, so a first-and-only unattended agent legitimately wins `MODE=primary` and edits files a live process is serving. `acquire --force-worktree` closes that for unattended fleet fanout: it skips the claim attempt entirely, always prints `MODE=worktree`, and deliberately publishes no claim so the primary stays free for a human session. `/cleanup-fleet`, `/cleanup-fleet-all`, and `/codebase-audit`'s security self-heal all use it — and so does `/issue-start` itself whenever `APP_LAUNCHER_SESSION_ID` is set, i.e. whenever App Launcher's Board dispatched the session rather than a human starting it. An interactive `/issue-start` with no such variable keeps the default claim-or-worktree behaviour, which is correct there.

**`mode` answers about the cwd, not about its argument.** The primary-vs-worktree answer is the hinge every teardown turns on, and it was silently wrong in exactly one direction. `mode <repo>` with a bare name — the form all three finishing skills document — hit `_resolve_path_arg`'s sibling fallback (added so `remove-worktree fleet-config-wt-7` resolves): from inside `fleet-config-wt-652`, `fleet-config` doesn't resolve locally, so it resolved to the *primary*, and `is_primary_checkout` truthfully answered `primary` about the tree it was handed. A worktree lane believing that takes the primary teardown path and runs `gh pr merge --delete-branch`, producing the very `'main' is already used by worktree` failure the primary-behind check exists to eliminate — no error, no `unknown`, and the wrong answer always the more dangerous one. `mode` now reads the cwd's own checkout and treats the argument as *identifying the repo* rather than selecting a tree: reconciliation compares shared git dirs, so a worktree naming its own primary is a match, while a genuinely different repo, an unresolvable name, or a cwd outside git prints `UNKNOWN reason=<why>` and exits 2 — a helper that cannot establish which checkout it was asked about says so instead of guessing. The fallbacks themselves are untouched, still right for `remove-worktree`. Its sibling subcommands were audited and need no change: `land-primary` and `remove-worktree` act on a *named* target by design (and each already refuses a wrong-kind target), while `acquire`/`release`/`status` are repo-scoped — their lock lives in the shared git dir and `git worktree list` reads identically from every tree, so argument-vs-cwd resolution cannot change their answer.

**A worktree lane still has to land the primary.** "Never `git checkout <main>` from a worktree" was silently read as "never touch the primary at all", so the worktree branch of `/issue-finish` ended at `remove-worktree` with no landing step *and no statement that landing hadn't happened* — leaving the primary behind `origin` while the lane reported the change shipped. Here that is severe rather than cosmetic: `hooks/` and `skills/` reach `~/.claude` from the primary, so a merged hook or skill change does nothing fleet-wide until that tree fast-forwards (on 2026-08-16 the primary sat 2 commits behind with two merged PRs reported as shipped; `project-scaffolding`'s primary kept a *failing* local gate after the PR fixing it had merged). `land-primary <repo> <issue>` closes it: `assert-owner`'s guard plus "already on the default branch", then `pull --ff-only` and a `rev-list --count HEAD..origin/<default>` check, printing exactly one `PRIMARY=live behind=0` / `PRIMARY=stale reason=<why>` line that the finish summary quotes verbatim. The original caution is intact — it never checks out, stashes, or forces, and `--ff-only` fails safely rather than merging; a refusal is *reported*, never recovered, because merged and live are two facts and a lane that cannot establish the second must say so rather than let silence imply it. The same call site also drops `--delete-branch` in worktree mode (its local half fails `'main' is already used by worktree` — 6 for 6 that day, and six lanes invented six different recoveries), deleting the remote ref explicitly and the local one with `-D` only after an ancestry check, since a squash merge rewrites the SHA and defeats `-d`.

**…except into a tree something is actually serving.** `land-primary` shipped with three questions — is the claim mine, is the tree clean, is it on its default branch — and an hour later all three passed while it fast-forwarded a primary whose tray was serving it: `app-launcher`'s disk moved to `1705558` while the running Python stayed on `9af573f`, so `jobs-row.js` on disk gained a control the live API had never heard of. Static assets are read per request, Python is held in memory, so the Jobs tab was rendering one UI out of two commits. The asymmetry is what decides the fix: *not* landing leaves disk and process both old — behind but coherent; landing leaves disk new and process old — behind **and** skewed. Both need the same restart, so refusing costs nothing the restart won't fix, and there is deliberately no "landed anyway" success variant. The signal needed no new config — `hooks/projects.toml` already separates exactly the right set, because a `tray_cmd` *is* the declaration that a long-running process serves that tree (`fleet-config` declares none, correctly: nothing runs out of it, and landing it is what makes a merge live through the `~/.claude` junctions). Liveness is established from the OS listener table rather than a connect attempt, which on this host cannot answer the question at all: a connect to a *closed* loopback port doesn't come back refused, it hangs to the timeout, indistinguishable from a hung service — and `netstat`'s own table is positive evidence in both directions. Absent from it → land; in it → refuse, naming the port, the commit the live process reports, and the restart as the remedy so an operator reads it as work parked rather than a tool that broke; table unreadable or no port to probe → also refuse, because a probe that cannot be completed is not proof of absence. `/propagate-vendored` lands primaries the same way and inherits the same refusal. Restarting anything is deliberately *not* part of it: restarts here are confirmation-gated and operator-owned, so the tool stops creating the skew and says what unblocks it. The capability itself lives in **`skills/_lib/worktree/service_probe.py`** rather than inside the claim FSM — "is this repo's declared service listening right now, and at which sha?" is a generic question `/issue-finish`, `restart_and_verify_webapp`, and any future health sweep would ask, and `land-primary` is only its first caller; `worktree_claim` imports `service_state` and re-exports the names its own tests and callers already use.

**…but first, is there anything to pull at all?** That guard shipped asking its question one step too early: `grocery-shopping-automation` sat at `6f8f641`, its webapp reported `6f8f641`, zero commits behind — and `land-primary` still answered `PRIMARY=stale reason=live process serving this tree (webapp :8502 at 6f8f641); restart required`, exit 1. Nothing was stale and no restart would have changed a byte. The service refusal is right about fast-forwarding a tree out from under a running server, but a landing that is a **no-op cannot skew anything** — there is no second commit for the assets to come from. Reporting stale there is the mirror image of the rule the whole guard exists to uphold: unknown-is-not-pass forbids folding an unestablished fact into the passing state, and this folded an *established* one out of it, on every `/issue-finish` in a tray repo — which is precisely how a reader learns to skip the one line that check exists to produce. So the distance from the remote is counted first and passed into `land_primary_check` like every other fact, and `behind == 0` returns `PRIMARY=live behind=0` before the service question is asked. The count is taken against a **freshly fetched** ref, because `land-primary` runs right after a `gh pr merge` that never touched local refs — against a stale `origin/<default>` a genuinely-behind tree would read as level, the one error direction this guard cannot afford. A fetch or count that fails is `None`, not `0`: unknown takes the ordinary path through the service guard, exactly as before. The earlier guards still speak first (a dirty or off-branch primary reports its own reason however far behind it is), and the refusal for a behind primary with a live service is untouched for the case it was written for — genuinely behind, live service, still refused.

**…and the fast-forward must not delete a live file the merge untracked.** A merged change that untracks a machine-local file — `git rm --cached` plus a `.gitignore` line, or a rename to `<name>.sample` — is right for the repo and still deletes the working-tree copy on every checkout that fast-forwards over it: git removes a file whose path the incoming commit drops from the index, ignored afterwards or not, and the pull exits 0 onto a clean-looking tree. No gate or reviewer can see it — the lane builds in a worktree and the loss only happens at the primary's fast-forward (incident account: [recurring-gotchas.md](../recurring-gotchas.md#untracking-a-live-config-deletes-it-on-pull)). So every fast-forward the workflow runs goes through **`skills/_lib/untrack_guard.py`**: it lists the paths `HEAD..<target>` deletes or renames away (`diff --name-status -M --diff-filter=DR`), copies each live one aside, runs `merge --ff-only` to the resolved commit, and puts back every one that is now gone **and ignored**. A path the merge deletes without ignoring stays deleted (an intended tracked deletion; restoring it would dirty the tree); a path whose ignore state git cannot report is **kept aside** in its stash dir and reported, neither restored nor lost; a range it cannot list refuses the fast-forward. Every kept file is reported as `RESTORED_UNTRACKED=<paths>` / `KEPT_ASIDE=<path> stash=<dir>`, never silently. `land-primary` and `fleet_audit_scan.py` call it in-process; `/issue-start`, `/issue-finish` (primary mode), `/quick` and the `/cleanup-fleet-all` teardown's check 6 run its CLI (`untrack_guard.py fast-forward <repo> [--ref <ref>]`) instead of `git pull --ff-only`, and the lane result carries what it kept as `restoredUntracked`. `tests/test_untrack_guard.py` reproduces the shape of a real incident in the `automation` repo through `land-primary` against a fixture repo.

**Teardown is symmetrically defensive.** `remove-worktree` tolerates a worktree git has already **deregistered** while its directory survives — the state a leaked process leaves behind — by inverting the `<repo>-wt-<N>` convention when `rev-parse` can no longer resolve the primary, always after the junction strip, and exiting non-zero with the path named if the tree is still there afterwards, so the caller reports honest residue instead of a false clean. It also refuses outright (exit 2, deletes nothing) unless its target actually *is* a linked worktree: a primary checkout (`--git-common-dir` == `--git-dir`) is rejected, and a basename that doesn't match `<repo>-wt-<N>` is rejected unless `--force-nonstandard-name` is passed.

`skills/_lib/active_issue.py` publishes the issue-level lifecycle that App Launcher's Board consumes. `/issue-start` adds `<repo>#<number>` to `~/.claude/hooks/state/active-issues.json` once its branch is ready; `/issue-finish` and `/issue-yolo` remove it only after a successful merge. `/issue-batch`'s in-place path inherits `/issue-start`, while its pre-created worktree path writes explicitly before dispatch. Each row carries `repo`, `number`, `branch`, and `started_at`, plus optional owner fields when positively known: `owner_session_id` (`APP_LAUNCHER_SESSION_ID`), `owner_pid` (the agent process, `CLAUDE_PID` — never the helper's own short-lived pid) and `owner_host`. `classify_owner(row, live_session_ids=…, pid_probe=pid_state, host=current_host())` returns the string `live`, `dead` or `unknown` for a consumer such as the Board: evidence of life wins, `dead` needs positive evidence (the owner session absent from a *readable* live-session list, or the owner pid confirmed gone on its own host), and owner-less legacy rows, foreign-host rows or any unreadable input are `unknown`. `pid_state` is tri-state on purpose — a claim's `dead` needs positive evidence; the state lock reads `pid_state(pid) is True`, so an unknown probe counts as not alive there. Classification never deletes a row; mutations still prune rows older than 24 hours so a crashed agent cannot disable a card forever. The helper tolerates a missing/corrupt file, uses atomic replacement with target-named temporaries (`.active-issues.json.<rand>.tmp`) that the next writer sweeps by age, so a hard-killed writer's orphan is attributable and finite (`hooks_state.atomic_write_text()`, the `skills/_lib` mirror of `hooks/_lib.py`'s copy), and locks the whole read-modify-write transaction so simultaneous batch starts cannot lose unrelated rows. `CLAUDE_HOOKS_STATE_DIR` redirects the file for hermetic tests.

Two Windows specifics, both load-bearing. **The `.venv`** — worktrees don't share untracked files, and a 24-repo fleet can't recreate heavy venvs per worktree, so the helper *junctions* (`mklink /J`) the primary's `.venv` into the worktree; a junctioned venv resolves `sys.prefix` and imports through the link, so the verification gate (`& .\.venv\Scripts\python.exe …`) just works. **The teardown order** — `git worktree remove` does a recursive delete that *follows a junction into its target*, so the helper strips the `.venv` junction with `rmdir` (reparse-safe, no `/s`) **before** `git worktree remove`, or it would wipe the primary's real venv (same junction footgun as `uninstall.ps1`). Never hand-roll `git worktree add`/`remove` + a venv junction in a skill; the helper owns both halves. **On 2026-09-12 that convention cost two repos their venv in one night, and the second time the helper itself is what pointed the lane at the loaded gun**: `setup-worktree`, finding a stale worktree directory in the way, printed *"clean with: `git -C <repo> worktree remove --force <wt>`"* — the one command the whole teardown order exists to avoid. The lane ran it, git followed the still-present `.venv` junction, and `task-os`'s primary venv was gutted *under a live app on `:8448`* (partially, not wholly: the delete aborted on the `.pyd` files that process held open, which is why the damage looked file-level and unlike the `local-llm-hub-lite` case rather than like the same mechanism it was). That hint now names `remove-worktree` and says why. Two lessons generalise past this one string. First, **a helper that owns a dangerous ordering must never emit a recovery hint that bypasses its own ordering** — the hint is read at exactly the moment the reader has no context and most trusts the tool. Second, **the guard belongs in the layer that cannot be forgotten**: `venv_discipline.py`'s rule 4 now refuses `git worktree remove`, `rm -rf`, `Remove-Item -Recurse`, `rmdir /s` and `python -m venv` against any path that resolves through a `.venv` junction, whoever types it and whichever harness they type it in, so the safe ordering no longer depends on every future brief remembering to restate it. The `<repo>-wt-<N>` sibling naming is deliberate: `hooks/_lib.py`'s `detect_project()` strips a trailing `-wt-<N>` suffix from the path segment that carries it before matching against the repo's `cwd_prefix` in `projects.toml` (falling back to it only when the raw cwd matches nothing, so a repo whose real name happens to contain that shape still matches directly first), so `notify_on_idle` names the right project even when called from inside the worktree (a `.worktrees/` layout would break that match). `/audit-fleet`'s filesystem crawl skips linked worktrees via a `.git`-is-a-directory guard.
