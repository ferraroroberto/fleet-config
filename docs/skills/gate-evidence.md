# Gate evidence (a green bound to the tree it ran against)

`skills/_lib/gate_evidence.py` replaces "green this session" (a remembered pass) with a pass bound to a content hash of the whole working tree. `run --label <L> -- <argv>` runs the gate itself (so the exit code is observed, not reported), hashes the tree before and after, and records `{cmd, exit, wtree, utc}` only when the two agree; a tree that changed mid-run, or an unhashable one, drops any earlier record for the label instead of leaving a stale pass. `check --label <L> [--expect-cmd]` prints exactly one of `FRESH` / `STALE` (changed paths named on stderr) / `MISSING` / `UNKNOWN`. The hash copies the index (`rev-parse --git-path index`, so linked worktrees work) to a temp file, points `GIT_INDEX_FILE` at it, and runs `git add -A` + `git write-tree`: the real index is never touched, committing identical content stays `FRESH`, any edit or new untracked non-ignored file goes `STALE`, ignored files (`.env`, `.venv`) never count. Evidence lives at `rev-parse --git-path gate-evidence.json`, outside the working tree and per worktree. `GIT_INDEX_FILE` has no `-c` form, so `git_run.run_git` gained a keyword-only `extra_env` that layers under `git_env()` — `GIT_OPTIONAL_LOCKS=0` cannot be dropped. Consumers: `/issue-finish` step 3 runs the gate through `run --label gate`; step 3c's no-double-run, step 5's skip-the-CI-wait and `/e2e`'s dedupe rule each ask `check`, and `/e2e` records its slice as `e2e-<tier>`. Anything but `FRESH` means re-run once or watch CI — it fails closed. `check-red --label red` is the inverse question for a bug fix: `run` also records a failing exit, and `check-red` prints `RED` only when that record failed (not exit 0, not 127 "never started") on a tree other than the current one, i.e. the new test was seen red before the fix; `NOT_RED`, `SAME_TREE`, `MISSING` and `UNKNOWN` all fail closed, and `pr_body/check.py` turns them into the `red-first` rule. Tested end to end against temp repos and a linked worktree (`tests/e2e/test_gate_evidence.py`).

## The Mac nightly line

The probe fake ratchet (project-scaffolding's `docs/probe-fake-ratchet.md`) prints `MAC_NIGHTLY: unverified (...)` when a branch's diff touches a declared probe module: per-platform fakes passed, no Mac ran. That is a state beside the gate result, never part of it. `run` passes the command's stdout through unchanged, reads it for that line and keeps what it saw beside the label's record, including for a run whose pass is not recorded. `mac-nightly [--label gate]` answers `MAC_NIGHTLY=unverified` followed by `**Mac nightly:** unverified (<paths>)` (the line a finish report and PR body carry), `MAC_NIGHTLY=none` (claim nothing; there is no "verified"), or `MAC_NIGHTLY=unknown` (exit 2): a repo that enables `[probe_fake_ratchet]` whose gate output was never read, was not read to its end, came from a failed run or belongs to another tree. A repo that does not enable the ratchet is `none` without any record, since nothing there prints the line. `pr_body/check.py` holds the PR body to the same answer.

## Per-unit run history

`run --units` (implied when the command runs `run_acceptance.py`) also records how each unit of the gate did, so a unit's time, outcome and process spawns can be compared across runs. The gate reports to temp files named by `FLEET_GATE_UNIT_REPORT` and `FLEET_GATE_SPAWN_REPORT`: `tests/acceptance/run_history/unit_report.py` writes one line per unit (a check function or a standalone suite file, never one `check()` call) and publishes the running unit in `FLEET_GATE_UNIT`; `skills/_lib/unit_history/spawn_probe/sitecustomize.py`, on `PYTHONPATH` for the run, counts every `subprocess.Popen` in any Python process of the gate's tree under that unit. Afterwards `unit_history/ledger.py` (this repo's ledger location over the vendored `unit_history/unit_ledger.py`) appends one `unit` row per unit and one `run` row to `<hooks state>/gate-unit-ledger.jsonl` (gitignored with the rest of `hooks/state/`): run id, UTC time, label, the tree hash the run started on, status (`pass` / `fail` / `skip`), seconds and spawns, plus, for a failed unit only, `output`: the last 8,000 characters of what it printed on stdout and stderr (or the traceback it raised), so a red unit can be diagnosed from the ledger without a manual repro. The child also gets `FLEET_GATE_WTREE`, the tree hash the run started on. `FLEET_GATE_ONLY=<unit>[,<unit>]` makes the dispatcher run and report only those units, which is how a new test's red-before-fix record is taken on the pre-fix tree. With `FLEET_GATE_COVERAGE_REPORT` and `FLEET_GATE_COVERAGE_ROOT` set, the probe's coverage half records the lines each unit ran in files under the root (`sys.monitoring`, each line reported once per unit); the weekly burst uses it to build the coverage map. The spawn figure is a floor: a child started with `-I`/`-S` or a scrubbed environment is not seen. A ledger write failure is reported on stderr and never changes the gate's exit code. `python skills/_lib/unit_history/cli.py summary [--runs N]` prints counts and seconds for the last N runs: total seconds, spawns, unit count, the failing units, and the per-unit medians of the top 20. Tested in `tests/unit_history/test_unit_history.py`.
