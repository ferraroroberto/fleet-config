# Skills

The skill inventory across both tiers, why the tiers are split the way they
are, and the shared `skills/_lib/` primitives the issue-workflow skills are
built on — the claim-or-worktree concurrency lock, the issue lifecycle marker,
the UX-conformance gate, and the deploy-coverage gate.

Skills live in **two tiers**, both versioned in this repo:

- **Global** (`skills/`, junctioned → `~/.claude/skills` + `~/.agents/skills`) — load in every session in every repo: the issue-workflow set (`/issue-add`, `/issue-start`, `/issue-finish`, `/issue-yolo`, `/issue-triage`, `/issue-batch`, `/issue-finish-batch`), `/e2e`, `/quick`, `/handoff-commit`, `/screen`, `/codebase-audit`, `/design-sync`, `/e2e-audit`, `/docs-shots`, `/propagate-vendored`, and the shared `_lib/` helpers. `/e2e`, `/design-sync`, `/e2e-audit`, `/docs-shots`, and `/propagate-vendored` are global (not fleet-only) because they operate on *sister* repos and must load there.
- **Fleet-only** (`.claude/skills/`, project-scoped — Claude Code loads it only when cwd is `fleet-config`) — the whole-fleet orchestrators that never make sense from a single sister repo: `/audit-fleet`, `/design-sweep`, `/cleanup-fleet`, `/cleanup-fleet-all`, `/chief`, `/context-audit`, `/context-purge`, `/insights-weekly`, `/learning-log`, `/system-map`, `/config-map`, `/fleet-health`, `/sota-watch`. Living under `.claude/skills/` instead of the junctioned `skills/` keeps their descriptions out of every *unrelated* session's always-on context (fleet-config#161) while still loading them here. `/codebase-audit` deliberately stays **global** even though it's an audit — `/audit-fleet` fans out sub-agents that `cd` into each repo and invoke `/codebase-audit` there, so it has to be available everywhere. One caveat: project-scoped `.claude/skills/` is a Claude Code concept; Codex reads `~/.agents/skills` (the global junction) only, so these fleet skills don't reach Codex — acceptable, since they run via `claude -p` on a schedule.

Every checked-in scheduled `run-weekly.bat` routes its Claude call through `skills/_lib/claude_progress.py`. The stdlib-only adapter enables Claude Code's verbose `stream-json`, converts it into flushed elapsed-time milestones for App Launcher's live Jobs pane, keeps assistant reports readable, drops thinking/signatures/raw payloads/token noise, tolerates future or malformed events, and returns the child process's exit code unchanged — except where it has established that a clean exit is a lie. A stalled stream (`124`), the CLI's background-task kill (`125`), a skill's own `SCHEDULED-RUN-FAILED` delivery assertion (`123`) and a stream that truncated near shutdown (`122`) each override an exit `0` with their own code and their own message, so an unattended job that did nothing shows red rather than green. Those are all symptom detectors; `--delivery-check <script.py>` is the outer one — a post-condition run after the child exits *whatever* its exit code was, asking whether the run's actual artifact exists (`121` when it does not). `/audit-fleet`'s checks for a fresh digest comment on its ledger issue, after a scheduled run reported success having audited zero repos and posted nothing (fleet-config#560).

**Stall watchdog.** The adapter also kills a scheduled run whose stream has gone completely silent and exits `124`, so a wedged unattended run surfaces as a *failed* job within the hour instead of holding its slot until a human notices (fleet-config#411). The default limit is 45 minutes of silence — far above any legitimate quiet stretch, since every wrapped Bash/PowerShell call is itself bounded by the context filter's `FLEET_CONTEXT_FILTER_TIMEOUT` (600s default). Tune it per launcher with `--stall-timeout <seconds>` (consumed by the adapter, never forwarded to `claude`), fleet-wide with `CLAUDE_PROGRESS_STALL_TIMEOUT`, or disable it with `0`. The kill is a process-tree kill: Claude's own sub-processes hold the stdout pipe, so killing only the direct child would leave the adapter wedged alongside the run it just ended. The watchdog kills *before* it announces the kill, and the announcement is best-effort — announcing first parks the watchdog thread in a `print()` on a backpressured stdout, so the kill never runs (fleet-config#514).

**False-success guards.** A scheduled run that reports `exit 0` having delivered nothing is worse than one that crashes, so the adapter turns each known shape into its own exit code. Claude Code's `--print` mode kills any sub-agent still in flight once its background-task ceiling elapses and exits `0` regardless (fleet-config#506) — the adapter watches stderr for that kill signature and exits `125` instead, and now also *prevents* the kill by handing the child `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`, the CLI's own documented "wait indefinitely" setting (fleet-config#519). The ceiling is set after the inherited environment (a stale ambient value can't silently reinstate it) and before any explicit `env=` override, and the 45-minute stall watchdog remains the real upper bound on a wedged run. The third shape — a run that ends perfectly normally having done no work at all — is invisible to both, because only the skill knows what "no work" means for it: a scheduled skill asserts its own delivery at the end of its run and prints the literal marker `SCHEDULED-RUN-FAILED` when that assertion fails, which the adapter maps to exit `123` (`/audit-fleet`'s step-6 delivery assertion is the reference implementation: ≥1 repo evaluated, a digest composed and printed, and the digest comment either posted or skipped with a stated reason).

Beyond the issue-workflow trio (`/issue-add`, `/issue-start`, `/issue-finish`) and `/handoff-commit`, this repo also ships:

- **`/codebase-audit`** — read-only quality sweep of the resting codebase against its `CLAUDE.md` and senior-dev standards. Bundles findings into at most 7 GitHub issues (one per fixed bucket: duplication, stale/dead code, CLAUDE.md drift, maintainability, slop — AI-generated bloat whose volume doesn't earn its keep — bugs, and documentation — README/`docs/` that drift from `CLAUDE.md`, repeat themselves, go stale, or omit a shipped feature), self-assigned, deduped against open issues, with a stricter filing bar for the bugs and documentation buckets, the two that historically re-surfaced the most low-value noise (fleet-config#251). An eighth kind, **security**, is *not* a public checklist bucket — a gap sitting in a public issue is itself a disclosure — so it is self-healed in place (step 8b: a redacted issue with no vulnerability detail, one branch fixing every gap with a mandatory regression test, generic commit/PR text, auto-merge only on a green gate, a private `--kind security` review alert, and escalate-not-merge on any failure). Complements the diff-scoped `/code-review` / `/simplify` / `/security-review`.
  - **Idempotence.** A per-repo `audit-meta` **ledger issue** records the audited **default-branch** commit SHA + rubric hash — never the working checkout's `HEAD`, which the squash-merge + delete-branch pipeline destroys (fleet-config#567) — so a re-run over an unchanged repo short-circuits before reading any files. `audit_issue.py ledger-write` is the single entry point that composes *and* upserts that block, so the agent never hand-writes the sha or the delimiter (fleet-config#566): it records the verified default-branch commit and refuses rather than guessing, accepts either marker form while normalizing every write back to the canonical one (a drifted ledger self-heals), and refuses a body that wouldn't parse back. A ledger the gate can't read — unparseable block or unresolvable baseline — routes the repo to a full audit under its own distinct reason (`fleet_audit_scan.broken_ledgers()`), named in the sweep plan line and the digest so a recurring weekly cost can't masquerade as organic change; `fleet_audit_scan.py`'s `accounting` block asserts the buckets sum back to the repos enumerated so none can vanish.
  - **Skip rules**, so a repo is never re-flagged for churn it caused itself: `SKIP_SELF_FIX` when its only commits since the last audit are `/cleanup-fleet` (or self-healed security) fixes for its own findings, detected via merged-PR `closingIssuesReferences` against its managed bucket issues; `SKIP_BELOW_THRESHOLD` when organic commits — weighted by conventional branch type (`feat`/`refactor` full, `fix`/`chore` partial, `docs`/`test` none) — haven't yet accumulated past the weighted-LOC threshold into `AUDIT`, with the ledger left untouched so the total keeps accumulating across runs (fleet-config#315). All these decisions are one shared, unit-tested Python sweep (`skills/_lib/audit_issue.py`'s `evaluate_repo` + `skills/_lib/fleet_audit_scan.py` for the whole-fleet pass), not per-repo LLM prose.
  - **Traceability.** Each whole-repo audit posts a counts-only `<!-- audit-snapshot -->` comment to the ledger issue — a per-category findings table (date · sha · the seven buckets · total · security-fix count) — kept off the gate's hot path (which reads only the ledger body), so opening a repo's ledger shows its findings *trajectory* over time. Each managed issue (ledger + one per bucket) carries a hidden `<!-- audit-managed: kind=… -->` marker and is upserted through `skills/_lib/audit_issue.py`, so a re-run merges into the one issue per type rather than filing a duplicate.
- **`/design-sync`** — the **web-app design-conformance** detector. Reads the fleet design system (`~/.claude/design.md` light + `~/.claude/design.dark.md` dark — Google's `design.md` schema, Vercel's two-file light/dark convention, GitHub-mobile palette), maps its tokens onto a target app's CSS custom properties (light + dark), and surfaces the values that have **drifted** from the spec — plus the spec's component and interaction contracts: the navigation contract (the floating bottom-tab pill), PWA install icons from the canonical `brand_gen` family with distinct regular/maskable assets, collapsible cards against the `disclosure` contract (card padding zeroed, summary height/padding, open-state divider, body padding — fleet-config#231), and the mobile contracts promoted from home-automation#409 (#342): editor `<dialog>`s (with or without a `<form>` wrapper) held to the `modal` contract, effective 44px hit-target authoring, Chart.js tick budgets + non-colour series cues, and the `loading/ready/empty/stale/error` async-lifecycle vocabulary. Rendered-only geometry (effective rects, overlap, the viewport×theme matrix) is reported as `unmeasured` unless the repo ships the canonical browser harness (project-scaffolding#157). It files exactly one deduped `design-drift` issue per repo through the *same* `skills/_lib/audit_issue.py` upsert machinery as `/codebase-audit`, so `design-drift` is a first-class audit bucket: `/cleanup-fleet design-drift` fans out fixers and `/issue-triage` treats it like any other. Default mode is read-only on code (reports + files the issue); `/design-sync apply` writes the aligned token values into the working tree for review. Skips Streamlit POC spikes and never re-authors nav/components (those are vendored verbatim from `project-scaffolding`). The fleet-wide weekly sweep that runs it across every web app is `/design-sweep` (below), with the `design-drift` bucket surfaced in the `/audit-fleet` digest (#180).
  - **Tailnet-cert conformance** (fleet-config#210) rides the same read as one adjacent infra check on the same web-app population: a Tailscale-reachable app (a `*.ts.net`/Tailscale mention in `README.md`/`CLAUDE.md`/`docs/**`) that still provisions HTTPS *only* via a self-signed CA + `/install-ca` mobileconfig dance, with no `tailscale cert` provisioner, is convention drift from the `project-scaffolding#89` standard. The heuristic is a deterministic truth table in the pure, unit-tested `skills/_lib/cert_drift.py` (`detect`); on drift it files a **separate** deduped `cert-drift` issue (its own first-class bucket, never folded into `design-drift`) pointing at the standard, so `/cleanup-fleet cert-drift` can migrate them later. It never auto-applies the cert migration (`apply` only touches CSS), and a genuinely LAN-only app — self-signed but no Tailscale signal — correctly stays clean.
- **`/e2e`** — the fleet's one owner of **e2e decisioning, execution, and inline suite maintenance** (fleet-config#556), built to stop full Chromium+WebKit runs being the price of every diff without ever under-testing. Fronts project-scaffolding's diff-proportionate routing convention (`docs/e2e-routing.md`): probes the repo with the deterministic `skills/_lib/e2e_route.py` (classifier / `[e2e]` table / suite / web-surface facts), runs the repo's own `scripts/classify_e2e.py` and honors its tier (`skip`/`static`/`full`, fail-safe to `full`) verbatim, **self-heals adoption** where the router is missing (byte-verbatim classifier copy from the scaffold + a conservative starter `[e2e]` table + the anti-drift test, all riding the current feature branch), and falls back to same-vocabulary LLM judgment only where no classifier can exist yet — uncertainty always escalates to `full`, never narrows. The same run maintains the suite as a side effect: tests deleted with the feature that used them, qualifying Loop-2 regressions added directly (respecting the <15-test target), routing-table rules kept honest. Delegated to by `/issue-finish` (step 3c), `/issue-yolo` (Phase 3d), and `/issue-batch` sub-agents — evaluation is mandatory before every PR, execution proportionate — and invocable standalone (`/e2e`, `/e2e plan`, `/e2e full`) mid-session after ad-hoc changes. A repo with no suite at all gets a worth-it evaluation (webapp/Streamlit repos only) rather than a silent pass.
- **`/quick`** — the sanctioned **trunk-commit lane below the issue threshold** (fleet-config#558): one capped, verified, conventional commit pushed directly to the default branch — no issue, no PR — for changes where that ceremony buys nothing (a one-liner, a color tweak; nothing to plan, no second reviewer, one commit is already the revert unit). Explicit invocation is the authorization (the matching carve-out lives in `global-CLAUDE.md`'s Branch & PR hard rules — the only exception to "never commit to main directly"). Guardrails, in priority order: **auto-escalation** ("this outgrew `/quick`" → `/issue-add`/`/issue-yolo`) whenever the change exceeds the caps (≤2 files, ~≤20 lines, no new files, no API/schema/dependency/design surface) or a design question appears; **verification never skipped** — the repo gate plus the `/e2e` evaluation (whose proportionate routing is what makes the lane affordable: a cosmetic diff routes `static`/`skip` in seconds); edits ride an ephemeral `quick/<slug>` branch ff-merged to main, so a red gate or an escalation leaves main untouched and launcher-dispatched sessions never edit `main` in place. Three-lane boundary: `/quick` = cosmetic/one-liner with zero decisions · `/issue-yolo` = real bounded work · `/issue-start plan` = design-bearing.
- **`/e2e-audit`** — **on-demand** e2e/regression test-suite redundancy audit (fleet-config#406), deliberately **not** a weekly job — suite bloat is feature-driven, not time-driven, and the fleet already runs six skills weekly. Runs the deterministic `skills/_lib/e2e_test_audit.py` scan: resolves the repo's test dir from its `## CI expectations` CLAUDE.md block (falling back to `tests/e2e/`, the shared convention `project-scaffolding`'s `docs/playwright-ui-testing.md` establishes), inventories test files, counts both raw `def test_` functions and the true pytest-collected node count (parametrize-expanded), clusters near-duplicate test names, flags **same-file tests sweeping the same `@pytest.mark.parametrize` matrix** (the blind spot name clustering can't see — differently-named twins over one shared `MATRIX` collide on nothing, which is how a confident "0 clusters" over 32 collected nodes once closed `project-scaffolding#209` before PR #219 collapsed the same tests to 8 with no coverage loss; fleet-config#602), flags file-size outliers, and — when the repo declares a `## UX surface` block — cross-references declared key views against test coverage. A `## CI expectations` heading **inside a fenced code block** is ignored, so a repo that only *documents* the block template isn't read as declaring one; and a scan whose test dirs resolve to nothing on disk reports `test_dirs_resolved: false` — an explicit *unknown*, never folded into "no tests". LLM judgment is confined to confirming each candidate cluster/gap is real (never re-deriving a count) before filing exactly one deduped `e2e-redundancy` issue through the same `skills/_lib/audit_issue.py` machinery as `/codebase-audit`/`/design-sync` — a first-class audit bucket `/cleanup-fleet e2e-redundancy` fans out fixers for. **Report-only, never rewrites or deletes a test** — the review half of the split with `/e2e` (which owns execution + in-branch maintenance, fleet-config#556). First validated against `app-launcher`'s `tests/e2e/` (~400 collected nodes vs. `playwright-ui-testing.md`'s explicit <15-test target).
- **`/docs-shots`** — the **judgment + orchestration** half of a repo's visual-docs screenshots (fleet-config#93); the deterministic capture engine (Playwright, fail-safe masking, the manifest, README generator) lives per-app, pinned to the shipped reference implementation `content-management`'s `config/doc_capture/` (`content-management#110`/PR#162). Activates only when a repo has `docs/screenshots/manifest.json` (`skills/_lib/docs_shots_plan.py discover`), else a silent no-op. Two entry points: standalone `/docs-shots [feature ...]` (a deliberate refresh — all features or named ones) and a Step-2b sub-step inside `/issue-finish` that intersects the PR diff against each feature's `source_globs` (reusing `ux_surface.py`'s glob matching) to build a stale set with reasons, plus surfaces any changed file under a manifest-covered directory matching no feature as a candidate for a new manifest entry. **Always propose-then-capture** — the engine never runs without the user's explicit OK — and the fail-safe mask guard (a feature with no `mask` selectors is refused, never captured raw) is entirely engine-owned; this skill only surfaces that verdict, never re-implements the guard. Report-only on its own initiative: never edits `manifest.json`/the README block by hand, never commits, pushes, or restarts.
- **`/propagate-vendored`** — turns a `project-scaffolding` component fix into a one-command, Dependabot-style distribution wave instead of N hand-filed issues + N hand-built PRs (~40 mechanical byte-copy PRs across 6–7 repos for two components, `project-scaffolding#144`–`#150`). Fans out a byte-for-byte re-vendor of one named component (`nav`, `tray_lifecycle`, …) to every adopter listed in its `.fleet.toml [vendored]` manifest entry: copy, hash-verify, bump the recorded sha, run that repo's own verification gate, and open an auto-merging PR linking back to the scaffold commit — no per-repo issue, since a byte-for-byte re-vendor carries no decision of its own. `--dry-run` (or bare `check`) reports who's behind, touching nothing. Invoke explicitly (by hand or a periodic batch), never reflex-fired per scaffold commit — see `skills/propagate-vendored/README.md` for the manifest-schema decision writeup.
- **`/audit-fleet`** — scatter-gather wrapper that runs `/codebase-audit` across every `ferraroroberto` repo under `E:\automation\`. A single Python sweep (`skills/_lib/fleet_audit_scan.py`, `--dry-run`-able on demand) enumerates the fleet, syncs each repo, and gates every one of them in one pass — skipping the unchanged, auto-advancing the ledger for repos whose only commits since the last audit are `/cleanup-fleet` fixing their own findings, and batching low-significance organic change until it crosses the weighted-LOC threshold (`below_threshold` bucket, fleet-config#315) — handing the orchestrator a ready-made to-audit list. It then audits the genuinely-changed ones through a bounded concurrency window per the fleet's model-tier policy ([`docs/model-tiers.md`](model-tiers.md)) — audit work runs at `hard` tier, with the ≤3-wide window enforcing the tier's Opus concurrency cap — and emits one diff-based weekly digest, genuinely-new findings called out separately from standing backlog (GitHub comment on the digest-state issue + Slack ping + stdout). Alongside the rot it files, it runs a **second lens on the same read** — a *fleet practices ledger*: each sub-agent surfaces hard-won reusable solutions and generalizable-convention candidates (the inverse of a finding — an asset to remember, not rot to fix), merged into one living catalog issue in `project-scaffolding` so the best of each repo is discoverable fleet-wide. **Self-paces against the live session budget** ([`docs/rate-gate.md`](rate-gate.md)): `statusline-command.ps1` caches the live 5h usage % to `~/.claude/hooks/state/rate-limits.json` on every render (fleet-config#259), so this skill reads it and pauses dispatch proactively, waiting in place until the window resets and resuming in the same run. A bounded 3-pause safety net stops the wait rather than looping forever; anything left over is picked up by next week's idempotent ledger gate. Built to run unattended on a weekly app-launcher job.
- **`/design-sweep`** — the fleet-wide, unattended half of `/design-sync` (fleet-config#180): a scatter-gather wrapper that runs the per-repo design-drift check across every FastAPI + static-PWA web app under `E:\automation\`. One deterministic Python sweep (`skills/_lib/design_sweep_scan.py`) reuses `/audit-fleet`'s filesystem crawl and `design_lint`'s own token detection to gate the fleet down to its token-styled web apps — skipping non-web repos and Streamlit POC spikes — then dispatches one **Sonnet** sub-agent per app (a ≤4 pacing window; Sonnet is exempt from the ≤3-Opus cap) running `/design-sync` report-only, and emits one combined digest (stdout + a `🎨 Design sweep` Slack ping via `--kind design`). Unlike `/audit-fleet`'s cheap orchestrator, this one runs at **`hard` tier (Opus)** — the enumeration/gating/digest reasoning is where a mistake is most expensive — so only ever the one Opus orchestrator is in flight. It owns **no** week-over-week ledger: the durable design-drift accounting lives in the single `audit-fleet digest state` ledger, where `/audit-fleet` tallies open `design-drift` + `cert-drift` issues per repo on a **separate baseline line**, alongside the six code buckets but never conflated with them. This sweep is the *doer* (files/refreshes the per-repo issues, which `/cleanup-fleet design-drift` then clears); `/audit-fleet` is the unified *reporter*. Built to run unattended on a weekly app-launcher job.
- **`/cleanup-fleet <bucket>`** — the fix-half of the audit loop. Takes one bucket label (`documentation`, `claude-md-drift`, `bug`, …), gathers every open issue carrying it across the fleet, scores each for complexity, and fans out **one background agent per repo** sized to the work via the fleet's easy/hard tier policy ([`docs/model-tiers.md`](model-tiers.md)): easy-tier issues run full `/issue-yolo` → merged (each firing its own PR-link ping); hard-tier issues build → stop for your review (per the doc's tier mapping) — and hand back a plain-English rationale summary (what was done, why, and why it's believed correct) rather than expecting a diff read, surfaced inline when the run reports back. One agent per repo by construction (the audit files one issue per repo per bucket). `hard` mode (default) presents the plan for approval and runs both tiers; `easy`/`silent` mode runs only the easy tier unattended and never auto-merges hard-scored work — safe to schedule after `/audit-fleet`. Once you've reviewed the hard-tier branches, `/issue-finish-batch` ships them in parallel (below).
- **`/cleanup-fleet-all [<bucket>...]`** — the genuinely **unattended** sibling of `/cleanup-fleet`: walks all eight queued audit buckets (or a restricted subset for a dry run) in one pass, with **no human review gate at all**. (`security` is never queued — it's self-healed inline by `/codebase-audit`; `cert-drift` is `/design-sync`'s review-only kind, also never queued.) Every issue goes through four independent agents — **build** (implement + verification gate, then stop), **validate** (a fresh agent, no memory of the build, that independently re-runs the gate and leniently judges whether the diff actually addresses the issue), **execute** (ship: push, PR, CI, merge, tray restart), and **teardown** (the terminal step of *every* lane: comment the outcome + any WIP SHA onto the issue, remove the worktree, delete the branch, verify the repo is back on a clean default branch) — so no single agent both builds and ships its own work unchecked, and no lane can end leaving state behind. A failed validation retries the build once with the validator's feedback, capped at 2 rounds total; a second failure **escalates**, meaning *commented on the issue and torn down* — never force-merged, never a branch parked for someone to find later. The retry/ship/escalate decision is deterministic code — a fixed lookup on each agent's schema-validated verdict, not a fourth LLM call re-interpreting an already-decided result — so a long unattended run can't drift or forget state.
  - **Three rules keep an unattended run honest** (fleet-config#518, #515). *Seriality*: one bucket at a time and one repo at a time inside it, the next lane starting only after the current one's teardown reports clean, so at most one worktree exists fleet-wide at any instant. *Teardown* judges its own lane's mess and nothing else — its own branch, its own worktree, the tree it left behind — while conditions it is not mandated to fix (a stale `index.lock`, a primary behind origin, a zombie-pinned empty shell, another lane's branch) are reported and never halt (fleet-config#534, #572). *Halt-on-residue*: a lane that can't be returned to clean halts the run rather than stacking a second worktree on the first. `tests/cleanup_fleet_all_flow.mjs` asserts all three against the real workflow script with stubbed agents, so a re-introduced fan-out fails the gate. Every agent works a forced worktree (`worktree_claim.py acquire … --force-worktree`), never a primary checkout, and a live-e2e guard refusal is a hard stop (`E2E_LIVE=1` is forbidden).
  - **A skipped repo is deferred, never dropped** (fleet-config#642). A repo that is dirty, off its default branch, or already holds a worktree is still skipped — never stashed, never force-switched, that criterion is unchanged — but the run no longer forgets it. The per-repo check is the re-runnable, stateless `skills/_lib/repo_preflight.py` (shaped after `issue_state_gate.py`, whose counts work precisely because something re-runnable computes them); its `skipped` list is the run's deferred set, re-checked once after the last bucket so a repo committed and pushed mid-run is picked up in the same pass, with the retry necessarily re-establishing every fact rather than replaying an hours-old verdict. Whatever is still unavailable lands in one `cleanup-deferred` tracking issue whose **open state means there is unprocessed work** — an empty deferred set closes it, a non-empty one reopens-or-creates it — and the final report carries `skipped: N repos, M issues unprocessed` on every run, zero included, beside the existing `candidates:` line. A run that skipped *every* candidate repo prints `SCHEDULED-RUN-FAILED` rather than reporting a clean sweep.
  - **Shape and runtime.** The build/validate/execute split is the fleet's reusable **independent-review gate** convention, documented in [`docs/independent-review-gate.md`](independent-review-gate.md) (fleet-config#408) so other build-then-ship skills can adopt it deliberately — `/issue-yolo` is the first adopter (fleet-config#433). Built on the **`Workflow` tool** (`.claude/workflows/cleanup-fleet-all.js`, its first use in this repo): the script owns zero Bash/filesystem access — every repo-mutating action happens inside a spawned agent — and the invoking `SKILL.md` never sees any agent's intermediate work, only the final structured result. Designed to run via `claude -p "/cleanup-fleet-all"` headless, so it never backgrounds a tool call and waits for a notification (fleet-config#314); it polls `TaskOutput` to completion within the same turn instead. First run should be attended (see the skill's Notes) before wiring the scheduled job.
- **`/issue-finish-batch <branches>`** — the parallel-finish step after `/cleanup-fleet` or `/issue-batch` build-and-stop. Given a set of already-reviewed branches, it fans out **one background Sonnet finisher per branch** (all at once — Sonnet is exempt from the Opus cap), each running the full `/issue-finish` flow one-shot (push, PR, CI-advisory, merge, delete branch, tray restart) and reporting back **only** on a genuine blocker a human must resolve. User-triggered, never automatic; per-branch `✅ Done` pings are kept and a single `🏁 Finished batch` roll-up closes the run. Manual `/issue-finish` per branch stays the always-available fallback.

## Concurrent same-repo work (claim-or-worktree)

Two agent sessions working the **same** repo used to collide: they shared one working directory, so a `git checkout` in session B rewrote the tree under session A mid-build (fleet-config#143). The collision window isn't branch-cut time — it's the minutes-long *study* phase before either agent writes anything. So the fix claims the repo at the **very first action**, before reading the issue: **first come, first owns `main`.**

`skills/_lib/worktree_claim.py` is the one concurrency primitive. `/issue-start`'s step 0 calls `acquire <repo>`, which atomically publishes a claim — written fully-populated in a private temp dir, then `rename`d into place, because a bare `mkdir`-then-write let two racers both win `MODE=primary` (fleet-config#334) — under the repo's shared git dir (`git rev-parse --git-common-dir`, visible from every worktree). The first session wins `MODE=primary` and works in place on `main`; every session after gets `MODE=worktree` and builds in an isolated sibling worktree `<repo>-wt-<N>` on its own branch, sharing the object store — separate HEAD + separate files, no race. Because `/issue-yolo`, `/issue-batch` in-place, and `/cleanup-fleet` all route through `/issue-start`, they inherit the behaviour for free.

**The branch may already exist.** `setup_worktree()` picks its `git worktree add` form from what's already there (fleet-config#602): an existing *local* branch is checked out as-is, a branch that exists only on `origin` is created from `origin/<branch>` so the lane resumes the work already pushed to it, and only a genuinely new branch is created off the default branch. The previous unconditional `-b <branch> <main>` crashed with a raw traceback on the first case and — silently — started the lane at `main` on the second, so every agent needing a worktree on an existing branch fell back to `acquire --force-worktree` plus a hand-made worktree. The one failure no start point can fix, a branch already checked out in another worktree, now names the holding tree.

**The worktree is a faithful runtime twin**, differing only where sharing is the bug. `setup_worktree()` stages the primary's gitignored runtime config (`config/*.json`, excluding `*.sample.json` templates) into the new worktree, since `git worktree add` only populates tracked files — without it, a repo's e2e suite silently mass-skips inside the worktree while its own pre-ship gate still reports green (fleet-config#470). That copy is byte-verbatim **except for a top-level `port`**, which is repointed into the `8500–8999` band — deterministic from the issue number, then probed past anything listening or already handed to a sibling config in the same worktree, so a repo with two ported configs gets two distinct ports. Carrying the primary's port across made every lane's e2e suite see the user's live tray and refuse to run, and left a worktree that actually boots the app trying to bind the primary's port (fleet-config#537). Secrets and every other field copy untouched.

**Release is a verified step.** `/issue-finish` releases the claim (primary) or tears the worktree down (worktree), confirming `status` → `CLAIM=free` so a foreign or abbreviated finisher can't silently skip it; `/issue-yolo`'s inline-merge path releases the claim itself in Phase 4, since it has no separate finish (fleet-config#174). A claim left behind anyway self-heals on the next `acquire`: it's reclaimed once it ages past the 8h TTL **or** as soon as its recorded branch no longer exists on the remote (a merged-and-deleted branch is definitionally done — `is_stale` checks `git ls-remote`).

**The claim decides only *tree selection*** — it says nothing about who holds it at the moment something actually runs `git checkout <main>` on the primary, and a concurrent flow that reached the primary tree without its own live claim did exactly that against a session with 7 uncommitted files (`app-launcher#633`, fleet-config#473). `assert-owner <repo> <issue>` closes that gap: `/issue-finish` step 5 and `/issue-start` step 4 both call it immediately before their `git checkout <main>`, refusing (with the "primary held since..." message) unless the tree is clean and the claim is free or already owned by the calling issue. It guards only those two call sites — a hand-run `git checkout`, a sub-agent, or a future skill still bypasses it, since this is a flow-level precondition, not an enforced boundary (a `PreToolUse` hook was tried for the adjacent problem and reverted within the hour for blocking legitimate operations fleet-wide, fleet-config#464).

**A running process is not a claim holder.** The launcher webapp, home-automation's tray, and this repo's own `hooks/`+`skills/` junctioned into every live `~/.claude` hold no claim, so a first-and-only unattended agent legitimately wins `MODE=primary` and edits files a live process is serving (fleet-config#515). `acquire --force-worktree` closes that for unattended fleet fanout: it skips the claim attempt entirely, always prints `MODE=worktree`, and deliberately publishes no claim so the primary stays free for a human session. `/cleanup-fleet`, `/cleanup-fleet-all`, and `/codebase-audit`'s security self-heal all use it — and so does `/issue-start` itself whenever `APP_LAUNCHER_SESSION_ID` is set, i.e. whenever App Launcher's Board dispatched the session rather than a human starting it (fleet-config#525). An interactive `/issue-start` with no such variable keeps the default claim-or-worktree behaviour, which is correct there.

**`mode` answers about the cwd, not about its argument.** The primary-vs-worktree answer is the hinge every teardown turns on, and it was silently wrong in exactly one direction. `mode <repo>` with a bare name — the form all three finishing skills document — hit `_resolve_path_arg`'s sibling fallback (added for `remove-worktree fleet-config-wt-7`, fleet-config#165): from inside `fleet-config-wt-652`, `fleet-config` doesn't resolve locally, so it resolved to the *primary*, and `is_primary_checkout` truthfully answered `primary` about the tree it was handed. A worktree lane believing that takes the primary teardown path and runs `gh pr merge --delete-branch`, producing the very `'main' is already used by worktree` failure #647 shipped to eliminate — no error, no `unknown`, and the wrong answer always the more dangerous one. `mode` now reads the cwd's own checkout and treats the argument as *identifying the repo* rather than selecting a tree (fleet-config#652): reconciliation compares shared git dirs, so a worktree naming its own primary is a match, while a genuinely different repo, an unresolvable name, or a cwd outside git prints `UNKNOWN reason=<why>` and exits 2 — a helper that cannot establish which checkout it was asked about says so instead of guessing. The fallbacks themselves are untouched, still right for `remove-worktree`. Its sibling subcommands were audited and need no change: `land-primary` and `remove-worktree` act on a *named* target by design (and each already refuses a wrong-kind target), while `acquire`/`release`/`status` are repo-scoped — their lock lives in the shared git dir and `git worktree list` reads identically from every tree, so argument-vs-cwd resolution cannot change their answer.

**A worktree lane still has to land the primary.** "Never `git checkout <main>` from a worktree" was silently read as "never touch the primary at all", so the worktree branch of `/issue-finish` ended at `remove-worktree` with no landing step *and no statement that landing hadn't happened* — leaving the primary behind `origin` while the lane reported the change shipped. Here that is severe rather than cosmetic: `hooks/` and `skills/` reach `~/.claude` from the primary, so a merged hook or skill change does nothing fleet-wide until that tree fast-forwards (on 2026-08-16 the primary sat 2 commits behind with two merged PRs reported as shipped; `project-scaffolding`'s primary kept a *failing* local gate after the PR fixing it had merged). `land-primary <repo> <issue>` closes it (fleet-config#647): `assert-owner`'s guard plus "already on the default branch", then `pull --ff-only` and a `rev-list --count HEAD..origin/<default>` check, printing exactly one `PRIMARY=live behind=0` / `PRIMARY=stale reason=<why>` line that the finish summary quotes verbatim. The original caution is intact — it never checks out, stashes, or forces, and `--ff-only` fails safely rather than merging; a refusal is *reported*, never recovered, because merged and live are two facts and a lane that cannot establish the second must say so rather than let silence imply it. The same call site also drops `--delete-branch` in worktree mode (its local half fails `'main' is already used by worktree` — 6 for 6 that day, and six lanes invented six different recoveries), deleting the remote ref explicitly and the local one with `-D` only after an ancestry check, since a squash merge rewrites the SHA and defeats `-d`.

**Teardown is symmetrically defensive.** `remove-worktree` tolerates a worktree git has already **deregistered** while its directory survives — the state a leaked process leaves behind — by inverting the `<repo>-wt-<N>` convention when `rev-parse` can no longer resolve the primary, always after the junction strip, and exiting non-zero with the path named if the tree is still there afterwards, so the caller reports honest residue instead of a false clean (fleet-config#526). It also refuses outright (exit 2, deletes nothing) unless its target actually *is* a linked worktree: a primary checkout (`--git-common-dir` == `--git-dir`) is rejected, and a basename that doesn't match `<repo>-wt-<N>` is rejected unless `--force-nonstandard-name` is passed (fleet-config#589).

`skills/_lib/active_issue.py` publishes the issue-level lifecycle that App Launcher's Board consumes (fleet-config#376 ↔ app-launcher#528). `/issue-start` adds `<repo>#<number>` to `~/.claude/hooks/state/active-issues.json` once its branch is ready; `/issue-finish` and `/issue-yolo` remove it only after a successful merge. `/issue-batch`'s in-place path inherits `/issue-start`, while its pre-created worktree path writes explicitly before dispatch. Each row carries `repo`, `number`, `branch`, and `started_at`; mutations prune rows older than 24 hours so a crashed agent cannot disable a card forever. The helper tolerates a missing/corrupt file, uses atomic replacement, and locks the whole read-modify-write transaction so simultaneous batch starts cannot lose unrelated rows. `CLAUDE_HOOKS_STATE_DIR` redirects the file for hermetic tests.

Two Windows specifics, both load-bearing. **The `.venv`** — worktrees don't share untracked files, and a 24-repo fleet can't recreate heavy venvs per worktree, so the helper *junctions* (`mklink /J`) the primary's `.venv` into the worktree; a junctioned venv resolves `sys.prefix` and imports through the link, so the verification gate (`& .\.venv\Scripts\python.exe …`) just works. **The teardown order** — `git worktree remove` does a recursive delete that *follows a junction into its target*, so the helper strips the `.venv` junction with `rmdir` (reparse-safe, no `/s`) **before** `git worktree remove`, or it would wipe the primary's real venv (same junction footgun as `uninstall.ps1`, fleet-config#136). Never hand-roll `git worktree add`/`remove` + a venv junction in a skill; the helper owns both halves. The `<repo>-wt-<N>` sibling naming is deliberate: `hooks/_lib.py`'s `detect_project()` strips a trailing `-wt-<N>` suffix from the path segment that carries it before matching against the repo's `cwd_prefix` in `projects.toml` (falling back to it only when the raw cwd matches nothing, so a repo whose real name happens to contain that shape still matches directly first), so `notify_on_idle` names the right project even when called from inside the worktree (fleet-config#471; a `.worktrees/` layout would break that match). `/audit-fleet`'s filesystem crawl skips linked worktrees via a `.git`-is-a-directory guard.

## UX-conformance gate (diff-keyed design check)

`skills/_lib/ux_surface.py` is the second cross-skill primitive — it decides, deterministically, whether an issue's change touched a web app's UX so the issue-workflow skills can gate the fleet design check on the *diff* rather than re-deriving a glob match in three places (fleet-config#195; convention + contract in `project-scaffolding#83`). A repo declares its surface in a `## UX surface` block in its own `CLAUDE.md` (`design spec applies`, `paths`, `key views`); a repo without one — `fleet-config` itself, any non-web repo, a Streamlit spike — yields `SPEC_APPLIES=no`, so the gate is a permanent no-op there. `applies <repo>` (block only, no git) drives the cheap design-aware spec-load at `/issue-start`; `check <repo>` adds `git diff --name-only <main>...HEAD` and reports `TOUCHED` + the `MATCHED` files for the gate at `/issue-finish` (step 3b) and `/issue-yolo` (Phase 3e). When the diff *did* touch UX, the gate fixes material token drift in-branch (not file-and-defer — that's `/design-sync`'s periodic job) and visually verifies the touched view via the `verify` skill. **The screenshot is inspected in-session only and never attached to a PR/issue/comment** — every repo is treated as public, so an uploaded UI screenshot is an information breach; the PR carries a text-only conformance line instead. Its block parser, brace expansion, glob→regex, and diff intersection are pure-logic unit-tested (`tests/test_ux_surface.py`, reached from the one acceptance gate).

## Deploy-coverage gate (merged is not shipped)

`skills/_lib/deploy_coverage.py` enforces the `project-scaffolding#199`/`#200` convention that a change is not done merely because it merged — the gap that let `home-automation#314` and `app-launcher#611`/`#615` report as shipped while a runtime component kept serving old code. A repo declares each not-fully-covered runtime component (out-of-tree, or an in-tree process deliberately excluded from the standard restart) in its own `CLAUDE.md` — a `## <component name>` heading whose bullets include `what/why`, `update command`, `liveness signal`, and `NOT restarted/deployed by`; app-launcher's `:8446` session-host (`GET /api/version`'s `session_host.stale`, `app-launcher#615`) is the reference case. A repo with no such block — nearly every repo today, including `fleet-config` itself — gets `DECLARED=no` and pays nothing: no git call, no extra step. `check <repo>` additionally diffs `<main>...HEAD` against the path-looking backtick tokens in each declared component's prose (the scaffold's template has no structured `paths:` field, unlike the sibling UX-surface block above, so a future reword can silently change what's detected) and reports `TOUCHED=yes|no|unknown` per component; `unknown` (no parseable path) is treated as touched, never as a silent "no". `/issue-finish` (step 6b) runs this after the restart step and, for any touched-or-unknown component, reads that component's liveness field from the same build-identity poll rather than issuing a second request — never blocking, never invoking the declared update command itself (a confirmation-gated manual action stays a human/operator call), only qualifying the finish summary across three honest outcomes: confirmed live, **merged but not yet live**, or unknown. Parser + matcher are pure-logic unit-tested (`tests/test_deploy_coverage.py`, reached from the one acceptance gate).
